- 슬라이드: [slides/slides.md](../slides/slides.md) (Slidev)
  - 실행: `npm run dev --prefix slides` / PDF: `npm run export --prefix slides`
  - 멘트는 각 슬라이드의 발표자 노트에 있고, 발표자 모드(`P`)에서 보인다.
- 분량: 15분 이내. 슬라이드 17장 (표지 1 + 부 표지 3 + 내용 13)
- 청중: 오픈소스 기여를 시작하지 못한 개발자
- 핵심 메시지: **good first issue로 시작해, 한 프로젝트 안에서 기여 범위를 넓혀 간다**
- 디자인: 흰 배경 + 파랑 강조, assertion-evidence 방식 — 제목은 짧은 명사형 한 줄, 본문은 증거 하나(캡처·카드·표).
- 문장 규칙: 제목은 명사형으로 짧게 끝낸다("~찾기", "~오타부터", "~후 구현"). 슬라이드 본문 문장은 평서(한다체), 멘트는 존댓말. 무생물 주어·명사 종결·경구 금지. 겪은 일을 법칙·교훈으로 일반화하지 않는다 ("~하면 ~한다", "~해야 한다" 금지). 역할을 부여하는 동사("맡았다") 주의.

## 슬라이드 구성 (덱과 동기화: 2026-08-21)

### 1. 표지 — 오타 수정에서 시작해 기능 머지까지
- 화면: 제목 + 오늘 답할 질문 세 개 (어디서 찾나 / 어떻게 기여하나 / 이력서에 어떻게 쓰나)
- 멘트: "안녕하세요, 이건창입니다. 제 첫 머지는 오타 수정이었습니다. 3개월 뒤에는 기능을 머지했고요. 오늘은 세 가지 질문에 그 3개월로 답하겠습니다. 어디서 찾는지, 어떻게 기여하는지, 이력서에 어떻게 쓰는지."
- PR 개수 같은 숫자는 화면에 쓰지 않는다 (적어 보인다). 3개월이라는 기간은 말로만.

### 1부 표지 — 오픈소스 찾는 방법
- 멘트: "저도 처음엔 어디서부터 시작할지 몰랐습니다." (실제 상황 맞는지 확인 필요)

**2. good first issue부터 찾기**
- 화면: goodfirstissue.dev 캡처 ✓
- 문장: "goodfirstissue.dev — 언어·프로젝트별로 모아 보여준다. 여기서 시작했다."
- 멘트: "good first issue는 메인테이너가 '입문자가 해도 된다'고 미리 골라 둔 이슈입니다. goodfirstissue.dev에 언어별로 모여 있고, 저는 여기서 시작했습니다. 팁 하나 — 아무 저장소나 주소 뒤에 /contribute를 붙이면 그 저장소의 목록이 나옵니다."

### 2부 표지 — 오픈소스 기여 방법 (fixture-monkey에서 보낸 3개월)
- 멘트: "찾았으면 다음은 어떻게 기여하느냐입니다. fixture-monkey에서 보낸 3개월을 순서대로 보여드리겠습니다."

**3. 오타에서 기능까지 3개월**
- 화면: fixture-monkey 기여 11건 목록 캡처 ✓ (전부 Approved)
- 멘트: "3개월 동안 올린 기여를 한 화면에 모은 겁니다. 전부 Approved로 닫혔고, 아래가 1월 오타 수정, 위가 4월 체인지로그입니다. 이제 이 목록을 단계별로 하나씩 보겠습니다."
- 역할: 2부 전체의 목록만 보여준다. "순서"는 9장이 맡으므로 여기서 언급하지 않는다 (중복 방지).

**4. 첫 PR은 오타부터** (#897, #895)
- 화면: PR 카드 2개 (제목·번호·Approved)
- 문장: "작으니까 금방 머지됐고, 그 덕에 다음 기여로 넘어갈 수 있었다"
- 멘트: "첫 PR은 문서 오타를 고친 겁니다. 작으니까 금방 머지됐고, 그 덕에 다음으로 넘어갈 수 있었습니다."

**5. 번역으로 기여** (#878, #894, #901, #904)
- 화면: 문서 PR 카드 4개 (각 카드에 "번역 추가" 표기)
- 문장: "2주 동안 PR 6개로 한국어 문서 4페이지를 번역해 추가했다"
- 멘트: "코드가 아니어도 기여입니다."

**6. 이슈 생성 후 구현** ([#962](https://github.com/naver/fixture-monkey/issues/962))
- 화면: 이슈 대화 카드 — 제안 + "PR도 제가 만들겠습니다" + 메인테이너 "Sounds great. Could you make a PR for it?"
- 문장: "발견한 문제를 이슈로 제안하고, 직접 구현해 #929로 머지했다"
- 멘트: "이번엔 쓰면서 불편했던 걸 이슈로 만들었습니다. Duration 필드에 Long을 넣어야 해서 불편했거든요. PR도 제가 만들겠다고 했고, 메인테이너가 바로 좋다고 답했습니다. 방향을 합의한 뒤에 구현해서 #929로 머지됐습니다."
- 배운 것은 8장에 모았다 (슬라이드당 증거 하나 유지).

**7. 기능 머지 이후의 기여** (#929, #967, #968, #975)
- 화면: 기능 머지(강조) + 버그 수정 + deprecated 제거 + 체인지로그 카드
- 멘트: "기능이 머지된 뒤에도 버그 수정, deprecated 정리, 체인지로그까지 이어서 했습니다. 시켜서 한 게 아니라 눈에 띄는 걸 직접 찾아서 했습니다." (역할을 맡은 게 아니라 개인적으로 진행한 것 — 사실관계 주의)

**8. 기여하면서 배운 것**
- 화면: 카드 2개
  - 기능을 구현하면서 (#929) — TDD로 어려운 문제를 단계적으로 해결하는 방법 / 스택트레이스로 원인을 찾는 방법
  - 유지 작업을 하면서 (#967 #968 #975) — 오래 유지되는 코드를 관리하는 방법 / 사이드 이펙트를 줄이는 방법
- 멘트: "구현할 때는 실패하는 테스트부터 만들었습니다. 원하는 로직을 테스트로 적어 두면 처음엔 실패하는데, 에러 스택트레이스를 따라가면서 고칠 위치를 찾았습니다. 유지 작업을 하면서는 메인테이너가 오래 유지되는 코드를 어떻게 관리하는지, 사이드 이펙트를 어떻게 줄이는지를 배웠습니다."
- 6·7장에 흩어져 있던 배운 것을 여기 모았다. 유지보수 항목의 근거는 2024년 이력서 초안 문장.

**9. 기여한 순서**
- 화면: 오타 → 문서 → 이슈 제안 → 기능 → 유지 작업, 화살표 단계 그림 (각 단계에 PR 번호) + 하단 한 줄 "메인테이너는 기여 이력이 있는 사람의 PR을 더 잘 받아준다" (출처: Gousios et al. 2014 · Tsay et al. 2014)
- 멘트: "정리하면 이 순서입니다. 오타, 문서, 이슈, 기능, 유지 작업. 작은 기여부터 순서대로 올라갔습니다. 연구로도 확인된 사실인데, 메인테이너는 기여 이력이 있는 사람의 PR을 더 잘 받아줍니다. 메인테이너 손이 덜 타는 영역부터 기여하면서 이해도를 높이면, 메인테이너를 번거롭게 하는 질문이 줄어듭니다. 그렇게 기여 빈도와 기간을 늘려 가면서, 나중에는 메인테이너와 함께 어려운 문제를 풀어 보시길 바랍니다."
- 근거: PR 수락 요인 연구 — [Gousios et al. 2014](https://dl.acm.org/doi/10.1145/2568225.2568260) (기여자의 track record가 수락에 영향), [Tsay et al. 2014](https://dl.acm.org/doi/10.1145/2568225.2568315) (프로젝트 내 사전 상호작용이 많을수록 수락 확률 상승), [NPM 생태계 연구 (EMSE 2025)](https://link.springer.com/article/10.1007/s10664-025-10706-1) (생태계 전체 기여 이력도 수락에 긍정적)

### 3부 표지 — 오픈소스 이력서 정리 방법
- 멘트: "마지막으로, 이걸 이력서에 어떻게 쓰느냐입니다."

**10. 개발자를 보는 여섯 축**
- 화면: 『육각형 개발자』 표지만 (최범균, 한빛미디어) ✓
- 멘트: "『육각형 개발자』라는 책이 있습니다. 제목처럼 개발자는 구현 하나가 아니라 여러 축으로 평가받는다는 관점입니다. 책이 말하는 여섯 축 — 구현 기술, 품질·코드 이해, 아키텍처·패턴, 응집도·결합도, 리팩터링·테스트, 업무 관리·공유. 이 축들을 오픈소스 기여로 어디까지 보여줄 수 있는지 정리해 봤습니다."
- 축 출처: [Wormwlrm의 책 리뷰](https://wormwlrm.github.io/2023/08/13/Hexagonal-Developer.html)

**11. 여섯 축으로 본 내 기여**
- 화면: 레이더형 육각형 그래프(SVG, 상=3칸·중=2칸·하=1칸) + 오른쪽 축별 근거 문장. 기준: 상 = 머지 기록으로 증명, 중 = 기여 과정에서 배움, 하 = 오픈소스로 드러나기 어려움

  | 축 | 어필 | 근거 |
  |---|---|---|
  | 구현 기술 | 상 | 라이브러리에 없던 타입 지원을 구현해 머지했다 |
  | 품질·코드 이해 | 상 | 처음 보는 코드에서 고칠 위치를 찾아냈고, 쓰지 않는 코드를 정리했다 |
  | 리팩터링·테스트 | 상 | 테스트를 먼저 작성하고 코드를 고쳐 나갔다 |
  | 응집도·결합도 | 중 | 기존 설계 안에서 수정하며 모듈 경계를 배웠다 |
  | 아키텍처·패턴 | 중 | 라이브러리의 설계와 패턴을 읽으며 배웠다 |
  | 업무 관리·공유 | 하 | 마감과 우선순위 없이 하고 싶은 일만 골라서 한다 |

- 멘트: "책의 여섯 축에 제 기여를 대응해 봤습니다. 상은 머지 기록으로 증명되는 축, 중은 기여 과정에서 배운 축입니다. 업무 관리는 오픈소스로 드러나기 어렵습니다. 마감과 우선순위 없이 하고 싶은 일만 골라서 하니까요."
- 중 등급 두 축의 근거 문장은 실제 경험과 맞는지 확인 필요.

**12. AI 이후 달라진 머지 기록의 가치**
- 화면: 표 하나

  | | AI 이전 | AI 이후 |
  |---|---|---|
  | PR이 증명하는 것 | 이 코드를 짤 수 있다 | 문제를 찾고, 합의하고, 검증을 통과했다 |
  | 이력서에서의 역할 | 기술 스택의 근거 | 메인테이너가 검증한 공개 기록 |

- 문장: "AI가 코드를 대신 짜 주면서, '만들었다'는 말만으로는 실력을 보여주기 어려워졌다"
- 멘트: "AI가 코드를 대신 짜 주면서 '만들었다'는 말의 힘이 약해졌습니다. 머지는 다릅니다. 메인테이너가 심사해서 통과시킨 기록이고, 링크만 열면 누구나 확인할 수 있습니다."

**13. 역량 한 문장 + PR 하나**
- 화면: 실제 이력서 문장 2개 + 증거
  - "처음 보는 대량 코드에 위축되지 않고 방향을 잡는다" ← #929

- 자료 출처: `개인 문서/_지식 정리/24-4 ✅ AVID/1주차 피드백 결과.md`

## 오픈소스로 보여줄 수 있는 능력 / 없는 능력 (11장 근거, Q&A 대비)

- 상·중·하 기준: 상 = 머지 기록으로 증명되는 축, 중 = 기여 과정에서 배운 축(응집도·결합도, 아키텍처·패턴 — 기존 설계를 읽고 그 안에서 수정하며 배운다), 하 = 오픈소스로 드러나기 어려운 축(업무 관리·공유 — 마감·우선순위 없이 하고 싶은 일만 고른다).
- 육각형 축 밖에서도 못 보여주는 능력이 있다: 말로 하는 실시간 소통, 운영 책임(온콜·장애 대응), 리뷰하는 쪽의 역할(기여자는 리뷰를 받는 쪽).
- 한계를 먼저 말하면 3부 주장이 과장으로 들리지 않는다.

## AI 활용 기여로 어필 가능한 능력 (Q&A 대비, 리서치 2026-08-21)

배경: AI로 그럴듯한 PR을 만드는 비용이 0에 가까워지며 저품질 AI PR이 쏟아졌다. Python 생태계의 Jazzband는 AI 스팸 PR을 감당하지 못해 문을 닫았고, Ghostty·curl·QEMU 등이 AI 기여 정책을 강화했다. 메인테이너들이 요구하는 건 AI 금지가 아니라 "책임지는 사람"이다.

Kubernetes AI 기여 가이드라인(2026-06) 기준으로 어필 가능한 능력:
1. **검증 능력** — "작동한다"로는 부족하고 왜 작동하는지 설명해야 한다. AI를 쓴 PR이 머지됐다는 건 이 검증을 통과한 공개 기록.
2. **설명 능력(오너십)** — 리뷰어 질문에 본인이 답해야 하며, 설명 못 하면 거절된다.
3. **투명성** — AI 사용을 PR 설명에 명시하는 게 정책. 밝히고도 머지된 기록이 차별점.
4. **선별·판단 능력** — AI가 만들 수 있는 무한한 변경 중 프로젝트에 필요한 것을 고르는 판단 (이슈 선합의 방식이 여기에 해당).
5. **정책 준수** — 프로젝트별 AI 정책을 읽고 맞추는 것 자체가 역량.

취준생 채용 기준과의 대응 (2026 신입 채용 트렌드):
- AI 산출물 검증 역량(AI 허용 코딩테스트 확산, AI 역량 요구 공고 1년 새 2배) ← 머지된 AI 활용 PR
- 문제 정의력(기업들이 코딩 실력보다 앞세우는 기준) ← 이슈 제안 #962
- 디버깅 능력(테스트 작성 + 에러 단계적 추적) ← TDD·스택트레이스 사례
- 설명 능력("왜 이 방식인지") ← 리뷰 대응 공개 기록
- 협업 경험(신입 면접 단골, 실무 경험 부재의 대체재) ← 리뷰 왕복 기록
- 주의: 검증 없이 던져 닫힌 AI PR도 공개 기록으로 남는다. PR 수보다 머지되는 PR.
