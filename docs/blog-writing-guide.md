# Blog Writing Guide

이 문서는 `hello tis blog`에 글을 추가할 때 따르는 작성 기준이다.

## 문체와 첨삭 원칙

모든 글의 작성·수정에 적용하는 사용자 선호다.

- **정확한 전문 용어:** 모호한 비유 대신 기술적 조건과 현상을 쓴다. 예를 들어 “테스트 데이터가 가벼웠다”는 “운영 데이터 규모를 반영하지 못했다”로 고친다.
- **최소한의 단어:** 의미를 유지하면서 수식어, 반복 설명, 불필요한 도입과 결론을 삭제한다. 문장을 줄이더라도 조건과 인과관계는 유지한다.
- **일관된 용어:** 같은 개념은 같은 용어로 쓴다. 표현을 다양하게 하려고 동의어를 섞지 않는다. 서로 다른 지표나 개념은 구분한다.
- **구체적인 범위와 조건:** “수백 ms”, “소량”, “훨씬”, “허용 범위” 대신 측정 범위나 판단 조건을 명시한다. 수치가 없으면 미확인으로 적고, 근사값을 정확한 값처럼 쓰지 않는다. 조건·한계·검증 항목처럼 병렬인 내용은 불릿으로 구분한다.
- **AI 문체 편집 방법 조사:** 사용자가 말하는 “AI 워싱”은 어색한 AI 문체를 자연스럽게 첨삭하는 작업이다. 관련 편집 방법을 조사해 적용한다. 단순한 동의어 치환보다 구체적인 표현, 문장 연결, 중복 제거를 우선한다.
- **시간 단위:** 1초 미만은 ms로 표기한다. 예: `0.38448초` → `384.48ms`.
- **그래프 설명:** 이미지 아래에는 사용률·시간·구간 최댓값 등 관측값을 짧은 불릿으로 쓴다. “포화가 관찰됐다”, “단독 원인은 미확정” 같은 해석만으로 설명을 끝내지 않는다. p99의 구간 최댓값과 테스트 전체 p99를 구분한다.
- **전체 문장 재검토:** 제목, description, 본문, 표, 코드 주석, 그래프 문구와 이미지 설명까지 검토한다. 수정한 문장이 기존 문장과 자연스럽게 이어지는지도 확인한다.
- **사실 보존:** 수치, 단위, 측정 조건을 유지한다. 실측값·추정값·계획을 구분하고, 확인하지 않은 결과를 추가하지 않는다.

편집 참고 자료:

- [Google 기술 문서 가이드: 용어 일관성](https://developers.google.com/style/translation#use-consistent-terminology)
- [GOV.UK: 명확하고 간결한 문장](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/)

## 글 작성 흐름

1. 글의 목적을 먼저 정한다.
   - 운영 기록: `Operations`
   - 개발 환경, 생산성, 내부 도구: `Platform`
   - API, 도메인, 제품 요구사항 구현: `Product`
   - AI 기능, 에이전트, RAG, 평가: `AI`
   - 책, 강의, 스터디, 기술 실습: `Study`
   - 주간 회고: `Weekly Review`
   - 연간 회고: `Annual Review`
2. `src/content/posts/` 아래에 Markdown 또는 MDX 파일을 만든다.
3. frontmatter를 먼저 작성한다.
4. 글 유형에 맞는 본문 구조를 따른다. 낙서장 글은 `상황 → (문제) → 원인 → 해결 → 결과` 순서로 쓴다.
5. 이미지나 그래프가 있으면 원본 수치와 함께 남긴다.
6. `pnpm astro check`로 콘텐츠 스키마를 확인한다.

## 파일 이름

파일 이름은 URL이 되므로 영어 소문자와 하이픈을 사용한다.

```text
src/content/posts/2026-week-27-review.md
src/content/posts/deployment-checklist-as-platform.md
src/content/posts/api-permission-modeling.md
```

하위 폴더는 URL에 포함된다. 정리용 폴더가 필요하지만 URL에는 빼고 싶다면 `_`로 시작한다.

```text
src/content/posts/_drafts/not-routed.md
src/content/posts/_assets/image.png
```

## Frontmatter

모든 글은 아래 형태를 기본으로 한다.

```md
---
title: 배포 파이프라인을 제품처럼 다루기
description: CI/CD를 내부 사용자 경험 관점에서 개선한 기록입니다.
pubDatetime: 2026-07-02T00:00:00Z
tags:
  - Platform
---
```

허용되는 태그는 하나만 선택한다.

```text
Operations
Platform
Product
AI
Study
Weekly Review
Annual Review
```

`Study`는 학습 과정과 그 과정에서 생긴 판단 기준이 글의 중심일 때 사용한다. 공부한 내용을 제품, 플랫폼, 운영 환경에 적용해 실제 결과를 낸 것이 중심이라면 해당 영역의 태그를 사용한다.

날짜는 UTC ISO 형식으로 쓴다. 한국 시간 기준으로 날짜만 중요하면 `T00:00:00Z`를 사용한다.

### Description 작성 기준

목록 카드에서 글의 핵심을 한눈에 파악할 수 있도록 짧은 한 문장으로 쓴다.

- **내용:** 무엇을 다뤘고 어떻게 풀었는지, 또는 무엇을 바꿨는지를 담는다.
- **길이:** 공백을 포함해 40 ~ 60자 안팎을 권장한다. 글자 수보다 카드의 두 줄 안에서 문장이 끝나는지를 우선한다.
- **표현:** 독자가 바로 이해할 수 있는 말로 쓴다. 배경, 세부 조건, 전문 용어를 나열하지 않는다.
- **확인:** 제목과 함께 읽었을 때 글의 주제가 드러나고, 말줄임표로 핵심 내용이 잘리지 않는지 확인한다.

낙서장 글의 예시는 다음과 같다.

```yaml
description: 출석 리워드의 복잡한 조건을 변수와 경계값으로 나눠 테스트를 설계했습니다.
```

```yaml
description: 출석과 리워드의 상태 조합을 정리하고, 서버에서 화면을 선택하도록 바꿨습니다.
```

### 카테고리에서 제외하는 글

스터디 결과처럼 일반 공개하되 홈의 주제 보드와 태그·카테고리 페이지에 추가하지 않을 글은 `hideFromCategories: true`를 사용한다.

```md
---
title: "설계 노트: 재고 원장과 스냅샷으로 동시성 다루기"
description: 시스템 설계 스터디 결과를 정리한 공유용 문서입니다.
pubDatetime: 2026-08-07T00:00:00Z
tags:
  - Study
hideFromCategories: true
---
```

이 글은 일반 게시물처럼 직접 URL, 전체 글, 아카이브, RSS, 검색에서 접근할 수 있다. 홈의 주제 보드와 태그·카테고리 페이지에서만 제외한다. 완전히 접근할 수 없는 초안은 `_drafts/`에 둔다.

### 낙서장 글 제목

낙서장은 개발 중 생긴 질문과 판단 과정을 정리하는 글의 작성 형식이다. 현재는 별도 태그가 없으므로 글의 주제에 맞는 기존 태그를 선택한다.

- 제목에는 항상 날짜를 넣고, `YYYY년 M월 D일: 제목` 형식으로 쓴다.
- 날짜는 `pubDatetime`의 한국 시간 기준 날짜와 맞춘다. 글을 수정해도 제목의 날짜는 바꾸지 않는다.
- 파일 이름과 URL에는 날짜를 추가할 필요가 없다.

```md
---
title: "2026년 9월 7일: 어떤 화면을 보여 줄지는 서버에서 정하기로 했다"
description: 출석과 리워드의 상태 조합을 정리하고, 서버에서 화면을 선택하도록 바꿨습니다.
pubDatetime: 2026-09-07T00:00:00Z
tags:
  - Product
---
```

### 설계 스터디 글 제목

설계 스터디 결과를 공유하는 글은 `설계 노트: {핵심 문제 또는 의사결정}` 형식으로 쓴다. 회차 번호는 제목에 넣지 않는다.

```text
설계 노트: 재고 원장과 스냅샷으로 동시성 다루기
설계 노트: 포인트 차감과 결제 사이의 정합성 다루기
```

## 본문 구조

읽는 사람이 무슨 일이 있었고, 어떻게 판단하고 바꿨는지 따라올 수 있게 쓴다. 낙서장은 아래 고정 구조를 따르고, 다른 글은 이어지는 유형별 구조를 참고한다.

### 낙서장 글

상위 제목은 `상황 → (문제) → 원인 → 해결 → 결과` 순서로 고정한다. 괄호는 선택 항목이라는 뜻이며 실제 제목에는 넣지 않는다.

| 제목 | 담을 내용 |
| --- | --- |
| 상황 | 독자가 알아야 할 서비스 배경과 기존 동작, 처음 의도 |
| 문제 | 기존 방식으로 다루기 어려워진 상황과 영향. 상황에서 충분히 설명했다면 생략 |
| 원인 | 문제가 생긴 이유와 조사하거나 학습한 내용. 참고한 개념을 사례에 어떻게 적용했는지 연결 |
| 해결 | 비교한 선택지, 선택 이유, 실제로 바꾼 내용 |
| 결과 | 확인한 변화와 남은 제약. 필요한 경우 다음에 확인할 내용 |

```md
## 상황

## 문제

## 원인

## 해결

## 결과
```

- `상황`, `원인`, `해결`, `결과`는 유지한다. 세부 내용은 각 절 아래 `###` 제목으로 나눈다.
- 결과를 아직 확인하지 못했다면 현재 확인한 범위를 적는다. 별도의 마무리 절에서 결론을 반복하지 않는다.
- 역할이나 조건을 나란히 설명할 때는 불릿을, 선택지의 장단점을 비교할 때는 표를 사용한다. 판단 과정은 문단으로 연결한다.

#### 자료가 추가될 때의 편집 기준

- 반복 개선은 측정 회차보다 변경 목적을 제목으로 쓴다. `원인`에는 초기 분석을 두고, `해결`에서는 각 개선을 `판단 이유 → 변경 사항 → 측정 결과`로 통일하고 관련 그래프를 함께 묶는다. 이전 단계에서 남은 문제를 다음 개선의 판단 이유로 연결한다. 전체 통계는 `결과`에서 한 번만 비교한다.
- 새 자료는 역할에 맞는 절에 배치한다. `원인`에는 가설·근거·측정 한계, `해결`에는 변경 사항·선택 이유·검증 방법, `결과`에는 측정값·판단·남은 검증을 둔다.
- 부하테스트의 초기 ASIS는 `문제`, 최종 TOBE는 `결과`에 둔다. 개선별 비교가 필요하면 해당 단계에 ASIS·TOBE 표를 넣고 최종 중복 표는 제거한다. 같은 API·지표로 비교하고, 별도의 k6 지표 표나 요약으로 같은 수치를 반복하지 않는다.
- 표에는 수치, 본문에는 해석을 쓴다. 초기 트레이스는 `원인`, 개선 후 트레이스는 해당 개선 단계에 두고, 전체 테스트 통계와 구분한다.
- 수정할 때 새 내용만 덧붙이지 않고 기존 설명과 통합한다. 테스트 태그·실행 명령·VU 설정 등 실행 정보는 판단 과정을 이해하는 데 필요할 때만 포함한다. 비교에 필요한 변경 변수·부하 조건·측정값을 우선한다.

### 다른 유형의 글

기본 흐름은 아래와 같다.

```md
## 개요

처음 3~5문단 안에서 사건, 원인, 대응, 결과를 먼저 말한다.
장애나 성능 개선 글이라면 숫자를 여기서 바로 보여준다.

## 결과부터

벤치마크, 장애 건수, 처리량, 비용, 응답시간처럼 결론을 숫자로 보여준다.
성과가 핵심인 글일 때만 사용한다.

## 딥다이브 1 : 첫 번째 쟁점

문제를 작게 나누고, 조건 분기, 내부 동작, 선택지를 설명한다.
이미지, 표, 코드, 로그는 주장 바로 아래에 둔다.

## 딥다이브 2 : 두 번째 쟁점

앞 섹션에서 해결되지 않은 질문을 이어서 파고든다.
각 딥다이브는 독립적으로 읽혀도 이해될 만큼 좁게 잡는다.

## 마무리하며

무엇을 알게 됐는지, 어떤 기준이 생겼는지, 다음에는 무엇을 다르게 할지 적는다.
```

기술 트러블슈팅 글은 아래 구조를 우선 사용한다.

```md
## 개요

장애 건수, 에러 메시지, 직접 원인, 최종 대응을 먼저 요약한다.

## 딥다이브 1 : 현상 재현과 조건 분기

요청 흐름, 실패 조건, 로그 패턴을 정리한다.

## 딥다이브 2 : 원인 후보 비교

비슷해 보이는 원인들을 구분한다.

## 딥다이브 3 : 선택한 해결책의 부작용

해결책이 만든 새 문제, race condition, 성능 비용을 적는다.

## 마무리하며

운영 기준, 재발 방지 기준, 앞으로의 설계 원칙을 정리한다.
```

성능 개선이나 프로젝트 회고는 아래 구조를 우선 사용한다.

```md
## 개요

무엇을 만들었고 어떤 결과를 냈는지 말한다.

## 결과부터

성공률, 처리량, 응답시간, 비용 등 핵심 수치를 표로 보여준다.

## 발견한 트레이드오프

속도와 안정성, 비용과 품질, 생산성과 위험처럼 서로 당기는 기준을 설명한다.

## 최적화 과정

### 1단계 : AS-IS → TO-BE

변경 전후 흐름을 그림, 표, 코드로 비교한다.

### 2단계 : 병목 제거

병목이 어디였고 어떤 방식으로 제거했는지 적는다.

## 마무리

이번 경험으로 생긴 판단 기준과 남은 문제를 적는다.
```

생각 정리나 AI/업무 방식 회고는 아래 구조를 우선 사용한다.

```md
## 개요

최근 느낀 변화와 글의 핵심 주장을 먼저 적는다.

## 쟁점 1 : 첫 번째 긴장감

생산성은 올라가지만 역량이 약해질 수 있다처럼, 양쪽이 모두 맞는 문제를 다룬다.

## 쟁점 2 : 두 번째 긴장감

역할 변화, 책임, 검증, 오너십처럼 더 큰 관점으로 확장한다.

## 역할이 바뀐 지점

AS-IS / TO-BE 표로 변화한 역할을 정리한다.

## 앞으로 더 잘하기 위해 필요한 것

다음 행동, 습관, 학습 주제를 적는다.

## 마무리하며

내가 어떤 개발자가 되고 싶은지 한 문장으로 묶는다.
```

학습이나 스터디 글은 아래 구조를 우선 사용한다.

```md
## 개요

무엇을 공부했고 어떤 질문에 답하려 했는지 먼저 적는다.

## 핵심 개념

책이나 강의 내용을 그대로 옮기기보다 이해한 언어로 좁혀 설명한다.

## 직접 적용하거나 실험한 내용

코드, 테스트, 벤치마크처럼 개념을 확인한 과정을 남긴다.

## 새롭게 생긴 판단 기준

학습 전후로 달라진 선택 기준과 적용 범위를 정리한다.

## 마무리하며

다음에 적용하거나 더 확인할 질문을 남긴다.
```

연간 회고는 아래 구조를 우선 사용한다.

```md
## 2026년, 어떤 걸 보여주고 싶었을까

한 해를 관통하는 한 문장과 감정을 먼저 적는다.

## 무엇을 했을까 - 개발 요소

업무 활동과 업무 외 활동을 링크 중심으로 정리한다.

### 좋은 경험이었던 일

대표 성공 경험 하나를 깊게 적는다.

### 아쉬웠던 일

대표 실패나 무산된 경험 하나를 깊게 적는다.

## 무엇을 했을까 - 비개발 요소

생활, 건강, 관계, 습관처럼 개발 밖에서 달라진 것을 적는다.

## 2026년, 터닝 포인트

전년 대비 달라진 태도나 행동을 적는다.

## 2026년, 나 자신을 이해한 해

무엇을 좋아하고 싫어하는지, 어떤 방향을 원하게 됐는지 적는다.

## 2027년의 목표

개발 목표와 비개발 목표를 나눠 적는다.
```

주간 회고는 아래 구조를 우선 사용한다. 한 주에 여러 트랙(운영 이슈, 공부, 프로젝트)이 굴러가므로 주제별 섹션으로 나눈다.

```md
## 이번 주 요약

한 주를 관통하는 한 줄을 먼저 적고, 주제별 결론을 표로 보여준다.

| 주제 | 이번 주 결론 |
| --- | --- |
| JVM 메모리 조사 | 가설 기각, 용의자 3개로 좁힘 |
| AI 공부 | ○○ 완료, △△는 다음 주로 |

## 주제 1 : 주제명 — 결론을 담은 제목

그 주의 메인 주제 하나만 깊게 쓴다.
무슨 일이 있었나, 어떻게 판단하고 움직였나, 이 주제에서 배운 것 순서로 쓴다.

## 주제 2 : 주제명 — 한 줄 결론

서브 주제는 3~5문장으로 짧게 쓴다. 한 일, 판단 하나, 배운 것 하나면 충분하다.

## 마무리하며

회고를 정리하는 섹션이다. 세 가지를 남긴다.

**한 주 총평** — 이번 주가 어떤 주였는지 한두 문장으로 묶는다. 감정 한 줄까지.

**다음에도 쓸 규칙** — 주제와 무관하게 재사용할 행동 규칙만 남긴다.
"이번 주에 안 사실"이 아니라 "다음에 같은 갈림길에서 어떻게 행동할지"를 적는다.

**다음 주에 할 것** — 주제별로 묶어 액션을 남긴다.
```

주간 회고 운영 규칙은 세 가지다.

- 딥다이브는 주 1개만 쓴다. 메인 주제만 판단과 행동까지 깊게 쓰고, 나머지는 결론 위주로 짧게 쓴다. 모든 주제에 같은 프레임을 반복하면 보고서가 된다.
- 섹션 제목에 결론을 담는다. 목차만 훑어도 한 주가 읽히게 한다.
- 한 주제가 글 절반을 넘으면 별도 글로 분리하고, 회고에는 요약과 링크만 남긴다.

짧은 주간 회고는 이 구조만 사용해도 된다.

```md
## 이번 주에 바뀐 것

## 배운 것

## 다음 주에 할 것
```

낙서장을 제외한 글은 위 예시의 모든 섹션을 채울 필요가 없다. `개요`에서 결론을 먼저 말하고, 본문에서는 질문을 하나씩 좁히며, 마지막에는 다음 판단 기준을 남긴다.

## 이미지 추가

이미지는 기본적으로 Astro가 처리하게 둔다. 대부분의 스크린샷, 다이어그램, 그래프 이미지는 `src/assets/images/` 아래에 저장한다.

글마다 폴더를 만들고 이미지를 모은다.

```text
src/assets/images/deployment-checklist/dashboard-before.png
src/assets/images/deployment-checklist/dashboard-after.png
src/assets/images/deployment-checklist/deploy-lead-time.png
```

본문에서는 alias 경로로 참조한다.

```md
![배포 전 대시보드](@/assets/images/deployment-checklist/dashboard-before.png)
```

Astro가 빌드 시 이미지를 최적화하므로, 블로그 본문에 들어가는 이미지는 이 방식을 우선한다.

### public을 쓰는 예외

`public/`은 Astro가 이미지를 최적화하지 않는다. 아래 경우에만 사용한다.

- CSV, JSON, PDF처럼 원본 파일을 그대로 내려받게 할 때
- 외부 도구가 고정 URL을 요구할 때
- Astro 이미지 파이프라인이 처리하지 않아야 하는 파일일 때

## 이미지 규칙

- 파일명은 영어 소문자와 하이픈을 사용한다.
- 민감한 값, 토큰, 사용자 정보, 사내 URL은 가린다.
- 스크린샷은 필요한 영역만 자른다.
- 같은 글의 이미지는 `src/assets/images/{post-slug}/`에 모은다.
- alt text에는 이미지가 보여주는 정보를 적는다.
- 큰 이미지는 올리기 전에 압축한다.

## OG 이미지

기본적으로 OG 이미지는 자동 생성된다. 별도 이미지를 쓰고 싶을 때만 frontmatter에 추가한다.

```md
---
ogImage: ../../assets/images/deployment-checklist/og.png
---
```

권장 크기는 `1200 x 640`이다.

## 표와 수치

성능, 운영, 생산성 개선은 느낌보다 수치로 기록한다.

```md
| Metric | Before | After | Change |
| --- | ---: | ---: | ---: |
| p95 latency | 420ms | 260ms | -38.1% |
| deploy lead time | 18m | 9m | -50.0% |
| alert noise | 42/week | 17/week | -59.5% |
```

수치에는 기준 기간을 함께 적는다.

```md
측정 기간: 2026-06-24 ~ 2026-06-30
대상: production API, business-hour traffic
계산: (after - before) / before * 100
```

## 그래프 반영

그래프는 이미지 하나만 올리지 말고 원본 수치도 같이 남긴다.

```md
![배포 리드타임 변화](@/assets/images/deployment-checklist/deploy-lead-time.png)

| Week | Lead time |
| --- | ---: |
| 2026-W24 | 18m |
| 2026-W25 | 14m |
| 2026-W26 | 11m |
| 2026-W27 | 9m |
```

반복해서 갱신할 그래프라면 같은 폴더에 원본 CSV를 둔다.

```text
src/assets/images/deployment-checklist/deploy-lead-time.png
public/data/deployment-checklist/deploy-lead-time.csv
```

본문에는 그래프 해석을 한 문장으로 붙인다.

```md
배포 리드타임은 4주 동안 18분에서 9분으로 줄었다. 가장 큰 변화는 수동 승인 단계를 제거한 뒤에 나타났다.
```

## 코드와 설정

코드는 언어와 파일명을 함께 적는다.

```ts file="src/content.config.ts"
tags: z.array(z.enum(TOPIC_TAGS)).length(1).default(["Platform"]);
```

변경 전후를 보여줄 때는 diff 표기를 사용한다.

```diff
- tags:
-   - Platform
+ tags:
+   - Weekly Review
```

## 체크리스트

글을 올리기 전에 확인한다.

- 전문 용어를 정확히 쓰고, 같은 개념의 용어를 통일했다.
- 편집 방법을 조사·적용하고, 모든 문장의 군더더기와 어색한 표현을 검토했다.
- 태그가 허용 목록 중 하나인지 확인했다.
- 제목과 description이 본문 내용과 맞는다.
- description은 핵심을 담은 짧은 한 문장이며, 목록 카드의 두 줄 안에서 말줄임표 없이 읽힌다.
- 낙서장 글은 제목에 발행일이 있고, `상황 → (문제) → 원인 → 해결 → 결과` 순서를 따른다.
- 이미지에 민감 정보가 없다.
- 그래프에는 원본 수치나 표가 함께 있다.
- 수치에는 기간, 대상, 계산식이 있다.
- 링크가 상대 경로나 사이트 내부 경로로 올바르게 연결된다.
- 카테고리에서 제외할 글이라면 `hideFromCategories: true`를 설정했다.
- `pnpm astro check`가 통과한다.
