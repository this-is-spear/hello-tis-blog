## 상황

개인 홈 서버에서 [프로젝트 생성부터 Preview 배포까지 연결했다](/posts/mvp-platform-home-server). 이제 이 흐름을 회사에서 사용하려면 무엇을 준비해야 할지 고민하고 있다.

만들고 싶은 것은 개발 경험과 관계없이 회사가 허용한 내부 데이터를 활용해 서비스를 만들고, 동료들과 테스트할 수 있는 사내 개발 플랫폼이다. 민감한 데이터를 사용할 때 필요한 보안 조건을 공통 기능으로 제공해, 환경을 준비하고 같은 검토를 반복하는 부담을 줄이고 싶다.

아직 회사 도입이나 효과를 확인한 단계는 아니다. 이 글에는 사내 적용을 준비하는 순서와 판단 기준을 정리한다.

## 원인

자동 배포가 동작해도 회사 데이터를 사용할 수 있는 것은 아니다. 어떤 사용자와 앱이 어떤 데이터에 접근할 수 있는지, 데이터가 외부 AI 서비스나 로그로 전달되는지도 확인해야 한다. [NIST의 Zero Trust 원칙](https://csrc.nist.gov/pubs/sp/800/207/final)도 네트워크 위치만으로 신뢰를 부여하지 않고, 자원에 접근하기 전에 인증과 인가를 수행하도록 설명한다.

사용자가 계속 활용할 수 있는지도 별도 문제다. 현재 구현의 중심은 생성된 코드의 실행과 배포다. 비개발자가 자연어로 요청하고 코드를 수정하는 경험은 사용할 AI 도구와 온보딩까지 연결해야 한다. 내가 옆에서 매번 대신 처리하면 준비를 기다리던 일이 내 지원을 기다리는 일로 바뀔 수 있다.

## 해결

아래는 아직 실행하지 않은 파일럿 계획이다. 대상 업무와 사용자, 기간은 담당자와 합의할 단계다.

### 첫 사용자와 업무 하나를 정한다

한 팀에서 반복되는 업무 하나부터 살펴본다. 최근 수행한 사례를 보고, 어떤 데이터가 필요했는지와 접근·환경 준비에서 어디를 기다렸는지 확인한다. 실제로 써보고 결과를 판단할 담당자가 있어야 한다.

도구를 만드는 사람, 만들어진 도구를 쓰는 사람, 도입을 결정하는 사람의 요구를 각각 확인한다. 직속 리더와는 내가 맡을 범위, 본업에서 조정할 시간, 중간 점검 시점을 합의한다. 업무 결과와 플랫폼 지원을 누가 책임질지도 정한다.

### 실제 데이터를 쓰기 전에 허용 범위를 합의한다

보안·데이터·인프라 담당자와 데이터 흐름을 함께 보며 다음 조건을 정한다.

- **접근 권한:** 포털, 배포된 앱, 데이터 각각에 접근할 사용자와 앱, 권한 회수 방법.
- **데이터 범위:** 사용할 데이터와 목적, 읽기·쓰기 권한, 보존 기간과 삭제 방법.
- **실행과 통신:** 앱 간 격리, 자원 한도, 허용할 통신 목적지와 자격증명 관리.
- **AI와 기록:** 코드 작성 도구와 앱의 AI 호출에서 전송·저장할 정보, 로그와 접근 기록에 남길 범위.

합의한 표준 범위는 재사용하고, 범위를 벗어나는 요청은 담당자가 검토하도록 설계한다. 민감 데이터 접근 허용 여부는 첫 실제 데이터 사용 전에 확인한다.

### 기존 회사 도구와 같은 업무로 비교한다

회사의 인증·데이터 접근·배포 기반에 필요한 사용 흐름을 추가하는 방법과, 홈 서버의 구현을 회사 환경에 맞추는 방법을 비교한다. 현재 회사 기반은 더 확인해야 한다. 같은 업무를 수행해보며 준비 시간, 사용자 지원, 유지 비용을 비교하고, 실제로 부족한 부분을 개발 범위로 정한다.

### 허용된 데이터로 수정과 테스트를 반복한다

먼저 합성 데이터로 연결과 통제를 점검하고, 접근이 허용된 실제 데이터로 업무의 대표 사례와 예외 사례를 확인한다. 허용된 접근뿐 아니라 미허용 접근과 권한 회수 후 재접근이 차단되는지도 검증한다.

첫 시연 뒤에는 사용자가 두 번째 수정과 배포를 직접 수행하도록 한다. 내가 대신 조작하거나 설명한 시간도 지원 공수로 기록한다. 도입 전후에는 다음을 같은 기준으로 비교한다.

| 확인할 것                 | 남길 기록                                                          |
| ------------------------- | ------------------------------------------------------------------ |
| 첫 내부 테스트까지의 준비 | 요청부터 첫 테스트까지 걸린 시간과 승인·환경 준비·구현·배포별 대기 |
| 사용자 자립과 지원 부담   | 직접 수정·배포한 범위, 막힌 지점, 운영자의 지원 시간               |
| 실제 활용                 | 생성·활성·종료 환경 수를 구분하고, 실제 테스트와 반복 사용 기록    |
| 통제와 업무 품질          | 접근 허용·거부·회수 결과, 업무 사례의 오류와 재작업                |

### 반복 사용이 확인되면 다음 팀으로 넓힌다

첫 사용자가 자기 업무에 활용하고 같은 흐름을 반복할 수 있는지 본 뒤, 비슷한 문제를 가진 다음 팀에 사례와 온보딩 방법을 전달한다. 지원 부담이 효과를 소모하거나 기존 도구가 더 적합하면 범위를 줄이거나 방식을 바꾼다.

운영으로 전환할 서비스는 회사의 기존 보안 승인·운영 절차를 따른다. 공통 승인 파이프라인과 운영 자동화는 운영 전환 사례와 반복 작업이 충분히 쌓인 뒤 별도 범위로 검토한다.

## 결과

현재 정리한 것은 사내 적용의 제안과 검증 순서다. 다음 행동은 직속 리더와 범위를 논의하고, 실제 업무를 보여줄 첫 사용자와 보안·데이터 담당자를 만나는 것이다. 그때 확인한 제약으로 파일럿 범위와 성공·수정·중단 기준을 구체화하려 한다.

이 과정에서 보안 요구를 사용 가능한 개발 환경으로 만들고, 사용자가 반복해서 활용하도록 돕는 경험을 쌓고 싶다. 문제 선정, 대안 판단, 통제 검증, 사용자 지원과 인계에서 내가 맡은 일과 동료의 기여를 함께 남기려 한다. 도입 성과는 실제 사용과 측정 결과가 쌓인 뒤 그 범위 안에서 기록하겠다.
