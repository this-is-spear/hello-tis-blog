## 2장 느려진 서비스, 어디부터 봐야 할까

> 목차: 처리량과 응답 시간 · 서버 성능 개선 기초

### 핵심 내용 정리

사용자가 실행 후 동작하기 까지 걸린 시간으로 성능을 판단할 때, 다양한 시표가 연관돼 있다.
대표적으로 네트워크 속도, 디스크 속도, 메모리 크기, 클라이언트 CPU 속도 등이 해당한다.

지표 중에서 서버 성능과 연관된 중요 지표 2가지를 꼽자면 응답 시간과 처리량이 있다.

### 배운 점 / 인사이트

응답 시간과 처리 시간

- 응답 시간 : API 호출을 처리하는데 걸리는 시간
  - 응답시간은 2 가지로 나눠 측정하기도 한다. 전송량에 따라 TTFB, TTLB 차이가 발생할 수 있고, 데이터 특성과 네트워크 환경을 고려해 TTFB, TTLB 중 적절한 지표를 선택한다.
    - TTFB : 응답 데이터 중 첫 번째 바이트가 도착할 때까지 걸린 시간
    - TTLB : 응답 데이터의 마지막 바이트가 도착할 때까지 걸린 시간
  - [Speed Matters for Google Web Search](https://services.google.com/fh/files/blogs/google_delayexp.pdf) 에 따르면, 100ms 지연 시 검색 횟수 0.2% 감소, 400ms 지연 시 0.6% 감소한다고 한다. 아마존도 100ms 추가 지연될 때마다 매출이 1% 감소한다고 한다.
  - 응답 시간이 증가하면 트래픽과 매출이 줄어든다. 즉, 응답 시간이 길수록 서비스에 부정적인 영향일 미친다.
  - 응답 시간은 대부분 로직 수행, DB 연동, 외부 API 연동으로 이루어진다. 그 중 큰 비중이 있는 곳을 개선하는게 효과가 높을 가능성이 있다.
- 처리량 : 단위 시간당 시스템이 처리하는 작업량
  - 서버가 최대 5개 동시 처리 가능하고 요청당 응답시간 1초라면, TPS는 5다.
  - 최대 TPS를 넘어서는 요청은 대기하게 되며, 사용자 입장에서 응답 시간이 증가하는 문제를 보여준다.
  - 응답 시간 증가는 사용자 이탈로 이어지므로, 동시처리량을 늘리거나 처리 시간을 개선하는 방법중 하나를 선택한다.

병목 지점과 확장

- 병목 지점
  - 시스템 수용 가능한 TPS를 초과하면서 성능이 악화된다.
  - 모니터링 도구로 실행 시간에서 오래 걸리는 작업을 추적해야 한다.
- 확장
  - 수직 확장 : 수직 확장으로 급한 불을 빠르게 끌 수 있다.
  - 수평 확장 : 수평 확장으로 장비 용량 한계 문제를 극복할 수 있다. 이 때, 로드밸런서를 함께 활용한다.
- TPS 높이기 위해 무턱대고 서버를 추가하지 말고 병목 지점을 파악하는게 중요하다. DB 성능 문제로 서버 응답 시간이 지연됐을 때, 서버를 확장해도 문제가 개선되지 않는다.

DB 커넥션 풀

- DB 커넥션 풀 : DB 연결 과정이 오래걸려서 DB 커넥션을 미리 만들어 재활용한다. DB 커넥션 풀 주요 설정 값은 다음과 같다.
- QPS : 1초에 처리할 수 있는 요청은 (1s / 쿼리 실행 시간 _ 커넥션 풀 크기)이다. 즉, 풀 크기가 5이고 쿼리 실행 시간이 0.1s이면, QPS는 50(1s/0.1s _ 5)가 된다.
- 커넥션 풀 크기:
  - 초당 처리해야할 요청수 기준으로 커넥션 풀 크기를 산정하면 된다.
  - 중요한건 DB 상태를 보고 늘려야한다. DB CPU 80%에 육박하는 과정에서 커넥션 풀 크기를 늘리면 DB에 가해지는 부하가 더 커져 쿼리 실행 시간이 급격히 증가한다. (서버 수평 확장도 DB 커넥션 풀 늘리는 행위와 마찬가지니 주의하자.)
- 커넥션 대기 시간:
  - DB 커넥션 얻기 위해서 대기하게 되는데, 대기하는 만큼 응답 시간도 지연된다. 응답 시간이 중요할 경우 가능한 짧게 설정해야 한다.
  - 책에서는 0.5s에서 3s 이내로 지정한다.

캐시

- 서버 캐시
  - DB를 수평 확장, 수직 확장은 처리량을 높이는 데 도움되지만, 응답 시간을 획기적으로 줄이기 어렵다.
  - DB 확장 없이 처리량과 응답 시간을 개선하고 싶다면 캐시 고려하는게 좋다.
  - 캐시 적재하는 메모리 공간은 한정적이기 때문에 캐시 적중률과 삭제 규칙을 정하는게 좋다.
    - 캐시 적중률 : 캐시에 존재하는 건수/캐시에서 조회를 시도한 건수
    - 캐시 삭제 규칙 : LRU, LFU, FIFO (최신 데이터를 자주 조회한다는 가정하에 해당 정책을 활용해도 좋다.)
  - 캐시 사전 적재 : 트래픽이 급증한다면 데이터를 미리 캐싱하는 것도 고려해야한다. 캐시 적중률이 낮아지면 전체 응답 시간이 낮아지고 DB 부하도 증가한다.
  - 캐시는 로컬 캐시와 리모트 캐시가 있다.
    - 로컬 캐시 :
      - 장점 : 캐시 데이터에 빠른 접근 가능
      - 단점 : 저장할 수 있는 용량 적음
    - 리모트 캐시 :
      - 장점 : 저장할 수 있는 용량 큼
      - 단점 : 캐시 데이터에 빠른 접근 느림
  - 캐시 무효화 : 유효하지 않은 데이터를 캐시에서 삭제하는게 중요하다. 유효한지 여부가 민감한 경우 리모드 캐시에 보관해야 한다. 변경에 민감하지 않다면 유효 시간을 설정해 주기적으로 갱신해도 된다.
- 정적 자원
  - 서비스는 정적 자원과 동적 자원으로 구분된다.
  - 콘텐츠 이미지, JS, CSS가 정적 자원이며, 전체 데이터 80% 차지한다.
  - 브라우저 캐시
    - 재활용 가능한 데이터는 브라우저 캐시를 활용해 로컬에서 관리한다.
    - `Cache-Control` , `Expires` 로 캐싱하고 만료시킨다.
  - CDN
    - 결국 많은 요청이 몰린다면 대역폭이 부족해진다. 그래서 CDN 활용한다.
    - 사용자는 CDN이 제공하는 URL로 콘텐츠에 접근한다.
    - **CDN 사용시 파일 크기에 주의해한다. 큰 파일을 올려서 사용자들이 다운로드 받기 시작하면 전송량에 따라 과금되기 때문이다.**

카비지 컬렉터와 메모리 사용

- GC : 메모리 관리 부담을 줄여준다. 그러나 GC 실행시 모든 실행이 멈출 가능성 있다.
  - 메모리 사용량이 높을수록 GC 활발하다.
  - 버퍼와 스트림간 선택이 필요하다. 메모리 사용량을 최소화하려면 스트림으로 해결 가능하다.

응답 데이터 압축

- 데이터 전송 시간은 네트워크 속도, 전송 데이터 크기로 결정된다. 압축하면 전송 데이터 크기를 최소화할 수 있다.
- `Accept-Encoding` , `Content-Encoding` 으로 압축 알고리즘 결정 가능하다.

대기 처리

- 트래픽 폭증시 리소스 증설하거나 수용 가능한 트래픽만 처리하는 방법이 있다.
- 사용자 대기 시스템을 만들어서 처리한다.

### 더 알아볼 것 / 질문

Speed Matters for Google Web Search 에서 인사이트

- 웹서비스 관점에서 인사이트
  1. 노출이 길어질수록 악화된다
  2. 지연을 제거해도 바로 회복되지 않는다.
- 백엔드 관점에서 인사이트
  1. 스트리밍 방식의 응답은 사용성 개선이 된다. 첫 데이터가 빠르고 느림의 차이에 따라 이탈률이 급격하게 개선된다.
  2. 그럼에도 "일단 뭔가 보여줬으니 뒤는 좀 느려도 된다"는 생각을 버리자. 해당 논문은 렌더링 시점마다 지연을 넣었으며 첫 데이터를 렌더링 완료가 늦어도 이탈로 이어졌다. 처음 데이터를 빨리 전달하는것만 중요하지 않다.
  3. 지연 회복은 더디다. 문제가 발생하기 전 CI에서 성능 회귀 테스트를 하는게 사후 대응보다 훨씬 싸다.

마이크로서비스 아키텍처 구축 책에서 나온 (13.4) 캐시 내용 복기

- 캐시 사용 목적
  - 성능을 위해 : 캐시를 활용해 네트워크 호출 비용(네트워크 홉 + 요청 생성)을 줄이기 위해 도움된다.
  - 확장성을 위해 : 확장성을 위한 캐싱은 원본이 경합 지점이 되는 상황에서 유용하다. DB 읽기 복제본 처럼 읽기 경합을 피하는 경우다.
  - 견고성을 위해 : 원본을 가용하지 않는 경우에도 작동하므로 견고성이 향상된다. 이런 경우 캐시 무효와 메커니즘을 구성해 원본과 캐시 데이터 간 동기화가 잘 돼야 한다.
- 캐싱 위치 결정 방법
  - 클라이언트 측 캐싱
    - 설명 : 원본의 범위가 포함되지 않는 곳에 캐싱된다.
    - 목적 : 지연 시간 개선 + 견고성
    - 단점 : 무효화 메커니즘 선택 범위가 제한되기 쉽다, 클라이언트 측 캐싱이 늘어나면서 클라이언트 간 불일치 발생 가능성이 높아진다.
    - 대안
      - 클라이언트 간 캐시 데이터 동기화 방식으로 notification 기반 무효화 기술을 사용할 수 있다. (그러나 완전한 해소는 불가하다.)
      - 클라이언트 간 캐시 데이터 동기화 방식으로 캐싱 외부화로 함께 사용하는 방법이다. (누가 소유하는지 불분명해진다.)
  - 서버 측 캐싱
    - 설명 : 원본의 범위가 포함된 곳에 캐싱된다.
    - 목적 : 쿼리 비용 감소
    - 장점 : 정교한 캐시 무효화 메커니즘 구현이 쉽다.
    - 단점 : RTT가 존재하기 때문에 지연 시간 개선은 어렵다.
  - 요청 캐싱
    - 설명 : 원본 요청에 대한 응답을 캐싱한다.
    - 목적 : 응답 시간 개선
    - 장점 : 속도 최적화에서 가장 효과적이다.
    - 단점 : 캐싱 대상이 한정적이어서 캐싱 효과가 크지 않다.
- 캐시 무효화
  - TTL
    - 설명 : 캐시는 특정 기간 동안만 유효한 것으로 간주한다.
    - 장점 : 구현이 간단하다.
    - 단점 : 캐시가 만료되기 전까지는 캐시 데이터가 최신 상태로 유지되지 않는다.
  - 조건부 GET
    - 설명 : `HTTP` 응답에 `Cache-Control`, `Expires` 헤더 사용하거나 `ETag`를 사용해 요청 기반 캐싱이 가능하다.
    - 장점 : GET 요청할 때, 추가 헤더를 지정해 특정 기준이 충족되는 경우만 서빙할 수 있다.(유저 정보 헤더 추가해서 가능하다.) , 불필요한 자원 재생성 비용을 줄일 수 있다.
    - 단점 : 네트워크 RTT 횟수 줄이는 데 도움되지 않는다.
  - 알림 기반
    - 설명 : 이벤트를 사용해 구독자가 로컬 캐시 항목을 무효화할지 여부를 알 수 있도록 도와준다.
    - 장점 : 캐시가 오래된 데이터 제공 가능성을 줄여준다.
    - 단점 : 구현이 복잡하다. (데이터 변경시 알림에 데이터 변경 정보를 전달 방식 고려하기 어렵다.) , 알림 메커니즘 작동 여부를 검증이 어렵다 , **민감한 데이터가 광범위하게 노출될 수 있다.**
  - `write-through`
    - 설명 : 원본과 캐시가 동시에 업데이트된다.
    - 장점 : 캐시가 항상 최신 상태로 유지된다.
    - 단점 : 연속 쓰기가 발생하면 비효율적인가..? , 서버 측 캐시가 일반적으로 덜 유용할 수 있다...?
  - `write-behind`
    - 설명 : 캐시가 업데이트 되고 이후에 원본이 업데이트 된다. 캐시를 버퍼로 활용한다.
    - 장점 : 읽기를 빠르게 처리할 수 있다.
    - 단점 : 데이터 손실 가능성이 존재한다. 캐시 내구성이 떨어지면 기록 손실이 발생한다.
- 캐싱에는 황금 법칙이 존재한다.
  - 데이터 신선도(freshness)와 지연 시간에 대한 균형 맞추기 어렵다. 캐시 데이터가 많을 수록 데이터가 오래될 수 있으며 클라이언트가 최종적으로 보게되는 데이터가 최신인지 판단이 어렵다.
  - TTL이나 알림 방식을 활용해도 오래된 데이터를 캐싱할 수 있게 된다. 이 때, 캐싱은 주로 성능 최적화를 위한 것으로 고려한다. 또한 데이터 신선도를 더 쉽게 추론할 수 있도록 가능한 적은 위치에 캐시를 저장해야 한다.
  - 캐시 중독 : 캐싱 효과는 매우 강력하지만 원본에서 목적지까지 캐싱되는 데이터 전체 경로를 이해해야 캐싱 복잡성과 발생하게 될 문제를 인식할 수 있다.

## **3장 성능을 좌우하는 DB 설계와 쿼리**

> 목차: 성능에 핵심인 DB · 조회 트래픽을 고려한 인덱스 설계 · 몇 가지 조회 성능 개선 방법 · 알아두면 좋을 몇 가지 주의 사항 · 실패와 트랜잭션 고려하기

### **핵심 내용 정리**

### **배운 점 / 인사이트**

- DB 자체가 문제인 상황보다 잘못 사용해서 발생하는 문제가 더 많다. DB를 전문가 수준으로 이해하면 이상적이지만 서버 개발자 입장에서 조금만 신경 써도 DB 성능 문제를 충분히 줄이거나 없앨 수 있다.

몇가지 조회 성능 개선 방법

- 조회 트래픽을 고려한 인덱스 설계
  - 데이터가 많은 경우에 풀스캔이 동시에 발생하면 DB의 CPU 사용률이 100%에 도달하면서 제 기능을 하지 못한다.
  - 풀 스캔이 발생하지 않으려면 조회 패턴 기준으로 인덱스를 설계해야 한다.
- 인덱스
  - 복합 인덱스, 추가 컬럼을 인덱스에 포함시킬지 여부 결정하기 : 쿼리 실행 빈도와 실행 시간을 검토해서 포함 여부를 결정할 수 있다.
  - 커버링 인덱스 활용하기 : 인덱스에 포함된 값만으로 쿼리 결과를 구할 수 있다.
  - 선택도(카디널리티)를 고려한 인덱스 컬럼 선택하기
  - 인덱스는 필요한 만큼만 만들기 : 인덱스는 조회가 빠르지만 CUD 실행 시간이 증가할 수 있고, 메모리와 디스크에 영향을 준다.
- 몇 가지 조회 성능 개선 방법
  - 사전 집계하기 : count, sum 집계 쿼리는 조회 시점에 실행하면 시간 복잡도 N^2 와 같은 성능 문제가 발생할 수 있다. 미리 집계해서 별도로 저장하면 된다.
    - 그에 따른 동시성 문제가 따라올 수 있다. 증가/감소 쿼리를 사용할 때, DBMS가 지정한 트랜잭션 격리 수준에서 원자적으로 처리하는지 검증 필요하다.
  - 페이지 기준 목록 조회 대신 ID 기준 목록 조회 방식 사용하기 : 순서를 확인하기 위해서 처음부터 집계해야하기 때문에 데이터를 카운팅하는 만큼 실행 시간이 증가한다. 따라서 마지막 조회 ID를 활용해서 원하는 수만큼 데이터를 조회하면 데이터 카운팅해서 발생하는 지연 시간을 개선할 수 있다.
  - 조회 범위를 시간 기준으로 제한하기 : 조회 범위를 최소화하는 것도 방법이다. ID 기준 목록 조회 방식은 쿼리가 복잡해지는데, 해당 방식은 어떤 조건이 포함되는지 명시적이어서 좋다.
  - 전체 개수 세지 않기 : 데이터가 많으면 count 도 오래 걸린다.
  - 오대된 데이터 삭제 및 분리 보관하기 : 사용하지 않는 과거 데이터를 삭제 및 보관해 일관된 서비스 품질을 제공할 수 있다.
    - DELETE 쿼리를 사용해도 디스크 용량은 줄지 않는다. 단편화가 심해지면 디스크 I/O 증가하면서 쿼리 성능 저하될 가능성도 있다.
    - 단편화로 인한 성능 저하를 해결하기 위해 최적화 작업(데이터 재배치)을 진행해 물리 디스크 사용량을 줄여야 한다.
  - DB 장비 확장하기 : DB 부하가 증가하면 수직 확장과 수평 확장을 고려할 수 있다.
    - 수직 확장으로 일관된 서비스 품질 유지하고, 개선 방향을 모색한다.
    - 수평 확장으로 master-replica 를 고려해서 조회 기능에 대한 트래픽 개선해볼 수 있다.
  - 별도 캐시 서버 구성하기 : 비용 문제로 DB 확장이 어려울 때, 캐시 서버를 도입해 적은 비용으로 조회 처리량을 높일 수 있다. 캐시 도입시 코드 수정이 발생해서 코드 수정 비용까지 고려해야한다.

알아두면 좋을 몇 가지 주의 사항

- 쿼리 타임아웃 : 쿼리 실행 시간을 제한해 동시 요청 수로 인한 병목 발생 문제를 해결할 수 있다.
- 상태 변경 기능은 복제 DB에서 조회하지 않기 : 조회라고 무조건 복제DB를 조회하는건 아니다. 주DB와 복제DB간 순간적인 불일치가 발생하기 때문에 상태 확인 후 변경은 주DB에서 전부 이뤄져야 한다.
- 배치 쿼리 실행 시간 증가 : 데이터 증가에 따라 배치 실행 시간이 증가하기도 한다. 이 때, 커버링 인덱스를 활용하거나 데이터를 일정 크기로 나눠 처리한다.
- 타입이 다른 컬럼 조인 주의 : 타입이 다르면 인덱스 활용이 안될 수 있다. 타입 변환은 각 행마다 발생해서 비교하므로 인덱스 활용되지 않는다.
- 테이블 변경은 신중하게 : 테이블 수정으로 서비스 중단이 발생할 수 있다. mysql은 테이블 변경시 새테이블 생성 후 데이터를 복사해서 전달한다. 그 과정에서 CUD는 중단된다.
- DB 최대 연결 개수 : DB 연결 제한이 많아지면 DB 동시 처리량이 증가해 CPU 상승으로 이어진다. DB 연결 제한이 적어지면 서비스 수평 확장시 DB 연결이 부족해질 수 있다.

실패와 트랜잭션 고려하기

- 트랜잭션 경계 정확하게 설정해야 데이터 사이 일관성을 유지한다.
- 일부 기능은 트랜잭션 외에서 실행돼야 한다.

### **실무에 적용할 점**

- 복합 인덱스 설정 기준
  - 왼쪽 접두사 규칙 : 복합 인덱스는 선두 컬럼부터 순서대로만 탄다. `(a, b, c)` 인덱스는 `a`, `a+b`, `a+b+c` 조건에는 쓰이지만 `b`나 `c`만으로는 못 쓴다. 그래서 컬럼 순서가 인덱스 설계의 전부다.
  - 컬럼 순서 정하는 기준
    - equality(=) 조건 컬럼을 앞에, range(부등호·BETWEEN·IN 일부) 조건 컬럼을 뒤에 둔다. range 조건 컬럼 뒤의 컬럼은 인덱스를 타도 걸러내는 용도로밖에 못 쓴다.
    - equality 컬럼끼리는 선택도(카디널리티) 높은 컬럼을 앞에 두는 게 기본이다. 단, 자주 쓰는 쿼리 패턴이 우선이다. 선택도가 낮아도 모든 쿼리에 들어가는 컬럼이면 앞에 둘 수 있다.
  - 중복 인덱스 정리 : `(a, b)` 인덱스가 있으면 `(a)` 단독 인덱스는 왼쪽 접두사로 커버되므로 불필요하다. 인덱스 추가 전에 기존 인덱스의 접두사로 해결되는지 먼저 본다.
  - 커버링까지 고려 : 자주 실행되는 쿼리라면 SELECT 컬럼까지 인덱스에 포함시켜 테이블 접근 자체를 없앨지 검토한다. 대신 인덱스가 커지고 CUD 비용이 늘어나니 3장 본문의 "쿼리 실행 빈도와 실행 시간" 기준으로 판단한다.
  - mongodb 에서는 esr 로 설정하라고 함 (equality → sort → range) 그래야 filesort 가 안난다고 함. (MySQL도 같은 원리가 통한다. equality 다음에 sort 컬럼을 두면 인덱스 순서가 곧 정렬 순서가 된다.)
    - filesort란? : 인덱스 순서만으로 정렬된 결과를 얻지 못할 때, DB가 조회 결과를 정렬 버퍼에 올려 별도로 정렬하는 작업이다.
      - 이름과 달리 항상 디스크에 파일을 만드는 건 아니다. 정렬 버퍼(MySQL `sort_buffer_size`)를 넘으면 디스크 임시 파일까지 쓰면서 느려진다.
      - 인덱스가 (equality 컬럼) → (sort 컬럼) 순서로 잡혀 있으면 인덱스 자체가 이미 정렬돼 있어서 filesort 없이 순서대로 읽기만 하면 된다. range 컬럼이 sort 컬럼보다 앞에 오면 range 조건을 통과한 행들의 정렬이 깨져서 filesort가 난다. ESR 순서를 지키라는 이유가 이것이다.
      - 발생 여부는 실행 계획으로 확인한다. MySQL은 `EXPLAIN`의 Extra에 `Using filesort`, MongoDB는 `explain()`의 `SORT` 스테이지로 드러난다.

### **더 알아볼 것 / 질문**

- 파티셔닝과 샤딩
  - 선택하는 기준
    - 파티셔닝 : 한 DB 인스턴스 안에서 테이블을 물리적으로 나눈다. (MySQL `PARTITION BY RANGE` 등)
      - 조회 범위를 파티션 단위로 좁히고(파티션 프루닝), 오래된 데이터를 파티션 DROP으로 즉시 정리할 수 있다.
      - 장비는 여전히 한 대라서 CPU·메모리·디스크 한계는 못 넘는다.
    - 샤딩 : 여러 DB 인스턴스에 데이터를 나눈다.
      - 쓰기 처리량이나 저장 용량이 단일 장비 한계를 넘을 때 쓴다.
      - 대신 샤드를 넘는 조인·트랜잭션이 안 되고, 샤드 키 설계·라우팅·리밸런싱 비용이 크다.
    - 판단 기준 : 문제가 "조회 범위와 데이터 정리"면 파티셔닝, "단일 장비의 쓰기 TPS·용량 한계"면 샤딩이다.
    - 적용 순서 : 인덱스·쿼리 개선 → 파티셔닝 → 읽기 복제본 → 샤딩. 샤딩은 운영 복잡도가 가장 크니 마지막 수단으로 미룬다.
- 오래된 데이터 삭제 및 분리 보관하는 방법 정리
  - 압축해서 보관하기
    - 아카이브 테이블로 `INSERT ... SELECT` 후 원본을 지우거나, S3 같은 객체 저장소에 Parquet·CSV+gzip 형태로 내려서 보관한다.
    - MySQL 압축 테이블로 DB 안에 보관하는 방법도 있다. 아카이브 테이블을 압축 포맷으로 만들면 SQL로 바로 조회할 수 있는 상태를 유지하면서 디스크를 줄인다.
      - `ROW_FORMAT=COMPRESSED` : 테이블 생성 시 `KEY_BLOCK_SIZE`(16KB 페이지 기준 8·4·2·1KB)로 압축 정도를 지정한다. 값이 작을수록 압축률이 높아지지만 읽기·쓰기 때 압축/해제 CPU 비용이 커진다.

        ```sql
        -- 생성 시 압축 지정
        CREATE TABLE order_archive (
            id BIGINT PRIMARY KEY,
            payload JSON,
            created_at DATETIME
        ) ENGINE=InnoDB ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=4;

        -- 기존 테이블을 압축 포맷으로 전환
        ALTER TABLE order_archive ROW_FORMAT=COMPRESSED, KEY_BLOCK_SIZE=4;
        ```

      - `ROW_FORMAT=COMPRESSED` 주의사항
        - `innodb_file_per_table=ON`(기본값)이어야 적용된다.
        - 전환 ALTER는 테이블 재생성이다. 테이블 크기만큼 디스크 여유가 필요하고 복제 지연이 생긴다.
        - `KEY_BLOCK_SIZE`를 너무 작게 잡으면 압축 실패 → 페이지 분할 → 재압축이 반복되면서 오히려 느려진다. 실제 데이터 샘플로 압축률을 재보고 정한다.
        - 버퍼 풀에 압축 페이지와 해제된 페이지가 이중으로 올라가 메모리 효율이 떨어질 수 있다. 쓰기가 계속 들어오는 테이블에는 안 맞고, 읽기 위주 아카이브에 쓴다.
      - 페이지 압축 : `COMPRESSION='zlib'`(또는 lz4)로 페이지 단위 투명 압축을 건다. 펀치 홀을 지원하는 파일시스템이 필요하다.

        ```sql
        -- 생성 시 페이지 압축 지정
        CREATE TABLE order_archive (
            id BIGINT PRIMARY KEY,
            payload JSON,
            created_at DATETIME
        ) ENGINE=InnoDB COMPRESSION='zlib';

        -- 기존 테이블에 페이지 압축 설정 (기존 페이지는 그대로다)
        ALTER TABLE order_archive COMPRESSION='zlib';
        OPTIMIZE TABLE order_archive; -- 재작성해야 기존 데이터에 압축이 적용된다
        ```

      - 페이지 압축 주의사항
        - `ALTER ... COMPRESSION=...`은 설정만 바꾼다. 기존 페이지는 그대로라서 `OPTIMIZE TABLE`로 재작성해야 실제로 줄어든다.
        - 펀치 홀(hole punching)을 지원하는 파일시스템·커널(ext4, XFS 등)이 필요하다. 지원하지 않으면 경고만 나오고 압축되지 않는다.
        - 파일 크기(`ls`)는 그대로이고 실제 디스크 점유(`du`)만 줄어든다. 용량 모니터링은 du 기준으로 봐야 한다.
        - 백업·스냅샷 도구가 sparse 파일을 지원하는지 확인한다. 지원하지 않으면 백업본에서 압축 효과가 사라진다.
      - 자주 조회하지 않는 아카이브 용도라 압축/해제 비용 부담이 적고, 텍스트 위주 데이터면 절반 이하로 줄어드는 경우가 많다.

    - RANGE 파티셔닝이 돼 있으면 파티션 DROP이 가장 싸다. DELETE와 달리 디스크가 즉시 반환되고 단편화도 없다.

  - 추출 후 DELETE 주의사항
    - 이관과 삭제를 한 트랜잭션으로 묶지 않는다. 대량 이관+삭제가 한 트랜잭션이면 undo 로그가 비대해지고 실패 시 롤백도 그만큼 오래 걸린다. 배치 단위로 이관 → 건수 검증 → 삭제 순서로 반복한다.
    - 이관 확인 전에 지우지 않는다. 아카이브 쪽 커밋과 건수 확인이 끝난 범위만 삭제 대상으로 삼는다.
    - LIMIT이나 PK 범위로 나눠서 지운다. 한 번에 지우면 undo 로그가 커지고, row 기반 binlog에는 삭제된 행이 전부 기록돼 복제 지연이 생긴다. 배치 사이에 잠깐 쉬면서 복제 지연을 모니터링한다.
    - 삭제 조건이 인덱스를 타는지 확인한다. 인덱스가 없으면 풀스캔에 잠금 범위도 넓어져서(gap lock 포함) 운영 쿼리가 대기한다.
    - 오래 걸리는 삭제 트랜잭션 자체가 문제를 만든다. 트랜잭션이 열려 있는 동안 undo purge가 밀려서(history list length 증가) 다른 쿼리까지 느려진다.
    - 외래 키의 `ON DELETE CASCADE`와 트리거를 확인한다. 의도하지 않은 테이블까지 연쇄 삭제될 수 있다.
    - 지워도 디스크는 반환되지 않는다. 공간 회수까지 필요하면 위의 최적화 작업(`OPTIMIZE TABLE`)을 별도로 계획한다.
    - 트래픽 적은 시간대에 돌리고, 처음에는 작은 배치로 시작해 복제 지연·잠금 대기를 보면서 배치 크기를 조절한다.
  - 최적화 방식 → 실제로 하게된다면 어떻게?
    - MySQL InnoDB 기준 `OPTIMIZE TABLE`(내부적으로 테이블 재생성)로 단편화를 해소하고 디스크를 반환한다.

      ```sql
      OPTIMIZE TABLE order_history;

      -- InnoDB는 내부적으로 아래와 동일하게 동작한다 (재생성 + 통계 갱신)
      ALTER TABLE order_history ENGINE=InnoDB;
      ANALYZE TABLE order_history;
      ```

    - `OPTIMIZE TABLE` 주의사항
      - InnoDB에서는 "Table does not support optimize, doing recreate + analyze instead" 메시지가 나온다. 에러가 아니라 재생성으로 대신 처리했다는 정상 동작이다.
      - 온라인 DDL이라도 사실상 테이블 전체를 복사한다. 테이블 크기만큼 디스크 여유가 필요하고 복제 지연이 생기니 트래픽 적은 시간대에 돌린다.
      - 시작과 끝에 메타데이터 잠금(MDL)을 잡는다. 오래 실행 중인 쿼리나 안 닫힌 트랜잭션이 있으면 잠금을 못 잡고, 그 뒤로 들어오는 쿼리까지 전부 대기한다. 실행 전에 긴 쿼리가 없는지 확인한다.
      - 도중에 중단하면 임시 테이블 정리와 롤백 비용이 든다. 복사 진행률은 `performance_schema`의 stage 이벤트로 확인할 수 있다.
    - 서비스 중단이 부담되면 gh-ost, pt-online-schema-change 같은 도구로 복사 속도를 조절하며 진행한다.
    - 주기 실행이 필요하면 MySQL 이벤트 스케줄러로 DB 수준에서 돌릴 수 있다.

      ```sql
      -- 이벤트 스케줄러 활성화 (기본 ON, RDS는 파라미터 그룹에서 설정)
      SET GLOBAL event_scheduler = ON;

      -- 매월 1회 새벽에 실행하는 이벤트
      CREATE EVENT optimize_order_history
      ON SCHEDULE EVERY 1 MONTH
      STARTS '2026-09-01 03:00:00'
      DO OPTIMIZE TABLE order_history;
      ```

    - 이벤트 스케줄러 주의사항 (실무에서는 외부 배치를 권하는 이유)
      - 실패해도 알림이 없다. 결과는 `information_schema.EVENTS`나 에러 로그를 직접 확인해야 한다. 외부 배치(cron)는 실패 알림·재시도·로그를 붙일 수 있다.
      - 실행 전 안전 확인을 못 한다. 긴 쿼리와 겹치면 메타데이터 잠금 대기가 쌓이는데, 이벤트는 무조건 정시에 돈다. 외부 스크립트는 "긴 쿼리 없는지 확인 → 실행" 같은 사전 점검을 넣을 수 있다.
      - `OPTIMIZE TABLE`은 binlog로 복제돼 복제본도 같은 재생성을 수행한다. 이벤트 자체는 소스에서만 실행되고 복제본에서는 `SLAVESIDE_DISABLED`로 비활성 상태다.
      - 전제 : InnoDB는 주기적인 OPTIMIZE가 필요 없는 경우가 대부분이다. 대량 삭제·아카이빙 직후 단편화가 실제로 생겼을 때(`information_schema.TABLES`의 `DATA_FREE`로 확인) 일회성으로 돌리는 게 정석이고, 정기 실행은 매번 테이블 전체 복사 비용을 내는 낭비가 되기 쉽다.

- 트랜잭션
  - 트랜잭션 경계 정확하게 설정하는 방법
    - 함께 성공하거나 함께 실패해야 하는 변경만 한 트랜잭션에 묶는다. 그 외 작업이 섞이면 커넥션 점유 시간만 길어진다.
    - 외부 API 호출, 파일 I/O, 알림 발송은 트랜잭션 밖으로 뺀다. 외부 응답이 느리면 그 시간만큼 DB 커넥션과 잠금을 쥐고 있게 되고, 외부 실패가 DB 롤백까지 끌고 간다.
    - 스프링이라면 `@Transactional` 범위를 좁게 잡고, 조회 → 긴 처리 → 저장 흐름이면 `TransactionTemplate`으로 저장 구간만 트랜잭션으로 감싼다.
  - 일부 기능은 트랜잭션 외에서 실행하는 방법
    - 커밋 이후 실행 : `@TransactionalEventListener(phase = AFTER_COMMIT)` 또는 `TransactionSynchronization#afterCommit`으로 커밋이 확정된 뒤에 알림·캐시 갱신을 실행한다.
    - 커밋됐는데 후속 작업이 실패하면 유실된다. 유실이 허용되지 않으면 같은 트랜잭션에서 이벤트를 테이블에 저장하고 별도 프로세스가 발행하는 아웃박스 패턴을 쓴다. (5장 트랜잭션 아웃박스 패턴과 연결)
  - `@Transactional` 기대 동작
    - 트랜잭션에서 회피되는 동작 (붙였는데 트랜잭션이 안 걸리는 경우)
      - self-invocation : 같은 빈 안에서 `this.method()`로 호출하면 프록시를 거치지 않아 트랜잭션이 적용되지 않는다. 별도 빈으로 분리하거나 트랜잭션 경계 메서드를 바깥으로 뺀다.
      - public이 아닌 메서드 : 프록시 기반 AOP는 public 메서드에만 적용된다. protected·private에 붙이면 조용히 무시된다.
      - checked exception : 기본 롤백 규칙은 `RuntimeException`과 `Error`뿐이다. checked exception은 롤백되지 않고 커밋된다. 필요하면 `rollbackFor`를 명시한다.
      - 예외를 catch로 삼킨 경우 : 메서드 안에서 예외를 잡고 정상 리턴하면 롤백 트리거가 없으니 그대로 커밋된다.
      - 다른 스레드 : `@Async`, `CompletableFuture` 등 새 스레드에서 실행되는 코드에는 트랜잭션이 전파되지 않는다. 트랜잭션은 스레드 로컬에 바인딩된다.
    - 주의해야하는 동작 (걸리긴 하는데 의도와 다르게 움직이는 경우)
      - 트랜잭션 범위 = 커넥션 점유 시간이다. 메서드 안에 외부 API 호출·긴 연산이 있으면 그 시간 내내 커넥션과 잠금을 쥔다. (위 "트랜잭션 경계 설정"과 연결)
      - `REQUIRES_NEW` : 바깥 트랜잭션을 멈춰두고 커넥션을 하나 더 잡는다. 요청당 커넥션 2개를 점유하니 풀이 작으면 서로 커넥션을 기다리는 교착으로 풀 고갈이 날 수 있다.
      - rollback-only 전파 : 안쪽 트랜잭션(REQUIRED로 참여)에서 `RuntimeException`이 나면 바깥에서 catch해도 트랜잭션은 이미 rollback-only로 마킹돼 커밋 시점에 `UnexpectedRollbackException`이 난다.
      - `readOnly=true`에서 쓰기 : Hibernate는 flush를 건너뛰어 변경이 조용히 유실되고, 드라이버가 서버까지 READ ONLY를 전파하면 쓰기 문장이 에러가 난다. (아래 Read-only 정리와 연결)
      - 격리 수준·타임아웃은 트랜잭션을 새로 시작할 때만 적용된다. 기존 트랜잭션에 참여(REQUIRED)하면 지정해도 무시된다.
  - 쿼리 간단 조회시 `@Transactional`을 굳이 붙여야 할까?
    - 상황 : insert ignore 쿼리 호출시 `@Transactional`을 붙인 이유에 대한 질문을 받음
    - MySQL InnoDB는 autocommit이 기본이다. 문장 하나가 그 자체로 하나의 트랜잭션이고, 에러가 없으면 즉시 커밋된다. InnoDB에서 트랜잭션 없이 실행되는 SQL은 존재하지 않는다. autocommit이 켜진 상태에서는 각 문장이 자체적으로 하나의 트랜잭션을 이루고, 에러가 없으면 그 직후 자동 커밋된다.
    - 단, 예외가 있다. JPA로 `executeUpdate()`를 실행하면 (Spring Data JPA의 `@Modifying` 네이티브 쿼리 포함) 트랜잭션이 없을 때 `TransactionRequiredException`이 발생한다.
    - 즉 JdbcTemplate이나 MyBatis면 없어도 동작하고, JPA `@Modifying`이면 필수다. 질문받은 코드가 어느 쪽인지가 답의 핵심이다.
  - Read-only에 대한 정리
    - 기본 동작
      - `Connection.setReadOnly(true)` 를 켜면 "이 커넥션에서는 읽기만 할 거니 최적화해도 된다"고 드라이버에게 주는 힌트일 뿐이다.
      - 즉, Hibernate Session의 flush mode를 미리 `FlushMode.MANUAL`로 세팅하는 일이다. 즉, 읽기 트랜잭션에서 dirty checking/flush 비용을 건너뛰는 용도다.
    - 옵트인 (설정에 따라)
      - `DataSourceTransactionManager.setEnforceReadOnly(true)`를 켜면 힌트를 넘어 트랜잭션 시작 직후 커넥션에 `SET TRANSACTION READ ONLY` 문을 실행한다.
    - 결론은 드라이버에 따라 Read-only 동작 방식이 다르다.
      - MySQL인 경우, `readOnlyPropagatesToServer=true`로 설정돼있으며, 트랜잭션 접근 모드를 READ ONLY로 설정하는 문장을 암묵적으로 실행한다. 그리고 InnoDB가 실제 최적화를 한다. read-only로 알려진 트랜잭션에는 트랜잭션 ID(TRX_ID) 할당을 생략한다.
      - 참고로 InnoDB가 read-only로 인식하는 경우는 세 가지
        - `START TRANSACTION READ ONLY` 시작
        - autocommit 상태의 non-locking `SELECT` 단문
        - `READ ONLY` 선언 없이 시작했더라도 쓰기 전까지 read-only 상태 유지

- 통신 과정은 연결-요청-응답-종료 4단계를 거친다.

  - 요청 후 응답 받는 대기 시간을 조절하기 위해 read timeout을 설정한다.
- read timeout은 상황별로 조절해야 한다. 외부 연동 서비스 가이드라인에 맞게 read timeout을 설정한다.

- OkHttp는 읽기 타임아웃과 별개로 call timeout을 설정할 수 있다. call timeout은 요청 시작부터 응답까지 전체 시간 기준으로 설정된다.

재시도

- 네트워크 통신 과정에서 간헐적으로 연결 실패하거나 일시적으로 응답이 느려지는 경우 재시도한다.
- 포인트 내역 조회는 재시도하면 되지만 포인트 차감은 상황에 따라 재시도 여부가 달라진다.
- 재시도 가능 조건
  - 단순 조회 기능
  - 연결 타임아웃 (<-> 읽기 타임아웃은 이미 요청 처리 중이라 상황에 따라 달리한다.)
  - 멱등성을 가진 변경 기능
- 재시도 횟수와 간격
  - 재시도 횟수는 1~2번이 적당하다. 3번 이상은 간헐적인 오류로 보기 어렵다.
  - 재시도 간격은 3초 간격이 적당하다. 일시적인 네트워크 문제가 해소될 가능성이 높다.
- retry storm 안티 패턴
  - 재시도로 성공 가능성을 높일 수 있지만, 연동 서비스에 더 큰 부하로 이어질 수 있다.
  - 연동 서비스는 재시도 횟수만큼 부하가 이어진다. 또한 성능이 느려진 상태라서 상황이 더 악화될 수 있다.

동시 요청 제한

- 연동 서비스의 최대 처리량을 초과하는 요청을 보내면 안된다.
- 일부 요청만 허용하고 남은 요청은 거부해서 응답 시간을 완화하는 것도 방법이다. (벌크헤드 패턴)

서킷 브레이커

- 외부 연동 서비스가 정상 아닐 때, 외부 연동 서비스에 요청을 보내는 것보다 바로 에러 응답(fail-fast)하는 게 좋다.
- 서킷 브레이커는 `Closed`-`Open`-`Half Open` 상태로 과도한 오류가 발생하면 연동을 중지시키고 빠르게 에러를 응답해 장애 전파를 방지한다.
  - 임계치를 넘으면 `Open` 상태로 전환한다. → 정해진 시간이 지나면 `Half Open` 상태로 전환한다. → `Half Open` 기간 동안 연동에 성공하면 `Closed`로 복귀한다.
- 서킷 브레이커 임계치
  - 시간 기준 오류 발생 비율
    - ex: 10초 동안 오류 비율 50% 초과
  - 개수 기준 오류 발생 비율
    - ex: 100개 요청 중 오류 비율 50% 초과
- 외부 연동 서비스가 정상 아닐 때, 외부 연동 서비스에 요청을 보내는 것보다 바로 에러 응답(fail-fast)하는게 좋다.
- 서킷 브레이커는 `Closed`-`Open`-`Half Open` 상태로 과도한 오류가 발생하면 연동을 중지시키고 빠르게 에러를 응답해 장애 전파를 방지한다.
  - 임계치를 넘으면 `Open` 상태로 전환한다. -> 정해진 시간이 지나면 `Half Open` 상태로 전환한다. -> `Half Open` 기간 동안 연동에 성공하면 `Closed`로 복귀한다.
- 서킷 브레이크 임계치
  - 시간 기준 오류 발생 비율
    - ex : 10초 동안 요류 비율 50% 초과
  - 개수 기준 오류 발생 비율
    - ex : 100개 요청 중 오류 비율 50% 초과

DB와 외부 연동

- 외부 연동과 트랜잭션 처리
  - 외부 연동에 실패했을 때 트랜잭션 롤백
    - 트랜잭션 범위 내에서 외부 연동 실패한 경우, 트랜잭션 롤백이 가능하다.
    - 변경된 데이터가 DB에 반영되지 않으므로 큰 문제 없다.
  - 외부 연동은 성공했는데, DB 연동에 실패해서 트랜잭션 롤백
    - read timeout 발생한 경우, 외부 연동 성공 여부 확인이 어렵다.
    - 트랜잭션 롤백했는데, 외부 서비스가 실제로 성공했을 경우, 2가지 방법 중 하나를 검토해야 한다.
      1. 일정 주기로 두 시스템의 데이터가 일치하는지 확인하고 보정하는 방법. 불일치 건 발견하면 수동 보정
      2. 성공-확인 API를 호출하는 방식. 일정 시간 후 이전 호출이 실제로 성공했는지 확인하는 API 호출. 성공 여부에 따라 롤백 진행.
    - 두 시스템 간 데이터 일관성이 중요한 기능이라면 정기적으로 데이터 일치를 확인하는 프로세스를 갖추는 것이 바람직하다.
    - 취소 API가 없는 경우, 일정 주기로 데이터가 맞는지 비교하는 프로세스를 갖추는 것이 중요하다.
- 외부 연동이 느려질 때, DB 커넥션 풀 문제
  - DB 트랜잭션 범위 내에서 외부 연동을 수행할 때, 외부 연동이 느려지면서 커넥션 풀 부족 현상이 발생할 수 있다.
  - 트랜잭션 외부에서 수행한다면, 트랜잭션으로 반영된 데이터를 되돌리는 보상 트랜잭션을 사용하며, 데이터 후보정이 필요하다.

### 실무에 적용할 점

- 일관성 중요도에 따른 API 연동 설계 방법
  - 판단 기준: 이 연동이 틀어졌을 때 돈이나 데이터가 틀어지는가.
  - 일관성이 중요하지 않은 연동(알림 발송, 통계 전송 등): 실패해도 로그만 남기고 넘어간다. 타임아웃 + 제한된 재시도면 충분하다.
  - 일관성이 중요한 연동(결제, 포인트 차감 등)은 설계 단계에서 세 가지를 갖춘다.
    1. 멱등키: 클라이언트가 요청마다 고유 키를 만들어 보내고, 서버는 같은 키의 요청을 한 번만 처리한다. read timeout 후 재시도해도 이중 처리가 안 된다. [Stripe의 `Idempotency-Key` 헤더](https://docs.stripe.com/api/idempotent_requests), EC2 RunInstances의 client token이 이 방식이다.
    2. 성공-확인(조회) API: 타임아웃으로 결과를 모를 때 이전 요청의 처리 여부를 조회할 수단. 연동 서비스가 제공하는지 계약 단계에서 확인하고, 없으면 주기 대사에 의존한다는 걸 알고 설계한다.
    3. 주기 대사(비교·보정) 배치: 두 시스템 데이터를 정기적으로 비교해 불일치를 찾는다. 멱등키와 확인 API가 있어도 마지막 안전망으로 필요하다.
  - [설계 노트: 포인트 차감과 결제 사이의 정합성 다루기](/posts/point-payment-deduction-consistency-design)에서 다룬 문제와 같은 구조다. 4장을 읽고 나니 그때의 선택지를 멱등키/확인 API/대사 세 층으로 다시 설명할 수 있다.
- 동시성 정도에 따른 동시성 제어 방법
  - 낙관적 락: 충돌이 드물다는 가정. 버전 컬럼으로 충돌을 감지하고(JPA `@Version`) 충돌하면 재시도한다. 잠금을 잡지 않아 처리량이 높지만, 충돌이 잦으면 재시도 비용이 커진다.
  - 비관적 락: 충돌이 잦다는 가정. `SELECT ... FOR UPDATE`로 먼저 잠근다. 대기가 생기지만 재시도가 없다.
  - 선택 기준: 같은 행을 동시에 수정하는 빈도(race condition 발생 정도). 드물면 낙관적, 잦으면 비관적. 실패 시 재시도 흐름을 만들 수 있는지도 본다 — 사용자 요청은 재시도로 풀 수 있지만, 배치 대량 갱신은 비관적 락이 단순하다.
  - 6장에서 본격적으로 다루니, 그때 [외부 API 연동의 정합성, 분산락, 그리고 테스트 전략](/posts/external-api-consistency-and-locking)의 사례와 붙여서 정리한다.
- Spring Boot 4 이후부터 HTTP 연동 라이브러리 선택 기준
  - 기본값에 맡기면 HTTP 커넥션 풀을 제어할 수 없다.
  - `RestClient`의 request factory 기본값은 classpath 순서로 정해진다 — Apache HttpClient → Jetty → JDK HttpClient(`java.net.http`) → `SimpleClientHttpRequestFactory`(HttpURLConnection). ([공식 레퍼런스](https://docs.spring.io/spring-framework/reference/integration/rest-clients.html))
  - 기본 의존성만 있는 스프링 부트 앱은 Apache도 Jetty도 없으므로 JDK HttpClient가 잡힌다. `RestTemplate`은 Simple이 기본이다.
  - 커넥션 풀 관점에서 보면
    - `SimpleClientHttpRequestFactory`: 관리되는 커넥션 풀이 없다.
    - JDK HttpClient: 내부에서 커넥션을 재사용하지만 풀 크기·대기 시간을 설정하는 API가 없다. 시스템 프로퍼티(`jdk.httpclient.connectionPoolSize`, `jdk.httpclient.keepalive.timeout`)로 일부만 조절된다.
  - 4장의 세 설정(풀 크기, 커넥션 대기 시간, keep alive)을 조절하려면 Apache HttpClient(`PoolingHttpClientConnectionManager`)나 Jetty를 의존성에 넣고 명시해야 한다. 외부 연동이 중요한 서비스라면 기본값에 맡기지 않는다.

### 더 알아볼 것 / 질문

- read timeout은 상황별로 조절해야 한다. 가이드라인이 없다면 p95/p99 기준으로 설정하는 건 어떨까?
  - [AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter)가 같은 방식을 쓴다. 허용 가능한 false timeout 비율(정상인데 타임아웃으로 끊기는 요청의 비율)을 먼저 정하고, 그에 해당하는 다운스트림 응답 시간 백분위를 타임아웃으로 잡는다. 0.1%를 허용하면 p99.9다. p99로 잡는 건 정상 요청 1%를 끊겠다는 선택이므로, 백분위 선택이 곧 허용 오차 선언이다.
  - 원문이 짚는 주의점 세 가지
    - 응답 시간이 고른 서비스(p99.9가 p50에 가까움)는 백분위 그대로 잡으면 작은 지연 증가에도 타임아웃이 쏟아진다. 여유분을 더한다.
    - 인터넷 구간을 지나는 호출은 최악 네트워크 지연을 반영한다.
    - 타임아웃이 DNS 조회나 TLS 핸드셰이크까지 포함하는지 확인한다. 원문에는 배포 직후 새 커넥션의 TLS 수립 시간 때문에 20ms 타임아웃이 반복해서 터진 사례가 실려 있다.
- Apache HttpClient의 socket timeout과 OkHttp의 call timeout
  - socket timeout(Apache HttpClient 5의 `responseTimeout`): 패킷과 패킷 사이의 최대 무응답 시간이다. 패킷이 조금씩이라도 계속 오면 전체 응답이 아무리 오래 걸려도 타임아웃이 나지 않는다. ([Baeldung 정리](https://www.baeldung.com/httpclient-timeout))
  - OkHttp의 `callTimeout`: DNS 조회, 연결, 요청 전송, 서버 처리, 응답 본문 읽기까지 호출 전체 시간을 한 번에 제한한다. 기본값이 0(무제한)이라 직접 설정해야 한다. connect·read·write timeout은 각각 기본 10초다. ([Baeldung 정리](https://www.baeldung.com/okhttp-timeouts))
  - 실무 의미: 응답이 큰 API나 스트리밍은 read/socket timeout만으로는 전체 시간에 상한이 없다. "이 호출은 총 N초 안에 끝나야 한다"는 요구가 있으면 call timeout 계열이 필요하다.

    ![HTTP 호출을 풀 대기부터 응답 읽기까지 가로 타임라인으로 그린 도식. socket timeout은 응답 패킷 사이 간격마다 0부터 다시 재서 패킷이 이어지는 한 전체 시간에 제한이 없고, call timeout은 DNS 조회부터 응답 본문 끝까지 전체를 한 번에 잰다](@/assets/images/2026-august-week2-review/socket-timeout-vs-call-timeout.svg)

  - Apache HttpClient 5의 `connectionRequestTimeout`은 풀에서 커넥션을 가져올 때까지의 대기 시간이다 — 본문의 "HTTP 커넥션 풀 대기 시간 1~5초"가 이 설정이다.

- 재시도 횟수와 간격을 정하는 정량적인 기준
  - 책의 "1~2번, 3초"에 업계 기준을 붙이면 이렇다.
  - [Google SRE 책](https://sre.google/sre-book/handling-overload/): 요청당 최대 3회 시도 + 클라이언트 단위 retry budget — 전체 요청 대비 재시도 비율이 10%를 넘으면 재시도하지 않는다. budget 없이 요청당 3회만 제한하면 과부하 시 부하가 최대 3배까지 커지는데, budget을 얹으면 1.1배로 억제됐다는 실측이 실려 있다.
  - AWS: 고정 간격 대신 [지수 백오프 + 지터](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)를 쓴다. 간격을 매번 늘리되(capped exponential backoff) 무작위 지터를 더해 재시도가 같은 시각에 몰리지 않게 한다. 지터가 없으면 실패한 클라이언트들이 같은 시각에 다시 몰린다.
  - 라이브러리 기본값 참고: [resilience4j Retry](https://resilience4j.readme.io/docs/retry)는 최대 3회 시도(최초 호출 포함), 간격 500ms가 기본이다.
- retry storm이 발생하는 기준, 그리고 대비하는 방법
  - 발생 조건 세 가지 (AWS Builders' Library 기준)
    - 계층마다 독립적으로 재시도: 5계층 호출 스택에서 계층마다 3회씩 재시도하면 최하단 DB에는 3^5 = 243배의 부하가 간다.
    - 타임아웃이 너무 짧음: 정상 응답까지 실패로 판정해 전부 재시도로 돌린다.
    - 지터 없는 백오프: 실패한 요청들이 같은 시각에 다시 몰린다.
  - 대비 방법
    - 재시도는 호출 스택의 한 지점에서만 한다. 어느 계층이 재시도를 담당하는지 정하고 나머지 계층은 실패를 그대로 올린다.
    - retry budget 또는 token bucket으로 재시도 총량을 제한한다. AWS SDK는 2016년부터 token bucket 방식 재시도 제한을 내장한다.
    - 지수 백오프 + 지터를 기본으로 한다.
    - 서킷 브레이커도 같은 목적이지만, AWS는 열림/닫힘에 따라 시스템 동작이 두 갈래로 갈려 테스트가 어렵다는 부작용을 지적하며 token bucket을 선호한다.
    - 재시도 비율(재시도 수 / 전체 요청 수)을 지표로 모니터링한다. retry budget의 10%가 경보 기준선이 될 수 있다.

AWS Builders' Library 「Timeouts, retries, and backoff with jitter」에서 인사이트 ([원문](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter))

- 전제: 많은 실패가 "요청이 끝나지 않는" 형태로 나타난다. 기다리는 동안 클라이언트는 메모리·스레드·커넥션·포트를 계속 쥐고 있으므로, 방치하면 자원 고갈로 이어진다. 4장 도입부의 "스레드 풀이 외부 연동에 묶인다"와 같은 문제 의식이다.
- 타임아웃 값 정하기
  1. 모든 원격 호출에 타임아웃을 건다. 같은 장비 안의 프로세스 간 호출도 마찬가지다. connection timeout과 request timeout 둘 다.
  2. 허용할 false timeout 비율(정상인데 타임아웃으로 끊기는 비율)을 먼저 정하고, 다운스트림 응답 시간의 해당 백분위를 타임아웃으로 쓴다. 0.1% 허용 → p99.9.
  3. 이 방식이 안 통하는 경우: 인터넷 구간을 지나는 호출(최악 네트워크 지연을 반영), 응답 시간이 아주 고른 서비스(p99.9가 p50에 가까우면 여유분을 더한다), 타임아웃이 DNS 조회·TLS 핸드셰이크를 포함하지 않는 구현.
  4. 사례: 20ms 타임아웃이 배포 직후에만 터졌다. 원인은 새 커넥션의 TLS 수립 시간이 타이머에 포함돼서였고, 최종 해법은 트래픽을 받기 전 기동 시점에 커넥션을 미리 맺는 것이었다.
- 재시도와 백오프
  1. 재시도는 이기적(selfish)이다. 서버의 시간을 더 써서 자기 요청의 성공 확률을 올리는 행위다. 실패가 드물 땐 좋은 거래지만, 실패 원인이 과부하일 땐 부하를 키워 복구 자체를 늦춘다.
  2. 백오프는 지수적으로 늘리되 상한을 둔다(capped exponential backoff). 상한에 걸린 채 무한히 재시도하면 고정 속도로 계속 두드리는 것과 같으므로, 재시도 횟수 자체를 제한하고 실패를 상위 계층으로 올려 처리한다.
  3. 계층 곱셈: 5계층 호출 스택에서 계층마다 3회씩 독립적으로 재시도하면 최하단에는 3^5 = 243배 부하가 간다. 재시도는 스택의 한 지점에서만 한다.
  4. 서킷 브레이커에는 유보적이다. 열림/닫힘에 따라 시스템 동작이 두 갈래(modal)가 돼 테스트하기 어렵고 복구를 늦출 수 있다. 대신 token bucket으로 재시도 총량을 제한한다 — 토큰이 있으면 자유롭게 재시도하고, 소진되면 고정 비율로만. AWS SDK에 2016년부터 내장돼 있다.
  5. 부수 효과가 있는 API는 멱등성이 보장될 때만 재시도한다. EC2 RunInstances처럼 명시적 client token을 받는 API가 그 예다.
  6. "4xx는 재시도하지 않고 5xx는 재시도한다"는 원칙은 최종 일관성 때문에 흐려진다. 방금 4xx였던 요청이 상태 전파 후 성공하기도 한다.
- 지터
  1. 백오프만으로는 부족하다. 실패한 클라이언트들이 같은 시각으로 백오프하면 재시도가 다시 한꺼번에 몰린다. 무작위 지연(지터)을 더해 분산시킨다.
  2. 지터는 재시도만의 도구가 아니다. cron, 주기 작업, 타이머 전부에 적용을 권한다. 클라이언트 여러 대가 "매분 0초"에 맞춰 요청을 쏘는 패턴이 실제로 흔했고, 지터를 넣어 같은 작업을 더 적은 서버로 처리했다.
  3. 단, 스케줄 작업의 지터는 호스트마다 무작위가 아니라 호스트별로 항상 같은 값을 쓴다. 문제가 무작위로 발생하면 원인 추적이 안 되고, 패턴으로 발생해야 사람이 찾을 수 있기 때문이다.

Google SRE 「Handling Overload」에서 인사이트 ([원문](https://sre.google/sre-book/handling-overload/))

- 요청당 상한: 최대 3회 시도. 3번 실패했다면 데이터센터 전체가 과부하일 가능성이 높아 더 시도해도 소용없다는 판단이다.
- 클라이언트당 retry budget: 재시도 비율 10%. 각 클라이언트가 자기 전체 요청 대비 재시도 비율을 추적하고, 10%를 넘으면 재시도하지 않는다. 일부 서버만 과부하라면 재시도가 적게 필요할 것이고, 10%를 넘게 필요한 상황이면 백엔드 전체가 과부하라는 논리다.
- 실측 효과: 요청당 3회 제한만 있으면 최악의 경우 부하가 3배 근처까지 커지지만, 10% budget을 얹으면 1.1배로 억제됐다.
- 두 장치는 상호 보완이다. 요청당 상한은 개별 요청의 낭비를 막고, retry budget은 클라이언트 전체의 재시도 총량을 막는다.

세 자료의 교차점: 책 4장은 서킷 브레이커를, AWS는 token bucket을, Google은 retry budget을 쓴다. "재시도 총량을 제한한다"는 목표는 셋이 같고 수단이 다르다.

- 동시성 정도에 따른 동시성 제어 방법
  - 낙관적 락과 비관적 락.
  - race condition 에 따른 선택
- spring boot 4 이후부터 http 연동 라이브러리 선택 기준

### 핵심 내용 정리

### 배운 점 / 인사이트

동기 연동과 비동기 연동

- 외부 연동 결과가 필요한게 아니라면, 동기 방식 대신 비동기 방식 연동도 고려할 필요가 있다.
- 동기 방식
  - 특징
    - 프로그램 흐름 직관적으로 이해 가능
    - 디버깅 용이
  - 고려할점
    - 외부 연동 실패가 전체 기능 실패인지 확인 필요
    - 외부 연동된 서비스 응답 시간도 고려 필요
- 비동기 방식
  - 특징
    - 한 작업이 끝날 때까지 기다리지 않고 바로 다음 작업을 진행한다.
    - 외부 연동을 비동기 처리하면 외부 연동된 서비스 응답 시간까지 기다리지 않아도 된다.
  - 대표적인 방법
    - 푸시 서비스 연동
    - 포인트 서비스 연동
    - 검색 서비스 연동
    - SMS 발송 서비스 연동
  - 비동기 방식이 사용 가능한 서비스 특징
    - 연동에 약간의 시차가 생겨도 문제되지 않음
    - 일부 기능 실패해도 재시도 가능
    - 연동에 실패해도 수동 처리 가능
    - 연동에 실패해도 무시 가능
- 궁극적 일관성(eventual consistency)
  - 분산 시스템에서 데이터 복제가 발생할 때, 두 데이터 간 일관성 보장하지만, 일정 시간 지난 후 일관성이 맞춰진다는 의미.

별도 스레드를 이용한 비동기 연동

- 방법
  - 요청마다 스레드 생성해서 진행
  - 스레드풀 활용해서 진행
- 주의 사항
  - 트랜잭션 롤백이 안될 수 있다. 왜냐하면 외부 스레드의 예외가 전파되지 않기 때문이다.
  - 스레드 생성시 메모리를 할당하므로 문제가 발생할 수 있다.

메시징을 이용한 비동기 연동

- 메시징 이점
  - 두 시스템 간 영향을 주지 않는다. : 메시징 시스템 중간에 메시지 보관하는 버퍼 역할을 해서 consumer 용량에 맞게 메시지 처리가 가능하다.
  - 확장에 용이하다. : producer, consumer 늘리기만 하면 된다.
- 메시지 생성 측 고려 사항
  - 메시지 유실을 고려한다. 이 때 선택지는 3개다.
    - 무시한다. : 단순 로그는 유실되도 된다.
    - 재시도한다. : 중복 메시지 전송 가능성 있다.
    - 실패 로그를 남긴다. : 후처리한다. 후처리에 필요한 데이터를 남겨야 한다.
  - 트랜잭션 엮이는 일도 마찬가지로 조심하자.
    - 액티브MQ는 글로벌트랜잭션을 제공해 실패에 대응이 쉽다. 그러나 2-phase 커밋 기반이어서 처리량이 느리다.
- 메시지 소비 측 고려 사항
  - 메시지 소비자는 2가지 이유로 중복 처리할 수 있다.
    - producer 가 같은 데이터를 가진 메시지를 메시지 시스템에 두 번 전송한 경우
    - ~~consumer 가 메시지 처리 과정에서 오류가 발생해 메시지 재수신~~ -> 외부 API 타임아웃으로 인한 재시도. 그리고 외부 API 중복 호출 가능성
  - 메시지 ID를 부여해서 중복 여부를 검증해서 처리한다. -> 멱등성을 가진다.
  - 메시지 lag 을 주의하자. -> 모니터링 잘해서 잘 소비되는지를 판단하자.
- 메시지 종류 : 이벤트와 커맨드
  - 이벤트
    - 발생했음을 알림.
    - 정해진 수신자가 없고, 발행한 사건에 관심있는 소비자가 메시지를 수신한다.
  - 커맨드
    - 요청하는 메시지.
    - 수신측 기능 실행에 초점이 맞춰져야 한다.

트랜잭션 아웃박스 패턴

- 메시징 시스템 연동이 실패할 수도 있다. 메시지 데이터가 유실되지 않도록, 해당 데이터를 DB에 안전하게 저장한다. 그리고 메시지 중계 프로세스가 주기적으로 읽어서 메시징 시스템에 전송한다. DB 트랜잭션 범위 내, 아웃박스 테이블에 저장되므로 데이터 유실은 없다.

배치 전송

- 일정 간격으로 데이터를 전송한다. 배치 전송 과정은 다음과 같다.
  1.  DB에서 전송할 데이터를 조회한다.
  2.  조회한 결과를 파일로 기록한다.
  3.  파일을 연동 시스템에 전송한다.
- 파일 전송은 FTP, SFTP 또는 SCP 명령어로 수행한다.
- 파일로 데이터 주고받는 경우, 다음 항목도 함께 정해야 한다.
  - 송수신 주체, 시간, 경로
- 특징
  - 파일 생산자, 소비자 중 누가 전송 담당할지도 협의한다.
  - 정해진 규칙은 없고 운영 상황에 따라 조율한다.
  - 배치 파일은 누락 등 오류가 많아 오전 시간대 전송할 때가 많다. 글로벌 서비스라면 다른 시간대일 수 있다.
  - 파일 저장될 경로나 이름이 충돌하지 않도록 규칙을 정한다.
  - 파일 재처리 기능, 파일이 지정한 시간대에 전송하지 못할 때가 많다. 이럴 때를 대비해서 API를 만들어서 수동 배치 가능하게 세팅해야 한다.
- 생산자가 소비자로 업로드 할 경우 다음 같은 방식으로 동작한다
  - 지정할 경로에 파일이 존재하는지 확인
  - 파일이 존재하면 파일로부터 데이터 조회
  - 파일이 없으면 알맞게 후처리
  - 읽어온 데이터를 시스템에 반영
  - 처리 완료한 파일은 다른 폴더로 이동 (백업)
- 파일이 없는게 정상인지 확인도 필요하다. 데이터가 없어서 파일이 없는건지, 오류 때문인지 규칙을 잘 정의해서 빈파일을 전달할지 말지도 결정해야 한다.

CDC

- CDC란
  - 변경된 데이터를 추적하고 판별해서 데이터로 작업을 수행할 수 있는 패턴이다.
  - MySQL 같은 DBMS 데이터가 변경되면 그 변경 내용을 통지하는 기능을 제공한다. INSERT, UPDATE, DELETE 쿼리 실행 후, 커밋되면 DB 데이터가 변경되고, 변경된 데이터를 CDC 처리기에 전송한다.
  - **CDC로 처리하면 DB에서 처리된 순서대로 데이터가 전달된다는 특징이 있다**
- CDC 를 사용하는 유형은 두 가지다.
  - 변경 데이터를 그대로 전파할 때,
  - 변경 데이터를 변환해서 전파할 때,
- CDC 처리기 구성방법
  - DB, 메시징 시스템, API 등 다양한 방법으로 전파한다.
  - 두 시스템 간 데이터 동기화가 목적이면 DB 기반 CDC를 세팅한다.
  - 메시징 시스템에 데이터 전파하면 여러 시스템에 변경된 데이터 전달해 확장할 수 있다.
- CDC는 이벤트에 가깝지만, 이벤트처럼 정확한 의미 전달하지 못한다. 값 변경만 알려주기 때문이다.
- CDC와 데이터 위치
  - CDC 처리기는 변경 데이터를 어디까지 처리했는지 기록해야 한다.
  - Mysql 은 바이너리 로그로 CDC를 구현하는데, 변경된 데이터와 로그 파일 위치 값을 갖는다.
- CDC가 유용할 때
  - 시스템이 복잡해서 연동 코드 넣기 부담스러울 때, CDC가 유용하다.
  - 예시로 주문 시스템 신규 구축할 때 기존 주문 시스템 반영해야 하는 경우 사용한다.

### 실무에 적용할 점

- 별도 스레드를 이용한 비동기 연동 — 작업자가 비정상 종료되면 어떻게 처리할지 (개인 ThreadPoolExecutor 정리에서 차용)
  - 세 관점으로 나눠서 봐야 한다.
    - 스레드 관점 : 예외로 죽은 워커는 풀이 새 워커로 교체한다. 풀이 스레드 부족으로 말라 죽지는 않지만, 예외가 빈번하면 스레드 재생성 비용이 성능 문제가 된다.
    - 태스크 관점 : 예외를 던진 태스크는 재시도되지 않고 그대로 유실된다. 재시도가 필요하면 `afterExecute` 훅이나 태스크 내부 try-catch로 직접 구현한다.
    - 프로세스 관점 : 스레드 풀의 큐는 메모리에만 있다. 재배포·OOM kill·크래시가 나면 대기 중 작업과 실행 중 작업이 전부 유실된다.
      - graceful shutdown(`waitForTasksToCompleteOnShutdown` + `awaitTerminationSeconds`)은 정상 종료만 커버한다. SIGKILL·크래시에는 무력하다.
      - 유실이 허용되지 않으면 작업을 먼저 DB에 저장(PENDING)하고 처리 후 상태를 갱신(DONE)한다. 트랜잭션 아웃박스 패턴과 같은 구조다.
      - 실행 중 죽은 작업은 PROCESSING 상태로 오래 머문 건을 다시 큐잉(reaper)해서 복구한다. 이러면 at-least-once가 되므로 작업이 멱등해야 한다. 4장 멱등키와 연결된다.
  - `execute()`와 `submit()`의 예외 동작이 다르다.
    - `execute()` : 워커 스레드가 죽고 교체된다. `UncaughtExceptionHandler`가 호출되고, 아무도 안 보면 최소한 stderr에는 찍힌다.
    - `submit()` : 워커는 살아있고 예외가 Future 안에 갇힌다. `get()`을 호출하지 않으면 완전히 조용히 사라진다. fire-and-forget에서 가장 위험하다. ([SEI CERT TPS03-J](https://wiki.sei.cmu.edu/confluence/display/java/TPS03-J.+Ensure+that+tasks+executing+in+a+thread+pool+do+not+fail+silently))
    - `afterExecute(r, t)`는 태스크가 죽는 순간에도 finally 경로에서 호출되므로 로깅·알림의 마지막 기회다. 단 `submit()`이면 `t`가 null이라 Future를 직접 열어봐야 한다.
    - 주의 : `beforeExecute`/`afterExecute` 훅 자체가 예외를 던지면 워커 스레드가 연쇄로 비정상 종료될 수 있다고 Javadoc이 경고한다. 훅 안에서는 예외를 삼킨다.
  - 스레드 풀 설정 함정 (Spring Boot)
    - Boot 기본값은 core=8, max·queue 무제한이다. 큐가 무한이라 스레드 생성 조건(큐 포화)에 절대 도달하지 않아 풀이 8개로 고정되고, 작업이 밀리면 큐가 힙을 채워 GC 정지 끝에 OOM으로 죽는다. `queue-capacity`를 반드시 유한값으로 지정한다. ([spring-boot#22835](https://github.com/spring-projects/spring-boot/issues/22835))
    - 표준 조합 : `ThreadPoolTaskExecutor` + 유한 queueCapacity + `CallerRunsPolicy`. 거부 시 제출한 스레드가 직접 실행해서 자연스러운 백프레셔가 된다.
    - `@Scheduled`는 `@Async`와 별개의 풀(`ThreadPoolTaskScheduler`)을 쓰고 기본 크기가 1이다. 스케줄 작업이 밀리면 여기부터 확인한다.
    - `SimpleAsyncTaskExecutor`는 이름과 달리 풀이 아니다. 호출마다 새 스레드를 만든다. 단 Java 21+에서 `spring.threads.virtual.enabled=true`를 켜면 가상 스레드로 동작해 1급 선택지가 된다. (7장 가상 스레드와 연결)
  - ThreadLocal 컨텍스트(MDC, SecurityContext, 트랜잭션)는 새 스레드로 전파되지 않는다. 요청 추적 ID가 새 스레드의 로그에서 빠져 추적이 끊긴다. `TaskDecorator`로 복사하고, 커밋 전에 비동기 작업이 먼저 도는 문제는 `AFTER_COMMIT` 리스너로 푼다. (3장 트랜잭션 정리와 연결)
  - 참고 : [Spring Task Execution and Scheduling](https://docs.spring.io/spring-framework/reference/integration/scheduling.html) · [Spring Boot Task Execution](https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html)
- 메시징을 이용한 비동기 연동
  - 설명 : 두 시스템 사이에 메시징 시스템을 버퍼로 둬서 생산자와 소비자를 분리한다. 생산자는 브로커에 넣는 데까지만 책임지고, 소비자는 자기 용량에 맞는 속도로 꺼내 처리한다. 서로의 장애·지연이 상대에게 직접 전파되지 않고, producer/consumer를 늘리는 것만으로 확장된다.
  - 적용 방식
    - 메시지 종류부터 정한다. 이벤트인지 커맨드인지에 따라 설계와 책임 소재가 달라진다.
    - 발행 쪽 : 유실이 허용되면 발행하고 실패 로그만 남긴다. 유실되면 안 되면 아래의 트랜잭션 아웃박스로 발행한다. 액티브MQ의 글로벌 트랜잭션은 2PC 기반이라 처리량이 낮아 제외한다.
    - 소비 쪽 : 멱등 소비자가 필수다. 같은 메시지는 두 번 이상 도착할 수 있다.
  - 제약
    - 결과를 즉시 알 수 없다. 사용자가 응답에서 결과를 확인해야 하는 기능에는 쓸 수 없다.
    - 전달 보장은 at-least-once다. 중복 자체를 막을 수는 없고 소비 쪽에서 처리한다.
    - 브로커가 새로운 장애 지점이 된다. 브로커의 가용성, 디스크 용량, 버전 업그레이드를 관리하는 일이 추가된다.
  - 주의사항
    - consumer lag을 모니터링한다. 소비가 생산을 못 따라가면 lag이 계속 늘어난다. 겉으로는 처리 지연으로만 보인다.
    - 재시도 상한을 정하고, 계속 실패하는 메시지는 DLQ로 빼서 큐를 막지 않게 한다.
    - 순서가 필요한 메시지는 키 단위로 직렬화한다. 소비자를 병렬화하면 전체 순서는 깨진다.
    - 소비자를 늘리거나 재시도를 걸면 연동 서비스 호출량도 그만큼 늘어난다. 4장에서 정리한 retry storm이 소비자 쪽에서도 발생할 수 있다.
- 트랜잭션 아웃박스 패턴 ([microservices.io 원문](https://microservices.io/patterns/data/transactional-outbox.html))
  - 설명 : 메시지를 브로커로 바로 보내지 않고, 비즈니스 데이터 변경과 함께 같은 DB의 아웃박스 테이블에 한 로컬 트랜잭션으로 커밋한다. 별도 릴레이가 테이블을 읽어 브로커에 발행한다. "커밋되면 반드시 발행되고, 롤백되면 절대 발행되지 않는다"를 2PC 없이 얻는다.
    - 2PC가 제외되는 이유 : 코디네이터가 모든 참여자에게 prepare를 보내 전원의 동의를 받은 뒤 commit을 보낸다. 단계마다 네트워크 왕복이 생기고, 참여자마다 각 단계의 결정을 디스크에 기록해야 하며, prepare에 동의한 참여자는 commit 지시가 올 때까지 잠금을 쥔 채 기다린다. 커밋 한 번의 비용이 로컬 트랜잭션의 몇 배가 된다. 위에서 정리한 액티브MQ 글로벌 트랜잭션이 이 방식이다.
  - 적용 방식 : 릴레이는 폴링과 CDC 두 방식이 있다. 폴링은 스케줄러가 아웃박스 테이블을 주기적으로 조회한다. 구현이 단순한 대신 조회 주기만큼 지연되고 테이블에 조회 부하가 생긴다. CDC는 Debezium이 binlog를 읽어 발행한다. 지연이 짧고 커밋 순서가 보장되지만, 커넥터 배포와 복제 지연 모니터링이 운영 작업으로 추가된다. 위 CDC 절에서 정리한 구성 그대로다. ([Debezium 공식 블로그](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/)) 유실이 허용되는 연동이면 이 패턴 대신 `AFTER_COMMIT` 리스너와 실패 로그로 끝낸다.
  - 제약 : 보장은 at-least-once다. 릴레이가 발행 직후 죽으면 같은 메시지가 두 번 나간다. 여기서도 멱등 소비자가 전제다. 발행 시점도 커밋 직후가 아니라 릴레이 주기나 CDC 지연만큼 늦는다. 궁극적 일관성을 받아들일 수 있는 연동에만 쓴다.
  - 주의사항
    - 비즈니스 데이터는 고쳤는데 아웃박스 INSERT를 잊는 실수가 가장 흔한 문제다. 이벤트 발행을 엔티티 저장 지점 한 군데로 모은다.
    - 발행 완료 건이 계속 쌓인다. 테이블 삭제·보관 정책을 처음부터 정한다. 3장 오래된 데이터 삭제·단편화 문제가 여기서 재현된다.
    - 계속 실패하는 메시지 하나가 릴레이를 막지 않게 재시도 상한 + 실패 보관을 두고, 순서가 중요한 메시지는 릴레이 병렬화 시 키 단위로 직렬화한다.
    - 폴링 릴레이가 다중 인스턴스면 위의 `@Scheduled` 중복 실행 문제를 그대로 만난다.
  - 내 이력과의 대비
    - [외부 API 연동의 정합성, 분산락, 그리고 테스트 전략](/posts/external-api-consistency-and-locking)에서는 같은 이중 쓰기 문제를 동기 호출 + 보상 트랜잭션 + 대사로 풀었다. 아웃박스로 재설계하면 보상 조치가 줄어드는 대신 궁극적 일관성과 발행 지연을 받아들여야 한다. 사용자가 응답에서 결과를 확인해야 하는 기능이면 동기 + 보상을, 결과 확인이 늦어도 되는 기능이면 아웃박스를 선택한다.
    - 사가·도메인 이벤트가 이 패턴을 필요로 하는 쪽이고(이벤트를 안전하게 발행해야 사가가 성립), 이벤트 소싱은 대안이다. 사가를 공부할 때 이 항목과 다시 연결한다.

### 더 알아볼 것 / 질문

- `@Scheduled`와 복수 인스턴스 대응
  - 문제 : `@Scheduled`는 인스턴스마다 독립적으로 도는 로컬 스케줄러다. 파드를 2개 이상 띄우면 같은 작업이 인스턴스 수만큼 중복 실행된다. 스프링 자체에는 "한 인스턴스만 실행" 기능이 없다.
  - 대응 방법 1 — ShedLock (분산 잠금)
    - 설명 : 실행 직전 공유 저장소(DB 테이블, Redis)에 잠금 레코드를 쓰고, 성공한 인스턴스만 실행한다. 나머지는 대기 없이 스킵한다.
    - 적용 방식 : `@Scheduled` 위에 `@SchedulerLock` 애너테이션을 붙인다. 이미 쓰는 DB를 잠금 저장소로 재사용할 수 있어 도입 비용이 가장 낮다.
    - 제약 : 중복 방지만 한다. 놓친 스케줄 보상이나 failover는 없다.
    - 주의사항 : `lockAtMostFor`(노드가 죽었을 때 잠금이 풀리는 상한)는 작업 최대 실행 시간보다 길게, `lockAtLeastFor`는 시계 오차로 인한 즉시 재실행 방지용으로 잡는다. 저자 스스로 정확성 보장 장치가 아니라고 선을 긋는다 — 작업 멱등성은 여전히 필요하다.
  - 대응 방법 2 — Quartz 클러스터 모드
    - 설명 : 스케줄러 자체를 분산화한다. DB 잠금으로 조정해 클러스터 전체에서 한 번만 실행되고, 잠금 노드가 죽으면 다른 노드가 이어받는다.
    - 적용 방식 : JDBC JobStore + 클러스터 모드 구성. misfire 처리(놓친 스케줄 재실행), 잡 영속화, 동적 스케줄 변경까지 제공한다.
    - 제약 : 전용 테이블 11개를 만들고 스케줄러 설정을 따로 관리해야 한다. ShedLock은 테이블 1개로 끝난다.
    - 주의사항 : 놓친 실행을 반드시 보상해야 하는 작업일 때 선택한다. 중복 방지만 필요하면 ShedLock으로 충분하다.
  - 대응 방법 3 — 실행 주체 분리 (k8s CronJob, 스케줄러 전용 인스턴스)
    - 설명 : 스케줄링을 애플리케이션 밖으로 옮기거나(k8s CronJob이 시각마다 Job 파드를 하나 생성), 스케줄러 역할 인스턴스를 1개만 배포한다. 중복 문제가 구조적으로 사라진다.
    - 적용 방식 : CronJob은 작업마다 YAML 정의, 전용 인스턴스는 프로파일 분리로 구성한다.
    - 제약 : CronJob은 실행할 때마다 파드를 새로 띄운다. 매 실행에 JVM 기동 시간만큼 소요된다. 전용 인스턴스는 단일 장애점이 된다.
    - 주의사항 : 배치 작업에 적합하다. 실행 주기가 JVM 기동 시간보다 짧은 작업은 애플리케이션 안에서 처리한다.
  - 대응 방법 4 — 리더 선출
    - 설명 : 모든 인스턴스가 스케줄러를 갖되 리더만 실행하고, 리더가 죽으면 수 초 내 팔로워가 승계한다.
    - 적용 방식 : k8s Lease API 또는 Spring Integration의 리더 선출 기능을 쓴다.
    - 제약 : 구현 복잡도가 잠금 방식보다 높다.
    - 주의사항 : 단일 장애점 없이 고빈도 작업을 돌려야 할 때만 검토한다.
  - 공통 결론 : 어느 방식이든 노드 장애와 잠금 만료가 겹치면 중복 실행될 수 있다. 그래서 작업 멱등성까지 갖춰야 한다. ShedLock이 하는 일이 부록 C "DB로 분산 잠금 구현하기"의 패턴(잠금 테이블 + 소유자 + 만료 시각) 그대로라서, 부록 C 읽을 때 상호 참조한다.
  - 참고 : [ShedLock 가이드](https://rieckpil.de/lock-scheduled-tasks-with-shedlock-and-spring-boot/) · [Rethinking Java @Scheduled Tasks in Kubernetes](https://thenewstack.io/rethinking-java-scheduled-tasks-in-kubernetes/)
- 토스증권의 대규모 CDC 파이프라인 운영기 ([대규모 CDC Pipeline 운영을 위한 Debezium 개선 여정](https://toss.tech/article/cdc_pipeline))
  - 왜 챙겨봤는가 : 아웃박스 정리에서 CDC를 도입하면 커넥터 배포와 복제 지연 모니터링이 운영 작업으로 추가된다고 적었다. 이 글은 그 운영 작업이 실제로 어떤 문제로 나타나고 어떻게 개선했는지 보여주는 기록이다.
  - 스트리밍은 측정부터 어렵다 : 배치와 달리 특정 시점에 어떤 데이터가 얼마 만에 처리됐는지 확인하기 어렵다. 토스증권은 DB 이벤트 발생 시각(`source.ts_ms`)부터 타겟 도착까지 end-to-end 지연을 측정하고, 파이프라인을 Tier 1(300ms)부터 Tier 4(1시간)까지 지연 등급으로 분류해 운영한다.
  - 지표를 테이블 단위로 쪼갠다 : Debezium 기본 메트릭에 테이블별 초당 이벤트 수를 추가하고 Create/Update/Delete를 분류해 테이블 특성과 정합성을 파악한다.
  - 구축 시간이 도입 장벽이다 : 초기 적재는 배치(Sqoop)로 하고 Debezium은 `snapshot.mode=no_data`로 스트리밍만 시작하는 하이브리드로 초기 구성을 12시간에서 1시간으로 줄였다. 기존 파이프라인에 테이블 추가는 자체 개발한 `add_table` 스냅샷 모드로 5분 이내다.
  - 배울 점 : CDC를 검토할 때는 구현 여부보다 두 가지를 먼저 따진다. 지연을 몇 ms까지 허용할지 티어로 정의하고, 초기 스냅샷과 테이블 추가에 걸리는 시간을 확인한다.
