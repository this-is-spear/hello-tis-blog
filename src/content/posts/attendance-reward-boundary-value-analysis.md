## 상황

출석 챌린지에서는 다음 규칙으로 광고 제거 리워드를 제공합니다.

- **획득 조건:** 일주일 동안 연속 출석합니다.
- **광고 제거 기간:** 리워드를 수령한 날을 포함해 8일입니다.
- **수령 시점:** 7일 출석을 완료한 당일부터 완료 후 일주일 이내에 받을 수 있습니다.

자동 출석권도 보너스로 제공합니다. 사용자가 출석을 놓치면 자정 이후에 자동 출석권을 사용해 빠진 날의 출석을 채웁니다.

리워드를 받은 뒤 추가로 일주일 출석하면 광고 제거 기간이 자동으로 연장됩니다. 마지막 출석을 어떻게 채웠는지에 따라 연장을 처리하는 시점은 다릅니다.

- 사용자가 직접 출석하면 출석과 함께 즉시 연장됩니다.
- 자동 출석권으로 채우면 자정 이후에 출석권을 사용하면서 연장됩니다.

처음에는 출석 일수와 리워드 기간을 함께 확인하면 충분하다고 생각했습니다. 하지만 리워드를 늦게 받거나 자동 출석권을 사용하는 경우까지 더해지면서, 같은 일주일 출석이라도 처리 시점이 달라졌습니다.

## 문제

7일 출석을 완료한 뒤 리워드를 받는 시점에 따라 연장 결과가 달랐습니다.

- **완료 당일 수령:** 정상적으로 연장됐습니다.
- **이틀 뒤 수령:** 연장이 정상적으로 적용되지 않았습니다.

수령을 이틀 미루는 것은 허용된 행동입니다. 사용자가 수령 기한을 지켰고 이후 연장에 필요한 출석도 채웠다면 연장이 적용돼야 합니다. 그런데 수령 시점이 달라지자 결과도 달라졌습니다.

이 사례를 테스트에 추가하는 것만으로 충분할지 고민됐습니다. 다음 경우도 확인해야 했습니다.

- 완료하고 하루 뒤에 수령하는 경우
- 수령 기한에 가까워져서 받는 경우
- 마지막 출석을 자동 출석권으로 채우는 경우

예외를 발견할 때마다 테스트를 하나씩 늘리기보다, 어떤 기준으로 테스트를 나눌지 먼저 정리하고 싶었습니다.

## 원인

확인한 문제는 7일 출석을 완주하는 시점에 리워드 종료 여부를 판단하고 연장을 처리한다는 점이었습니다. 두 기간은 시작점과 길이가 다릅니다.

- **출석 완주:** 연속 출석 7일을 기준으로 판단합니다.
- **광고 제거:** 실제 수령일을 포함해 8일 동안 적용됩니다.

즉시 수령하는 경우에는 기존 판단으로도 정상 처리됐습니다. 하지만 수령이 늦어지면 리워드 종료 시점도 달라집니다. 출석 완주 시점이 리워드 종료 시점을 대신할 수 없었습니다.

수령일이 바뀌는 경계는 자정입니다. 아래 그림은 8월 23일에 완주한 사용자가 **23일 23:59:59에 받는 경우와 24일 00:00:00에 받는 경우**를 비교합니다. 수령 요청이 1초 늦어져 날짜가 바뀌면 만료일도 하루 뒤로 이동합니다. 실제 광고 제거는 만료일 다음날 00:30까지 유예되므로, 만료 날짜와 광고가 다시 나오는 시각은 구분해야 합니다.

![23일 수령과 24일 수령의 광고 제거 날짜를 두 줄로 맞추고, 아래에서 자정 직전과 정각의 수령 시각 및 만료일을 비교](@/assets/images/attendance-reward-boundary-value-analysis/01-claim-date-shift.png)

처음 문제가 발생한 이틀 뒤 수령 사례는 다음과 같습니다.

| 입력: 완주일 | 행위: 수령일  | 결과: 광고 제거 날짜 |
| ------------ | ------------- | -------------------- |
| 8월 23일     | 8월 23일 수령 | 8월 23 ~ 30일        |
| 8월 23일     | 8월 25일 수령 | 8월 25일 ~ 9월 1일   |

같은 날 완주해도 리워드가 끝나는 날은 다를 수 있습니다. 연장 조건을 채웠는지와 현재 리워드가 끝났는지를 각각 확인해야 합니다.

### 명세에서 구획과 경계를 찾아보기로 했습니다

이번 분석에서는 Maurício Aniche의 [『Effective Software Testing: A developer’s guide』](https://www.manning.com/books/effective-software-testing) 2장, 명세 기반 테스트를 참고했습니다. 예전에 책을 읽으며 남긴 [명세 기반 테스트 정리 글](https://github.com/this-is-spear/blog/blob/main/data/blog/books/effective-software-testing/2.mdx)을 다시 보면서, 입력을 나누고 경계를 찾는 방법을 이번 출석 리워드 문제에 적용해 보기로 했습니다.

![Maurício Aniche의 Effective Software Testing 책 표지](@/assets/images/attendance-reward-boundary-value-analysis/effective-software-testing-cover.jpg)

표지 출처: [Simon & Schuster 공식 도서 소개 · Manning 출판](https://www.simonandschuster.com/books/Effective-Software-Testing/Mauricio-Aniche/9781633439931)

명세 기반 테스트는 요구사항을 바탕으로 테스트를 도출하는 방법입니다. 모든 입력을 확인하기 어려우므로, 적은 테스트로 넓은 범위를 검증할 수 있도록 다음 세 단계로 정리했습니다.

1. **요구사항과 프로그램 이해**: 테스트할 행동이 무엇인지 파악하고, 입력에 따른 정상 결과와 실패 조건을 정리합니다.
2. **입출력 구획 탐색과 경계 분석**: 같은 방식으로 처리될 것으로 기대하는 입력을 묶어 대표값을 고르고, 동작이 달라지는 경계와 그 주변 값을 확인합니다.
3. **테스트 케이스 구현**: 선택한 입력과 기대 결과를 테스트로 옮기고, JUnit이나 Kotest 같은 도구로 자동화합니다.

테스트를 작성하다가 놓친 구획이나 경계를 발견하면 앞 단계로 돌아가 보완합니다. 처음부터 모든 경우를 떠올리기보다, 값을 선택한 근거를 남기고 테스트 스위트를 반복해서 강화하는 과정입니다.

여기서 구획은 같은 방식으로 처리되는 입력의 묶음이고, 경계는 처리 결과가 달라지는 지점입니다. 이번 사례에서는 다음 경계를 먼저 찾기로 했습니다.

- 출석이 6일에서 7일이 되는 순간
- 수령 기한이 끝나는 순간
- 광고 제거가 끝나는 순간

이틀 늦게 수령한 사례는 이미 문제가 확인된 재현 조건입니다. 다만 이틀 자체가 경계라고 단정할 수는 없습니다. 수령을 얼마나 늦췄는지에 따라 출석 완료와 리워드 만료의 관계가 어떻게 달라지는지 확인해야 합니다.

## 해결

### 무엇을 바꾸고 무엇을 비교할지 먼저 정했습니다

풀기 어려웠던 이유는 여러 조건이 서로 영향을 주기 때문이었습니다. 리워드를 받는 날이 바뀌면 광고 제거가 끝나는 날도 달라집니다. 같은 날의 출석을 채워도 직접 클릭했는지, 자동 출석권을 썼는지에 따라 완료 기록을 남기는 시각이 달라집니다.

그래서 먼저 다른 조건을 고정하고 **변수 하나의 경계**를 확인했습니다. 그다음 **여러 변수의 경계를 조합**했습니다. 각 표는 **입력 → 행위 → 결과** 순서로 읽도록 만들었습니다.

- **입력:** `출석 일수`, `수령 여부`, `연장 완료`처럼 변수별 열로 나눴습니다.
- **공통 조건:** 표 위에 `만료일 = 8월 23일`처럼 적었습니다.
- **행위:** 실행할 동작과 시각을 적었습니다.
- **결과:** 광고 표시나 수령 가능 여부를 나눠 적었습니다.

하나의 표에서는 질문 하나를 확인합니다. 예를 들어 **출석 일수 6일·7일 × 유예 종료 직전·정각**은 네 가지 조합입니다. 행을 따라 시간 경계를 비교하고, 출석 일수가 다른 행끼리 완주 여부의 차이를 비교할 수 있습니다. 날짜와 처리 순서가 중요한 사례에는 짧은 타임라인을 덧붙였습니다.

입력은 각 행의 **행위 직전 값**입니다. 연장 후 출석 일수가 새 도전 기준으로 바뀌는 경우에는 그 점도 표시했습니다. 가능한 모든 조합을 무조건 만들지는 않았습니다. 먼저 다른 조건을 고정하고, 실제로 만들 수 있는 입력 중 판단이 달라지는 조합을 골랐습니다.

분석할 변수와 경계는 다음처럼 정했습니다.

| 바꿔 볼 변수                       | 비교할 경계값                      | 확인하려는 차이                                    |
| ---------------------------------- | ---------------------------------- | -------------------------------------------------- |
| 채운 출석 일수                     | 6일 / 7일                          | 리워드를 받을 자격이 생기는가                      |
| 리워드를 받았는지                  | 수령 전 / 수령 후                  | 다음 출석과 출석권 획득이 가능한가                 |
| 수령 요청 시각                     | 수령 기한 1초 전 / 정확히 기한     | 받을 수 있는가, 기한이 지났는가                    |
| 리워드 만료일과 처리 날짜          | 만료일 당일 / 다음날 / 이틀 뒤     | 클릭과 자동 처리 중 어느 경로에서 연장하는가       |
| 광고 제거 종료 시각                | 다음날 00:29:59 / 00:30:00         | 광고 제거가 유지되는가, 끝나는가                   |
| 출석 후 지난 시간과 보유 출석권 수 | 4시간 직전 / 4시간 경과, 1장 / 2장 | 출석권을 한 장 더 얻을 수 있는가                   |
| 클릭과 자동 처리 순서              | 클릭 먼저 / 자동 처리 먼저         | 완주를 확인하는 시점과 실제 연장 결과가 달라지는가 |

시각은 초 단위로 표현했습니다. 예를 들어 00:29:59는 00:30:00보다 1초 앞입니다. 이 두 값을 비교하면 ‘종료 시각까지 포함하는지’가 드러납니다. 경계 직전의 값을 거점, 판정이 바뀐 첫 값을 접점이라고도 부르지만, 아래에서는 직전과 정각으로 풀어 적었습니다.

표를 읽을 때 구분할 내용은 다음과 같습니다.

- **기존 동작:** 앞서 코드에서 확인한 규칙을 기준으로 정리했습니다.
- **추가한 조합:** 확인한 규칙에서 결과를 도출했습니다. 모든 행을 실제 테스트로 실행했다는 뜻은 아닙니다.
- **유예 시간:** 현재 응답, 기대 결과, 추가로 검증할 조합을 구분했습니다.
- **안내 표현:** 내부 코드값의 의미를 풀어 썼으며, 실제 화면 문구를 인용한 것은 아닙니다.

서비스에서 의도한 규칙과 맞춰야 할 부분은 마지막에 따로 남겼습니다.

### 변수 하나씩 확인하기: 출석 일수와 이어진 날짜

**공통 조건**

- 첫 출석일: 8월 17일
- 리워드 수령: 아직 받지 않음

표마다 바꿀 변수와 고정할 조건을 나눴습니다.

**변수와 경계**

- 출석 기록: 0건 / 1건
- 출석 일수: 6일 / 7일
- 중간에 빠진 날: 없음 / 있음

자동 출석은 출석으로 인정한 날짜와 완료 기록 시각을 함께 봅니다.

**기록 유무와 완주 경계**

**고정 조건**

- `리워드 수령 = 안 받음`
- 출석 클릭 전까지 날짜가 끊기지 않음
- 클릭하는 날에는 아직 출석하지 않음

| 없음                          | 8월 17일 조회 | 0일 · 시작일 없음     | 미완주                  |

**날짜가 이어지는가**

**고정 조건**

- `첫 출석일 = 8월 17일`
- `오늘 = 8월 23일`
- `자동 보완 = 없음`

어제 출석만 바꿉니다.

| 입력: 8월 22일 출석               | 행위          | 결과: 출석 일수 | 결과: 도전 시작일 |
| --------------------------------- | ------------- | --------------- | ----------------- |
| 있음(17 ~ 22일 연속 출석 완료)    | 8월 23일 클릭 | 7일             | 8월 17일          |
| 없음(17 ~ 21일 출석 후 22일 결석) | 8월 23일 클릭 | 1일             | 8월 23일          |

**자동 출석권으로 마지막 날을 채울 수 있는가**

**고정 조건**

- `출석 기록 = 8월 17 ~ 22일`
- `8월 23일 출석 = 없음`

**23일 결석 → 24일 자동 처리 → 23일을 채웠는지 확인**하는 흐름입니다.

| 입력: 보유 출석권 | 행위                    | 결과: 출석 보완      | 결과: 완주                       |
| ----------------- | ----------------------- | -------------------- | -------------------------------- |
| 0장               | 8월 24일 자정 자동 처리 | 23일 보완 안 됨      | 완주 안 됨                       |
| 1장               | 8월 24일 자정 자동 처리 | 23일 보완 · 1장 사용 | 7일 완주 · 완료 기록 시각은 24일 |

### 변수 하나씩 확인하기: 리워드를 받을 수 있는 시각

**공통 배경:** 첫 출석일은 8월 17일입니다. 출석 일수, 완주 방식, 수령 시각, 중복 요청을 각각 별도 표로 비교합니다.

**변수와 경계**

- 출석 일수: 6일 / 7일
- 완주 방식: 직접 출석 / 자동 출석
- 수령 요청 시각: 기한 직전 / 정각

직접 완주한 사용자의 기한은 **8월 31일 00:00**입니다.

### 변수 하나씩 확인하기: 어느 날짜에 연장하는가

**공통 배경**

- 다음 도전 시작일: 8월 24일

### 여러 변수 조합하기: 수령 전후에 출석과 획득이 열리는가

| 새 수령               | 8월 30일          | 없음            | 8월 31일 조회 | 오늘부터 · 출석 0일                            |
| 오늘 클릭으로 연장    | 9월 1일           | 있음            | 8월 31일 조회 | 9월 1일부터 · 수령 당일 차단 규칙은 적용 안 함 |
| 오늘 자동 처리로 연장 | 8월 31일          | 있음            | 8월 31일 조회 | 오늘부터 · 출석 1일                            |

### 유예 시간으로 생기는 경계는 따로 모았습니다

유예는 **리워드 만료일 다음날 00:00부터 00:30 직전까지 광고를 계속 숨기는 30분**입니다. 이 구간에는 만료일은 지났지만 광고는 나오지 않습니다. 출석을 채우고 연장하는 자동 처리도 이때 실행되므로, 시간뿐 아니라 처리 순서를 함께 비교해야 합니다.

**시간 경계는 두 곳입니다.**

- **00:00:** 날짜가 바뀝니다.
- **00:30:** 광고를 숨겨 주는 시간이 끝납니다.

여기에 다음 변수를 조합했습니다.

- 출석 일수: 6일 / 7일
- 마지막 출석으로 인정한 날짜: 만료일 / 다음날
- 연장 기록: 없음 / 있음
- 처리 순서: 수령 먼저 / 자동 처리 먼저

| 묶어서 확인할 상황 | 바꿔 볼 변수와 경계값                                                 | 확인할 차이                                                |
| ------------------ | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| 유예 종료          | 만료 다음날 00:29:59 / 00:30:00                                       | 광고 표시와 수령 가능 여부가 각각 어떻게 바뀌는가          |
| 클릭과 자동 처리   | 클릭 먼저 / 자동 처리 먼저                                            | 완주 안내와 실제 연장 결과가 일치하는가                    |
| 자정과 완주 날짜   | 만료일 23:59:59 / 다음날 00:00:00, 마지막 출석 날짜가 만료일 / 다음날 | 만료일까지 채운 출석과 유예 중 새로 채운 출석을 구분하는가 |
| 자동 처리 지연     | 연장 완료가 00:30 직전 / 정각 / 이후                                  | 광고가 다시 나오는 순간과 실제 연장 적용이 어긋나는가      |
| 수령과 뒤늦은 연장 | 새 수령 기록 없음 / 있음인 채 자동 연장 실행                          | 이미 새로 받은 혜택에 연장을 중복 제공하는가               |

현재 코드에서 확인한 결과와 앞으로 만족해야 할 결과를 구분했습니다.

- **1·2번:** 현재 동작. 8월 30일 만료 사례입니다.
- **3번:** 현재 응답과 새 기대 결과의 비교. 8월 23일 만료 사례입니다.
- **4번:** 추가로 검증할 조합. 8월 23일 만료 사례입니다.

각 표에 실제 날짜를 적었습니다.

#### 1. 유예 종료 직전과 정각: 현재 수령 판단은 어떻게 바뀌는가

**고정 조건**

- 기존 만료일: 8월 30일
- 연장 완료: 아니요
- 다음 출석 도전: 7일 완주
- 새 리워드 수령 기한: 남아 있음

**변수와 경계**

- 유예 종료 직전: **8월 31일 00:29:59**
- 유예 종료 정각: **8월 31일 00:30:00**

각 행은 위의 고정 조건을 충족하는 사용자를 별도로 준비해 조회하거나 수령합니다.

| 입력: 유예 종료와의 관계 | 행위                   | 결과: 광고       | 결과: 안내·수령                     |
| ------------------------ | ---------------------- | ---------------- | ----------------------------------- |
| 1초 전                   | 8월 31일 00:29:59 조회 | 숨김             | 연장 대기                           |
| 정각                     | 8월 31일 00:30:00 조회 | 표시             | 수령 대기                           |
| 1초 전                   | 8월 31일 00:29:59 수령 | 숨김             | 기존 혜택 적용 중으로 수령 거절     |
| 정각                     | 8월 31일 00:30:00 수령 | 새 혜택으로 숨김 | 수령 성공 · 8월 31일 ~ 9월 7일 혜택 |

#### 2. 유예 안의 처리 순서: 클릭과 자동 처리 중 무엇이 먼저인가

**고정 조건**

- 기존 리워드 만료일: 8월 30일
- 자정 자동 처리 순서: 어제 결석 보완 → 완주 확인 → 연장

**변수와 경계**

- 클릭 시각: 자정 전 / 자정 후
- 완주 시점: 자동 처리 전 / 자동 처리 후
- 광고 제거: 00:30 유예 종료 전 / 종료 후

아래 표는 **클릭이 자동 처리보다 먼저 실행되는 하나의 연속된 시나리오**입니다.

**타임라인:** 8월 30일까지 완주 → 31일 00:00:03 클릭 → 00:00:05 자동 연장 → 새 도전 출석을 이어감.

| 입력: 저장된 출석                             | 입력: 실제 만료일 | 행위                        | 결과                                           |
| --------------------------------------------- | ----------------- | --------------------------- | ---------------------------------------------- |
| 7일(24 ~ 30일 연속 출석 완료)                 | 8월 30일 · 미연장 | 8월 31일 00:00:03 클릭      | 8건 기록 · 화면에는 상한인 7일 표시            |
| 8건(24 ~ 30일 완주 후 31일 추가 출석)         | 8월 30일 · 미연장 | 8월 31일 00:00:05 자동 처리 | 9월 6일까지 연장 · 31일 출석은 새 도전의 1일차 |
| 1일(새 도전에서 31일 출석 완료)               | 9월 6일           | 9월 1일 클릭                | 새 도전 출석 2일                               |
| 6일(새 도전에서 8월 31일 ~ 9월 5일 출석 완료) | 9월 6일           | 9월 6일 클릭                | 7일 완주 · 9월 7 ~ 13일로 다시 연장            |

출석 일수가 7에서 1로 바뀌어도 기록이 사라진 것은 아닙니다. 연장되면서 새 도전의 시작일이 바뀌고, 같은 클릭을 새 도전의 첫 출석으로 읽은 결과입니다.

두 번째는 **출석 시작이 하루 늦어 8월 31일에야 7일을 채우는 사용자**입니다. 자동 처리가 클릭보다 먼저 끝났고 새 수령 기한이 남아 있다는 조건을 고정했습니다.

**타임라인:** 8월 31일 자정 이후 자동 처리가 6일 확인 → 00:10 클릭으로 7일 완주 → 00:30 유예 종료.

위쪽 광고 제거 날짜와 아래쪽 출석 칸을 맞추면, 마지막 출석이 만료일 다음날에 놓이는 것을 볼 수 있습니다. 그림 아래에서는 **31일 00:10 클릭 직전의 출석 6일과 클릭 직후의 7일**을 비교했습니다. 아래 표는 이 과정을 시간순으로 보여줍니다.

이 경우에는 날짜뿐 아니라 **서버가 6일을 확인한 뒤에 사용자가 7일을 채웠다**는 순서가 문제였습니다. 자동 처리는 이미 끝났고, 클릭으로 연장할 수 있는 날짜도 지났습니다. 그런데 안내는 아직 광고 제거가 적용 중이라는 이유로 연장됐다고 말했습니다.

반대로 8월 31일 00:30까지 6일에 머문 사용자는 수령 대기로 바뀌지 않습니다. 광고는 다시 나오지만, 오늘 출석이 가능한 상태라면 출석을 계속할 수 있습니다. 만료 시각 하나만으로 클릭 가능 여부를 결정할 수 없었습니다.

#### 3. 자정과 완주 날짜: 광고 표시와 수령 자격을 나눠 판단하기

앞의 분석에서는 광고 제거가 적용 중인지와 연장할 수 있는지를 함께 보고 있었습니다. 기대 결과를 다시 정리하면서 **광고를 숨겨 주는 시간과 연장 자격을 판단하는 기간을 분리**하기로 했습니다. 자정 이후 30분은 자동 처리를 기다리는 여유 시간이며, 그 시간에 새로 출석을 채웠다고 연장 자격까지 늘어나는 것은 아니라는 기준입니다.

이번 네 가지 테스트는 날짜를 별도로 고정했습니다. 앞의 8월 23일 수령 사례와 달리, **8월 16일에 수령해 만료일이 8월 23일인 사용자**입니다.

**고정 조건**

- 기존 광고 제거 날짜: 8월 16 ~ 23일
- 광고 제거 유예: 8월 24일 00:00 ~ 00:30 직전
- 연장 기록: 없음
- 완주 후 리워드 수령 기한: 남아 있음

**변수와 경계**

- 7번째 출석으로 인정한 날짜: 23일 / 24일
- 실제 연장 처리: 기록 없음 / 있음
- 요청 시각: 자정 전후 / 00:30 전후

![위에는 16 ~ 23일 광고 제거와 24일 자정 이후 30분 유예, 아래에는 17 ~ 23일의 출석 1 ~ 7일과 수령 대기를 나란히 표시. 00:29:59와 00:30:00에는 광고 표시만 달라짐](@/assets/images/attendance-reward-boundary-value-analysis/07-grace-and-eligibility.png)

| 비교할 기준                   | 경계값                                | 이번 테스트에서 구분할 것                             |
| ----------------------------- | ------------------------------------- | ----------------------------------------------------- |
| 7번째 출석으로 인정되는 날짜  | 8월 23일 / 8월 24일                   | 기존 만료일까지 완주했는가, 다음날 완주했는가         |
| 만료일이 지났는지             | 8월 23일 23:59:59 / 8월 24일 00:00:00 | 광고를 계속 숨겨도 기존 만료일은 지났는가             |
| 광고를 숨기는 시간이 끝났는지 | 8월 24일 00:29:59 / 00:30:00          | 광고 표시만 달라지는가, 수령·출석 판단까지 달라지는가 |
| 실제 연장 처리 여부           | 연장 기록 없음 / 있음                 | 연장된 혜택이 실제로 존재하는가                       |

**두 사용자는 완주한 날짜가 다릅니다.**

**만료일까지 정상 완주한 사용자**

- 출석 날짜: 8월 17 ~ 23일
- 마지막 날 직접 클릭: 즉시 연장
- 마지막 날 자동 출석: 24일 자정 이후 출석 보완 → 연장

7일을 모두 채웠는데도 연장 기록이 없는 경우를 만들려면, 출석 보완은 끝났지만 연장 단계가 지연되거나 실패한 순간을 입력으로 준비해야 합니다.

**하루 늦게 완주하는 사용자**

- 17일: 결석했고 출석권으로도 보완하지 못함
- 18 ~ 23일: 6일 출석
- 24일 00:10: 클릭으로 7일 완주

광고는 아직 숨겨져 있지만 7번째 출석 날짜는 기존 만료일 다음날입니다.

여기서 **자동 처리가 실행된 날짜와 출석으로 인정한 날짜도 다릅니다.** 24일에 출석권으로 23일을 채운 정상 완주자는, 24일에 직접 클릭해 그날을 채운 사용자와 구분해야 합니다. 둘 다 서버에 기록을 남기는 날짜가 24일이라는 이유로 같은 조건으로 묶을 수 없습니다.

**네 테스트의 현재 응답과 기대 결과**

각 행은 별도로 준비한 시나리오입니다. 결과는 현재 응답과 새 기대 결과의 두 열로 나눴습니다.

**공통 조건**

- `연장 기록 = 없음`
- `새 수령 = 없음`
- `수령 기한 = 남음`

| 입력: 행위 전 출석                                   | 입력: 자동 연장 처리       | 행위                             | 결과: 현재                                          | 결과: 새 기대                                       |
| ---------------------------------------------------- | -------------------------- | -------------------------------- | --------------------------------------------------- | --------------------------------------------------- |
| 7일(17 ~ 23일 연속 출석 완료)                        | 지연·실패로 미연장         | 8월 24일 00:29:59 조회·수령      | 연장 대기 · 수령 거절                               | 수령 대기 · 수령 가능 · 광고 숨김                   |
| 7일(17 ~ 23일 연속 출석 완료)                        | 지연·실패로 미연장         | 8월 24일 00:00:03 클릭           | 오늘 출석 가능                                      | 수령 대기로 추가 출석 차단                          |
| 6일(18 ~ 23일 연속 출석 완료)                        | 6일 확인 후 연장 없이 완료 | 8월 24일 00:10 클릭 → 00:30 조회 | 완주 후 연장 대기 → 00:30 수령 대기. 실제 연장 없음 | 클릭으로 완주한 직후부터 수령 대기 · 00:30에도 유지 |
| 7일(18 ~ 23일 출석 후 24일 00:10에 마지막 출석 완료) | 6일 확인 후 연장 없이 완료 | 8월 24일 00:20 조회              | 출석권 획득까지 대기 안내                           | 수령 대기 · 출석권 획득 흐름 차단                   |

네 번째 테스트의 00:20은 출석하고 10분만 지난 시각입니다. 아직 4시간이 지나지 않았다는 사실을 확인하려는 테스트가 아닙니다. **수령 대기인 사용자에게 출석권 획득을 기다리도록 안내해도 되는가**를 확인합니다. 수령 대기라면 출석권을 얻는 흐름 자체를 막는다는 기대입니다.

네 테스트가 공통으로 요구하는 것은 **광고가 아직 나오지 않는다는 이유만으로 연장 대기나 출석 가능 상태로 판단하지 않는 것**입니다. 만료일, 완주한 날짜, 실제 연장 기록을 따로 확인해야 합니다.

특히 00:29:59와 00:30:00 사이에는, 새 수령이나 연장이 없다는 조건에서 광고 표시만 바뀌어야 합니다. 이미 수령 대기인 사용자의 상태가 이 시각 때문에 다시 바뀌어서는 안 됩니다. 이 기대 결과는 앞에서 정리한 현재 코드의 동작과 다르며, 아직 수정 후 통과를 확인한 결과는 아닙니다.

#### 4. 추가로 확인할 조합: 6일·7일과 자동 처리 지연

앞의 네 테스트는 유예 안에서 완주했거나, 이미 완주했지만 연장을 기다리는 경우였습니다. 이 기대 결과를 적용하려면 **아직 완주하지 않은 사용자**와 **자동 처리가 00:30을 넘긴 사용자**도 확인해야 합니다.

**고정 조건**

- 리워드 수령일: 8월 16일
- 기존 만료일: 8월 23일
- 유예 종료 시각: **8월 24일 00:30:00**

각 행은 별도로 준비하며, 결과는 아직 실행하지 않은 테스트의 기대 또는 확인할 규칙입니다.

**변수와 경계**

- 유예 종료 시점의 출석 일수: **6일 / 7일**
- 연장 기록이 생기는 시각: **00:30 직전 / 정각 / 이후**
- 자동 연장 전 새 수령 기록: **없음 / 있음**

수령 대기를 비교하는 행에서는 수령 기한이 남아 있다는 조건을 고정합니다.

**출석 일수 × 유예 종료 시각**

**고정 조건**

- `새 수령 = 없음`
- `연장 완료 = 아니요`

자동 처리는 24일의 추가 클릭 전에 연장 없이 끝났습니다. 6일은 18 ~ 23일만 출석한 사용자, 7일은 여기에 24일 00:10 출석을 더한 사용자입니다. **결과는 새 기대 기준**입니다.

| 입력: 출석 일수 | 행위: 8월 24일 조회 시각 | 결과: 광고 | 결과: 리워드 |
| --------------- | ------------------------ | ---------- | ------------ |
| 6일             | 00:29:59                 | 숨김       | 완주 전      |
| 6일             | 00:30:00                 | 표시       | 완주 전      |
| 7일             | 00:29:59                 | 숨김       | 수령 대기    |
| 7일             | 00:30:00                 | 표시       | 수령 대기    |

- **출석 6일:** 오늘 출석할 수 있습니다.
- **출석 7일:** 수령 대기이므로 추가 출석과 출석권 획득이 차단됩니다.

00:30 경계를 지날 때는 광고 표시만 바뀐다는 기대입니다.

**연장 완료 여부 × 유예 종료 시각**

**고정 조건**

- `만료일까지 완주 = 예`
- `새 수령 = 없음`

연장 완료인 행은 **8월 24 ~ 30일의 연장 기록이 조회 전에 저장된 경우**입니다. 여기서 출석 일수는 연장 전 완주분을 뜻하며, 연장 후 새 도전의 일수와 구분합니다. **결과는 새 기대 기준**입니다.

| 입력: 연장 완료 | 행위: 8월 24일 조회 시각 | 결과: 광고 | 결과: 적용 혜택         |
| --------------- | ------------------------ | ---------- | ----------------------- |
| 아니요          | 00:29:59                 | 숨김       | 기존 혜택의 유예        |
| 아니요          | 00:30:00                 | 표시       | 없음                    |
| 예              | 00:29:59                 | 숨김       | 8월 24 ~ 30일 연장 혜택 |
| 예              | 00:30:00                 | 숨김       | 8월 24 ~ 30일 연장 혜택 |

**연장 저장 시각 × 조회 순서**

**고정 조건**

- `만료일까지 완주 = 예`
- `새 수령 = 없음`

연장 완료 시각을 00:30 앞뒤로 옮깁니다. **아직 검증하지 않은 확인 항목**이며, 지연 중 광고 노출을 허용할지는 규칙 확인이 필요합니다.

| 입력: 연장 완료 시각 | 입력: 조회가 읽은 연장 | 행위: 8월 24일 조회 시각 | 결과: 확인할 광고 표시     |
| -------------------- | ---------------------- | ------------------------ | -------------------------- |
| 00:29:59             | 있음                   | 00:30:00 조회            | 연장 혜택으로 계속 숨김    |
| 00:30:00             | 없음 · 저장 전 조회    | 00:30:00 조회            | 기존 유예 종료로 표시 가능 |
| 00:30:00             | 있음 · 저장 후 조회    | 00:30:00 조회            | 연장 혜택으로 숨김         |
| 00:30:01             | 없음 · 저장 전 조회    | 00:30:00 조회            | 기존 유예 종료로 표시 가능 |
| 00:30:01             | 있음 · 저장 후 조회    | 00:30:02 조회            | 연장 혜택으로 다시 숨김    |

**새 수령 여부 × 뒤늦은 자동 연장**

**고정 조건**

- `만료일까지 완주 = 예`
- `자동 연장 = 지연`

새 수령을 허용한 기대 기준으로 **8월 24일 00:10 수령 → 00:10:01 자동 연장** 순서를 추가 검증합니다.

| 입력: 새 수령 완료  | 행위                        | 결과: 기대·확인할 규칙                                                      |
| ------------------- | --------------------------- | --------------------------------------------------------------------------- |
| 아니요              | 8월 24일 00:10:01 자동 처리 | 기존 완주분을 연장                                                          |
| 예 · 8월 24일 00:10 | 8월 24일 00:10:01 자동 처리 | 이미 수령한 완주분으로 중복 제공하지 않음. 지연된 연장을 건너뛸지 규칙 확인 |

00:30에 도달했다고 언제나 광고가 나오는 것은 아닙니다. **그전에 연장되거나 새 리워드를 받았다면 새로 적용된 기간을 확인**해야 합니다. 반대로 시계만 00:30 직전으로 고정하면 자동 처리 지연이나 저장 순서 때문에 생기는 차이를 놓칠 수 있습니다.

특히 유예 안의 새 수령을 허용한다는 기대는 뒤늦은 자동 연장과 연결됩니다. 수령 화면의 응답뿐 아니라 **혜택이 중복으로 생기지 않는지, 실제 적용 기간이 무엇인지**까지 함께 확인할 항목으로 남겼습니다.

### 조합해서 보니 확인할 문제가 세 가지 남았습니다

앞의 매트릭스에서 드러난 차이를 모았습니다. 아래는 테스트 입력표가 아니라, 서비스 규칙과 맞춰 볼 문제의 요약입니다.

| 확인할 변수           | 비교할 값                                   | 분석에서 드러난 차이                     |
| --------------------- | ------------------------------------------- | ---------------------------------------- |
| 완주 방식             | 23일 직접 완주 / 24일에 23일 자동 보완      | 수령 기한이 8월 31일 / 9월 1일로 달라짐  |
| 완주 날짜와 처리 순서 | 30일 만료 / 31일 자동 처리 뒤 00:10 완주    | 연장 완료 안내가 나오지만 실제 연장 없음 |
| 수령 당일 직접 출석   | 오늘 직접 완주 / 어제 출석을 오늘 자동 보완 | 수령 후 출석권 획득 가능 여부가 달라짐   |

- **완주일을 어느 날짜로 정하는가:** 출석으로 인정한 23일을 기준으로 할지, 서버가 처리를 끝낸 24일을 기준으로 할지 정해야 합니다.

- **광고를 숨기는 30분을 연장 자격에도 적용하는가:** 추가한 네 테스트에서는 만료일 다음날 새로 완주한 사용자를 수령 대기로 판단하도록 기대 결과를 정했습니다. 정상 완주자라도 아직 연장 기록이 없다면, 광고가 숨겨진다는 이유만으로 연장 대기라고 판단하지 않도록 정리했습니다.

- **출석권 획득에 오늘의 직접 출석 기록이 필요한가:** 자동 출석은 어제의 결석을 채운 기록이므로, 오늘 직접 출석한 기록과 다르게 취급됩니다. 두 사용자에게 같은 획득 기회를 줄 것인지 확인해야 합니다.

## 결과

고정 조건을 표 밖에 적고, 바꿔 볼 변수를 입력 열로 나눈 매트릭스를 만들었습니다. 경계 직전과 직후를 인접한 행에 놓으니 어떤 값을 바꿨을 때 결과가 달라지는지 비교하기 쉬워졌습니다. 출석 6일과 7일처럼 하나의 변수로 보이는 차이부터 시작해, 수령 여부·만료 시각·처리 순서를 함께 놓고 살펴봤습니다.

그 결과 다음 차이를 찾았습니다.

- 자동 출석으로 완주하면 수령 기한이 하루 늘어납니다.
- 연장 완료 안내와 실제 연장 처리가 다를 수 있습니다.
- 완주 방식에 따라 수령 당일 출석권 획득 가능 여부가 달라집니다.

유예 시간은 별도 절로 묶어 광고 표시와 수령·연장 자격을 분리한 네 가지 기대 결과를 정리했습니다. 추가 검증 대상으로는 다음을 남겼습니다.

- 유예 종료 시점에도 완주하지 못한 사용자
- 자동 연장이 유예 종료 전후에 완료되는 경우
- 새 수령 후 뒤늦게 자동 연장이 실행되는 경우

실제 수정과 자동화 테스트 결과는 아직 확인하지 않았습니다. 수령 기한과 출석권 획득에서 남은 규칙을 기획과 확인하고, 이번 기대 결과와 이틀 늦게 수령했던 최초 사례를 함께 테스트로 남기려고 합니다.

테스트에서는 다음 결과를 함께 확인할 계획입니다.

- 사용자에게 나가는 안내
- 출석 일수
- 사용하거나 얻은 출석권 수
- 실제 혜택의 시작일과 만료일

어떤 조건을 바꿨을 때 무엇이 달라져야 하는지 먼저 적으니, 테스트할 상황과 아직 결정하지 않은 규칙을 구분할 수 있었습니다.
