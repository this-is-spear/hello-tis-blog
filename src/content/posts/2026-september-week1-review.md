## 이번 주의 작업: MVP 플랫폼을 만들며 책임과 실행 단위를 나눴다

사내에서 MVP를 쉽게 검증할 수 있는 플랫폼을 구상하고 있다. 서버 구성과 공통 요소 연동은 AI에게 맡기고, 나는 공통 보안 가이드라인과 플랫폼 운영을 담당하는 구조다. 이번 주에는 첫 단계로 개인 홈 서버에서 사용할 플랫폼을 만들고 있다.

사용 흐름은 세 단계로 좁혔다.

1. **프로젝트 생성**: GitHub으로 로그인하고, 프로젝트 이름을 입력해 FastAPI 템플릿 기반의 비공개 저장소를 만든다.
2. **Preview 배포**: main에 코드를 push하면 빌드와 테스트를 거쳐 프로젝트별 고정 Preview URL에 반영한다.
3. **상태 확인**: 포털에서 접근 권한이 있는 프로젝트와 배포 이력을 확인한다.

첫 범위는 FastAPI와 main 기준의 고정 Preview URL로 잡았다. PR별 Preview, Production 승격, 다른 언어의 템플릿은 후속 범위로 뒀다. 현재 구현 범위와 구조는 [GitHub 기반 내부 MVP 플랫폼 구현 이슈](https://github.com/this-is-spear/hello-mvp-sandbox/issues/4)에 정리하고 있다.

### 문제가 생겼을 때 살펴볼 범위를 좁히려고 책임을 나눴다

구현하면서 시스템을 기능별로 묶어보면 어떨까 생각했다. 사용자 요청을 받아 프로젝트를 관리하는 플랫폼과, 코드를 빌드하고 배포하는 워커는 서로 다른 책임을 가진다. 이 둘을 독립적으로 구성하면 문제가 생겼을 때 확인하고 대응할 범위도 좁힐 수 있겠다고 봤다.

분리 기준은 실행 조건으로 잡았다. 어떤 입력으로 시작하는지, 어떤 권한이 필요한지, 얼마나 오래 실행되는지, 실패하면 어떻게 대응해야 하는지를 봤다. 워커는 빌드 시간이 길고 Docker 접근 권한이 필요하다. 배포가 실패해도 기존 Preview는 유지해야 한다. 사용자 요청을 처리하는 API와 다른 실행 단위로 둘 이유가 있었다.

| 구분        | 책임                                              |
| ----------- | ------------------------------------------------- |
| 접근        | HTTPS와 호스트별 라우팅                           |
| 사용자 포털 | 로그인, 세션, 화면, 사용자 권한 확인              |
| 플랫폼 제어 | 프로젝트 생성, 저장소 연동, 배포 요청과 상태 관리 |
| 변경 감지   | Webhook·Poller로 변경을 확인하고 작업 등록        |
| 배포 실행   | 작업 획득, 빌드, 테스트, 교체, 복구               |
| 서비스 실행 | 생성된 MVP 실행과 프로젝트 데이터 유지            |
| 상태 저장   | 프로젝트·배포·작업 이력 보존                      |

이 책임에 맞춰 프로젝트 폴더를 구분해서 관리하려 했다. 다만 폴더를 나누는 것만으로 장애가 분리되지는 않는다. 코드에서 책임을 구분하는 것과 실행 환경에서 영향을 분리하는 것은 별도로 봐야 한다.

현재 사용자 포털과 플랫폼 제어는 같은 API 프로세스에 두고, 워커는 별도 프로세스로 둔다. 변경 감지와 배포 실행 사이에는 PostgreSQL 기반의 영속 작업 큐를 둬 Worker가 중단돼도 등록된 작업이 남도록 한다. 같은 서버와 Docker를 공유하므로 호스트 장애의 영향까지 분리되는 구조는 아니다.

## 이번 주의 공부: IO 대기를 줄일 방법은 병목과 변경 비용을 보고 고른다

7장은 네트워크 IO와 자원 효율, 가상 스레드, 논블로킹 IO를 다룬다. 기억할 내용은 세 가지다.

- 블로킹 IO에서는 입출력이 끝날 때까지 스레드가 기다린다. 동시 요청을 처리하려고 플랫폼 스레드를 계속 늘리면 메모리와 스케줄링 비용도 고려해야 한다.
- 가상 스레드는 IO 대기가 많은 작업에서 동시성과 처리량을 높이는 수단이다. CPU 중심 작업의 실행 속도를 높여주는 것은 아니다. ([OpenJDK JEP 444](https://openjdk.org/jeps/444))
- 논블로킹 IO는 입출력이 끝날 때까지 스레드를 붙잡아 두지 않는 방식이다. 어떤 수단을 쓸지는 네트워크 IO가 실제 병목인지, 구현을 얼마나 바꿀 수 있는지부터 확인한다.

[지난주 CDC 실험](/posts/2026-august-week4-review)에서는 CPU 프로파일에 보이는 파싱 비용만으로 병목을 설명할 수 없었다. 대기 시간과 컨슈머 병렬성을 함께 확인했을 때 가장 큰 개선이 나왔다. 이번 장도 성능을 볼 때 실행 중인 코드뿐 아니라 기다리는 시간과 자원 사용 방식을 함께 살펴봐야 한다는 내용으로 이어졌다.

## 마무리하며

이번 주에는 MVP 플랫폼 구상을 개인 홈 서버의 구현으로 옮기면서 시스템의 책임을 구분해봤다. 이후 문제가 생겼을 때 무엇을 확인하고 어디까지 수정해야 하는지 알 수 있는 구조를 만들고 싶었다.

다음에도 구성 요소를 나눌 때는 입력, 권한, 실행 시간, 실패 대응을 기준으로 본다. 폴더의 경계와 프로세스의 경계도 구분한다. 성능을 개선할 때는 IO가 실제 병목인지 확인한 뒤 자원 효율과 구현 변경 비용을 함께 따진다.
