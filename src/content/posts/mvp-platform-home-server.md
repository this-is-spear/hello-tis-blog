## 사내 적용을 위한 빌드업

### 상황

개인 홈 서버에서 프로젝트 생성과 배포를 연결했다. 다음 목표는 개발 경험과 관계없이 허용된 내부 데이터로 서비스를 만들고, 동료들과 테스트할 수 있는 사내 플랫폼이다. 보안 조건을 공통 기능으로 제공해 반복되는 준비와 검토를 줄이고 싶다.

### 원인

자동 배포와 회사 데이터의 사용 권한은 별개다. 사용자·앱의 접근 권한과 외부 AI·로그로 전달될 정보를 확인해야 한다. [NIST의 Zero Trust 원칙](https://csrc.nist.gov/pubs/sp/800/207/final)도 네트워크 위치만으로 신뢰를 부여하지 않는다.

현재 구현은 코드의 실행과 배포가 중심이다. 비개발자의 코드 수정에는 AI 도구와 사용 안내를 연결해야 한다. 내가 매번 대신 처리하면 내 지원을 기다리는 일이 새 병목이 될 수 있다.

### 해결

아래는 아직 실행하지 않은 파일럿 계획이다.

1. **첫 업무와 담당자를 정한다.** 한 팀의 반복 업무를 관찰하고 필요한 데이터와 대기 시간을 확인한다. 만드는 사람·쓰는 사람·도입 결정자의 요구를 듣고, 리더와 역할·배정 시간·지원 책임을 합의한다.
2. **실제 데이터 사용 전에 조건을 정한다.** 보안·데이터·인프라 담당자와 접근·회수 권한, 보존·삭제, 앱 격리와 통신, AI 전송·기록 범위를 합의한다. 표준 범위는 재사용하고 예외는 담당자가 검토한다.
3. **기존 도구와 비교한다.** 회사 기반에 필요한 흐름을 추가하는 방법과 홈 서버 구현을 적용하는 방법을 같은 업무로 비교한다. 준비 시간과 지원·유지 비용을 보고 개발 범위를 정한다.
4. **수정과 테스트를 반복한다.** 합성 데이터로 통제를 점검한 뒤 승인된 실제 데이터로 검증한다. 미허용 접근과 권한 회수 후 접근 차단, 대표·예외 업무 사례를 확인한다. 두 번째 수정·배포는 사용자가 직접 수행하고 지원 시간을 기록한다.
5. **사용을 확인하고 넓힌다.** 첫 테스트까지의 시간, 활성 환경과 반복 사용, 오류·재작업을 도입 전후로 비교한다. 효과와 사용자 자립이 확인되면 다음 팀으로 넓히고, 지원 부담이 크면 범위를 조정한다.

운영 전환은 회사의 기존 승인·운영 절차를 따른다. 공통 승인 파이프라인과 운영 자동화는 전환 사례와 반복 수요가 쌓인 뒤 검토한다.

### 결과

아직 사내 도입이나 효과를 확인하지 않았다. 먼저 리더와 첫 사용자, 보안·데이터 담당자를 만나 파일럿 범위와 성공·중단 기준을 정하려 한다.

보안 요구를 사용 가능한 환경으로 만들고 정착시키는 경험을 쌓고 싶다. 문제 선정부터 검증·인계까지 내가 맡은 일과 동료의 기여를 남기고, 성과는 실제 사용과 측정 결과로 기록하겠다.

## 개인 홈 서버 구현

### 상황

아이디어를 시험할 때마다 실행 환경을 준비하는 일을 반복하지 않도록, 개인 홈 서버에 공통 실행 기반을 만들었다.

### 원인

코드를 작성한 뒤에도 실행 준비, 변경 반영, 실패 처리가 필요했다. 프로젝트마다 이 일을 직접 챙기면 실험이 늘수록 내 지원도 늘어난다. 반복되는 절차를 플랫폼이 맡도록 정리했다.

### 해결

사용자는 프로젝트를 만들고 코드를 수정한 뒤, 같은 주소에서 실행 결과를 확인한다. 플랫폼은 그 사이의 일을 맡는다.

- **실행 준비:** 프로젝트를 시작하는 데 필요한 공통 구성을 제공한다.
- **변경 반영:** 바뀐 코드가 실행 조건을 만족하는지 검사하고, 통과한 결과를 미리보기 환경에 반영한다.
- **상태 확인과 복구:** 진행 상황과 실패 이력을 보여준다. 실패한 단계에 따라 기존 실행 상태를 유지하거나 이전 정상 상태로 복구를 시도한다.

사용자 요청을 받는 일과 변경을 반영하는 일을 분리해, 오래 걸리는 작업이 다른 요청을 막지 않도록 했다. 세부 구현과 검증 기록은 [구현 PR](https://github.com/this-is-spear/hello-mvp-sandbox/pull/2)에 남겼다.

### 결과

프로젝트를 시작하고 수정한 결과를 사용해보는 흐름을 연결했다. 준비 시간과 내 개입이 줄었는지는 아직 측정하지 않았다. 현재는 서버 한 대의 미리보기 환경이며, 변경을 반영하는 동안 중단이 생길 수 있다. 복구·사내 보안 기준의 검증과 여러 버전 비교, 정식 운영 전환은 후속 과제다.
