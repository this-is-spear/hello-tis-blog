## 상황

아이디어를 시험하기 전에 인프라 준비와 보안 검토를 기다리는 일이 부담스러웠다. 준비는 아이디어가 살아남든 버려지든 매번 반복됐다.

이 준비를 줄일 수 있는지 확인하려고 MVP 플랫폼을 만들기 시작했다. 1단계로 개인 홈 서버에서 프로젝트를 만들고, 코드를 바꾸고, 실행 결과를 확인하는 흐름을 연결했다.

사내에서 활용할 목표와 도입 순서는 [홈 서버 실험을 사내 개발 플랫폼으로 가져가려면](/posts/internal-development-platform-adoption)에 따로 정리했다. 여기서는 개인 홈 서버에 구현한 흐름을 기록한다.

## 원인

처음에는 서버 구성을 AI에게 맡기면 준비가 줄어들 것이라고 생각했다. 하지만 생성한 코드를 어떤 절차로 배포하고, 실패하면 어떻게 복구할지도 정해야 했다. 이 판단을 프로젝트마다 반복하면 운영자인 내가 계속 개입하게 된다.

그래서 공통 템플릿과 배포 절차를 두고, 개발자나 AI가 만든 코드에 같은 확인 기준을 적용하기로 했다.

## 해결

### 프로젝트 생성부터 Preview 확인까지 연결했다

첫 범위는 FastAPI 서비스와 기본 브랜치 기준의 고정 Preview 주소로 좁혔다. Preview는 배포한 결과를 직접 사용해보는 미리보기 환경이다.

1. GitHub으로 로그인하고 프로젝트 이름을 입력하면, 플랫폼이 템플릿을 바탕으로 비공개 저장소를 만든다.
2. 개발자나 AI가 코드를 수정해 기본 브랜치에 반영하면, 플랫폼이 변경을 감지해 빌드·테스트·배포를 진행한다.
3. 첫 배포가 성공하면 Preview에 접속할 수 있다. 이후에는 같은 주소에서 변경한 결과를 확인한다.

포털에서는 자신에게 권한이 있는 프로젝트와 배포 상태를 확인한다. PR별 Preview와 정식 운영 환경으로의 승격은 후속 범위로 남겼다.

### 오래 걸리는 배포 작업을 분리했다

사용자 요청을 처리하는 일과 배포 작업을 별도로 실행하도록 나눴다. 변경 감지는 배포할 작업을 등록하고, 배포를 맡은 워커가 이를 가져와 실행한다. 배포 상태와 실패 이력은 저장해 포털에서 확인할 수 있게 했다.

이렇게 나누면 워커가 멈춰도 사용자 요청 처리와 이미 실행 중인 Preview를 유지할 수 있다. 다만 개인 서버 한 대에서 검증하는 범위여서 서버 자체의 장애를 견디는 구조까지 갖춘 것은 아니다.

### 실패했을 때의 처리도 정했다

- 빌드나 테스트가 실패하면 기존 Preview를 유지한다.
- 새 버전의 정상 동작을 확인하지 못하면 이전 정상 버전으로 복구를 시도한다.
- 버전을 교체하는 동안에는 중단이 생길 수 있다. 무중단 배포를 보장하지는 않는다.

세부 구현과 자동 테스트, 외부 접속 확인 결과는 [구현 PR](https://github.com/this-is-spear/hello-mvp-sandbox/pull/2)에 남겼다.

## 결과

개인 홈 서버에서 프로젝트 생성부터 Preview 자동 배포까지 연결했다. 서버 구성을 자동화하려다 보니, 실행 조건과 실패 처리까지 공통 절차로 정하는 일이 함께 필요했다.

아직 준비 시간이 얼마나 줄었는지, 운영자의 개입이 줄었는지는 확인하지 못했다. 다음에는 아래를 확인하려 한다.

- 프로젝트 생성부터 첫 Preview 확인까지 걸리는 시간과 운영자 개입 횟수.
- 장애가 났을 때 서비스와 데이터를 복구할 수 있는지.
- 사용자 권한과 사내 보안 기준을 일관되게 적용하고 자동으로 확인할 수 있는지.
