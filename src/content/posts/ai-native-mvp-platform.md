## 아이디어를 실행하기까지의 준비를 줄이고 싶었다

AI로 코드를 작성해도 실행 결과를 확인하기까지는 할 일이 남는다. 저장소를 만들고, 실행 환경을 준비하고, 테스트와 배포 방법을 정해야 한다. 아이디어를 하나 더 시험할 때마다 이 과정을 반복하면 코드 작성이 빨라진 만큼 검증도 빨라지지는 않는다.

처음 이 글에서는 인프라 준비와 보안 검토를 기다리는 시간을 병목으로 보고, 사내에서 MVP를 쉽게 검증할 수 있는 플랫폼을 구상했다. 반복되는 준비를 공통 기능으로 옮기면 제품을 만드는 사람은 아이디어를 구현하고 결과를 판단하는 데 집중할 수 있다고 생각했다. 다만 준비 시간이 실제로 얼마나 줄어드는지는 사용자를 받아 측정해야 한다.

그 첫 단계로 개인 홈 서버에서 **GitHub 프로젝트 생성부터 미리보기 환경인 Preview 배포까지** 연결했다. 사용자는 프로젝트 이름을 입력해 저장소를 만들고, 코드를 변경한 뒤 같은 Preview 주소에서 결과를 확인한다. 플랫폼은 변경 감지와 빌드, 테스트, 배포, 상태 기록을 맡는다.

이 글은 시연 영상의 사용 흐름을 먼저 살펴보고, 그 흐름을 지원하는 구현을 설명한다. 영상은 9월 4일의 첫 시연이며, 실행 단위 분리와 배포 복구는 이후 구현한 내용까지 반영했다.

### 1. GitHub으로 로그인하고 프로젝트를 만든다

영상 앞부분에서는 GitHub 인증을 마친 뒤 프로젝트 목록으로 돌아온다. 목록에는 각 프로젝트의 상태와 저장소 주소, Preview 주소가 함께 표시된다. 사용자는 자신에게 저장소 접근 권한이 있는 프로젝트를 확인한다.

**약 0:27부터** 프로젝트 이름에 `third-test`를 입력한다. 이어서 열린 GitHub 저장소에는 FastAPI 템플릿의 소스 코드와 테스트, Dockerfile이 들어 있다. 플랫폼이 GitHub Template Repository를 이용해 비공개 저장소를 생성하므로 사용자가 이 파일들을 처음부터 준비할 필요가 없다.

저장소 생성과 서비스 실행은 서로 다른 단계다. 프로젝트 이름과 Preview 주소를 받았어도 첫 배포가 끝나기 전에는 애플리케이션을 사용할 수 없다.

### 2. 프로젝트 상세에서 배포가 진행되는 과정을 확인한다

**약 0:45의 상세 화면**에는 `Recent deployments`와 `Recent events`가 보인다. 배포 목록은 어떤 커밋을 대상으로 작업하는지 보여주고, 이벤트 목록은 그 작업이 어디까지 진행됐는지 보여준다.

처음에는 프로젝트 생성 요청, 저장소 생성, Webhook 수신, 배포 큐 등록 같은 이벤트가 쌓인다. **약 1:33에는** 워커의 작업 획득과 빌드·테스트·배포 시작 이벤트가 추가된다. 화면에서는 최신 이벤트가 위에 놓이므로 아래에서 위로 읽으면 처리 순서를 따라갈 수 있다.

| 영상에 표시된 이벤트                     | 의미                                               |
| ---------------------------------------- | -------------------------------------------------- |
| `REPOSITORY_CREATED`                     | 템플릿을 바탕으로 GitHub 저장소를 만들었다.        |
| `DEPLOYMENT_QUEUED`                      | 배포할 작업을 대기열에 등록했다.                   |
| `WORK_ITEM_CLAIMED`                      | 워커가 대기 중인 작업을 가져갔다.                  |
| `BUILD_STARTED` · `TEST_STARTED`         | 실행할 이미지를 만들고 테스트하는 단계에 들어갔다. |
| `DEPLOY_STARTED`                         | Preview에 반영하는 단계에 들어갔다.                |
| `PREVIEW_READY` · `DEPLOYMENT_SUCCEEDED` | 실행 준비 확인과 배포가 완료됐다.                  |

이벤트는 성공 여부뿐 아니라 기다리는 위치를 알려준다. 작업이 등록된 채 대기하는지, 빌드 중인지, Preview를 준비하는 중인지 구분할 수 있어야 사용자가 상태를 확인하려고 운영자에게 매번 물어보지 않아도 된다.

### 3. Preview 주소에서 실제 응답을 확인한다

**약 1:45에는** `PREVIEW_READY`와 `DEPLOYMENT_SUCCEEDED`가 표시된다. 마지막에는 Preview 링크를 열어 템플릿 애플리케이션의 JSON 응답을 확인한다. 프로젝트를 생성한 결과가 저장소에만 남지 않고 접속할 수 있는 서비스로 이어진 장면이다.

영상은 템플릿의 첫 배포를 보여준다. 이후 코드를 수정할 때도 같은 배포 절차를 사용한다. 개발자나 AI 에이전트가 생성된 저장소의 `main`에 커밋을 push하면 플랫폼이 변경을 감지하고, 검증을 통과한 결과를 같은 Preview 주소에 반영한다. 코드 수정과 재배포, 실패 복구는 아래 구현 설명에서 다룬다.

## main의 변경을 실행 결과로 연결하기

사용자가 코드를 반영한 뒤에는 변경 감지와 배포 실행이 이어진다. GitHub 이벤트를 받는 요청 안에서 오래 걸리는 빌드까지 처리하지 않도록, 두 작업 사이에 PostgreSQL 작업 큐를 뒀다.

### Webhook으로 감지하고 Poller로 누락을 보완한다

GitHub이 Push Webhook을 보내면 수신기는 서명을 검증하고 관리 대상 저장소의 `main` 변경인지 확인한다. 배포 대상이면 프로젝트와 커밋 SHA를 작업 큐에 기록한다. 워커는 이 SHA로 지정된 코드를 가져오므로, 작업을 기다리는 동안 새 커밋이 생겨도 배포 대상이 바뀌지 않는다.

Webhook을 놓쳤을 때를 위해 Poller도 둔다. Poller는 주기적으로 GitHub의 최신 `main` 커밋을 조회해 아직 처리하지 않은 변경을 찾는다. 같은 프로젝트와 커밋 SHA는 하나의 배포로 기록해 두 경로가 같은 변경을 발견해도 중복 배포가 생기지 않도록 했다.

### 빌드와 테스트를 통과한 이미지를 Preview에 반영한다

워커는 작업 큐에서 작업을 가져와 다음 순서로 처리한다.

1. 지정된 커밋의 소스 코드를 가져온다.
2. Docker 이미지를 빌드하고 템플릿의 pytest를 실행한다.
3. 새 버전의 실행 환경을 준비하고 Ready 엔드포인트로 실행 준비 상태를 확인한다.
4. 성공한 결과를 저장하고 프로젝트의 고정 Preview 주소로 연결한다.

첫 지원 범위를 FastAPI로 좁힌 이유도 여기에 있다. 실행 방법과 테스트 방법, 준비 상태를 확인하는 방법을 공통으로 정해야 자동 배포의 판단 기준을 만들 수 있다. AI 에이전트가 수정한 코드도 이 절차를 거친다. 플랫폼 안에서 자연어 요청을 받아 코드를 생성하는 기능은 현재 구현 범위에 포함하지 않았다.

## 오래 걸리는 작업과 사용자 요청의 실행 단위를 나누기

현재 Compose 구성은 포털, 제어 API, Webhook 수신기, Poller, 워커, PostgreSQL을 각각 실행한다. 프로젝트의 Preview 컨테이너는 별도로 실행한다. 처음 글에서 포털·제어 API·Webhook 수신기를 하나의 실행 단위로 설명했던 부분은 이후 구현에 맞춰 갱신했다.

| 실행 단위                           | 책임                                                          |
| ----------------------------------- | ------------------------------------------------------------- |
| 포털 (`portal`)                     | GitHub 로그인과 세션, 프로젝트 화면을 제공한다.               |
| 제어 API (`control-api`)            | 프로젝트와 저장소를 만들고 배포 상태와 이력을 관리한다.       |
| Webhook 수신기 (`webhook-receiver`) | GitHub의 변경 알림을 검증하고 작업을 등록한다.                |
| Poller (`poller`)                   | GitHub을 주기적으로 조회해 누락된 변경을 찾는다.              |
| 워커 (`worker`)                     | 소스를 가져와 빌드·테스트하고 Preview 교체와 복구를 수행한다. |
| PostgreSQL (`postgres`)             | 프로젝트 상태, 배포·이벤트 이력, 작업 큐를 보존한다.          |
| 프로젝트별 Preview                  | 사용자가 만든 FastAPI 애플리케이션을 실행한다.                |

Nginx Proxy Manager는 HTTPS 접속과 호스트 이름에 따른 라우팅을 맡는다. 플랫폼 구성 요소 중 Docker 소켓은 워커에만 연결한다. 사용자 화면이나 Webhook 수신기가 직접 컨테이너를 조작할 필요가 없기 때문이다.

작업을 데이터베이스에 보존하면 워커가 중단돼도 대기 작업은 남는다. 워커는 작업을 가져갈 때 유효 시간이 있는 처리 권한을 받고, 처리 중에는 heartbeat로 이를 갱신한다. 작업 완료 시에도 해당 권한을 확인해 이미 만료된 워커가 뒤늦게 결과를 덮어쓰지 않도록 했다.

실행 단위를 나눠도 의존성이 모두 사라지는 것은 아니다. 포털은 제어 API에 의존하고 여러 구성 요소가 PostgreSQL을 공유한다. 모든 서비스가 한 서버와 Docker 데몬에서 동작하므로 호스트 장애는 전체에 영향을 준다.

## 실패한 변경에서 서비스와 데이터를 복구하기

자동 배포에서는 성공 경로만큼 실패한 뒤 무엇을 남길지도 중요했다. 빌드 실패와 Preview 교체 중 실패는 이미 변경한 대상이 다르므로 대응도 나눴다.

| 실패한 단계             | 처리                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| 빌드·테스트             | Preview 교체를 시작하지 않고 실패 이력을 남긴다. 기존 정상 Preview는 계속 실행된다.              |
| Preview 교체·Ready 확인 | 이전 정상 이미지와 데이터 볼륨, 라우트로 복구를 시도한다. 복구 자체가 실패하면 그 이력도 남긴다. |
| 워커 실행 중단          | 시작 시점과 작업이 없는 시점의 복구 점검에서 중단된 배포를 정리한다.                             |

데이터도 컨테이너 밖에 보존해야 한다. 현재 템플릿은 앱의 `/data`에 SQLite 데이터와 파일을 저장할 수 있고, 배포 시 이전 데이터 볼륨을 새 세대의 볼륨으로 복제한다. 새 버전의 준비 확인이 실패하면 이전 이미지와 변경되지 않은 이전 데이터로 돌아갈 수 있게 한 것이다.

이 교체 방식은 상태를 가진 애플리케이션을 다시 띄우는 `Recreate` 방식이다. 교체 과정에는 중단이 생길 수 있으며, 복구 실패도 가능하다. 또한 배포 실패에 대비해 이전 볼륨을 남기는 것과 서버 장애에 대비한 백업은 별개다. PostgreSQL과 프로젝트 데이터의 자동 백업·복원은 후속 과제로 남아 있다.

## 배운 점과 다음 검증

현재는 FastAPI 저장소의 `main`을 프로젝트별 고정 Preview 주소에 배포한다. PR별 Preview와 정식 운영 승격, 다른 런타임 지원, 사내 보안 기준 적용은 후속 과제다.

자동 배포를 구현하며 실행 조건과 실패 시 복구 기준도 함께 정해야 한다는 점을 배웠다. 다음에는 첫 Preview까지 걸리는 시간과 운영자 개입 횟수를 측정하고, 사용자가 수정과 재배포를 직접 이어갈 수 있는지 확인하려 한다.
