## 아이디어를 실행하기까지의 준비를 줄이고 싶었다

AI로 코드를 작성해도 실행 결과를 확인하기까지는 할 일이 남는다. 저장소를 만들고, 실행 환경을 준비하고, 테스트와 배포 방법을 정해야 한다. 아이디어를 하나 더 시험할 때마다 이 과정을 반복하면 코드 작성이 빨라진 만큼 검증도 빨라지지는 않는다.

처음 이 글에서는 인프라 준비와 보안 검토를 기다리는 시간을 병목으로 보고, 사내에서 MVP를 쉽게 검증할 수 있는 플랫폼을 구상했다. 반복되는 준비를 공통 기능으로 옮기면 제품을 만드는 사람은 아이디어를 구현하고 결과를 판단하는 데 집중할 수 있다고 생각했다. 다만 준비 시간이 실제로 얼마나 줄어드는지는 사용자를 받아 측정해야 한다.

그 첫 단계로 개인 홈 서버에서 **GitHub 프로젝트 생성부터 미리보기 환경인 Preview 배포까지** 연결했다. 사용자는 프로젝트 이름을 입력해 저장소를 만들고, 코드를 변경한 뒤 같은 Preview 주소에서 결과를 확인한다. 플랫폼은 변경 감지와 빌드, 테스트, 배포, 상태 기록을 맡는다.

## 프로젝트 생성부터 첫 실행까지

사용자는 다음 과정을 거쳐 첫 실행 결과를 확인한다.

1. GitHub으로 로그인해 프로젝트 목록에 들어간다.
2. 프로젝트 이름을 입력하고, 생성된 저장소의 기본 코드를 확인한다.
3. 프로젝트 상세에서 배포 진행 상황과 이벤트를 확인한다.
4. 배포가 끝나면 Preview 주소를 열어 애플리케이션의 응답을 확인한다.

### 1. GitHub으로 로그인하고 프로젝트를 만든다

GitHub으로 로그인하면 프로젝트 목록에서 상태와 저장소 주소, Preview 주소를 확인할 수 있다. 포털은 로그인한 사용자의 GitHub 저장소 접근 권한을 확인해 목록을 구성하고, 상세 화면을 열 때도 권한을 다시 확인한다.

프로젝트 이름을 입력하면 GitHub Template Repository를 바탕으로 비공개 저장소를 만든다. 저장소에는 FastAPI 기본 코드와 테스트, Dockerfile이 준비돼 있어 사용자는 아이디어 구현부터 시작할 수 있다.

저장소 생성과 서비스 실행은 서로 다른 단계다. `PROJECT_READY`는 프로젝트 생성이 끝났다는 뜻이고, 애플리케이션에 접속하려면 첫 배포의 실행 준비 확인까지 끝나야 한다.

### 2. 프로젝트 상세에서 배포가 진행되는 과정을 확인한다

`Recent deployments`에서는 배포 대상 커밋과 생성 시각을 확인한다. `Recent events`에는 이벤트 발생 시각, 종류, 심각도, 메시지가 표시돼 프로젝트 생성부터 빌드·테스트·배포까지 진행 상황과 실패 단계의 요약 메시지를 확인할 수 있다.

이벤트는 API, 변경 감지기, 워커가 처리 과정에서 남기는 기록이다. 주요 이벤트를 역할별로 정리하면 다음과 같다.

| 구분          | 이벤트                                                              | 기록하는 내용                                                                        |
| ------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 프로젝트 생성 | `PROJECT_CREATE_REQUESTED` · `REPOSITORY_CREATED` · `PROJECT_READY` | 생성 요청, 템플릿 저장소 생성, 프로젝트 준비 완료를 각각 기록한다.                   |
| GitHub 알림   | `WEBHOOK_RECEIVED` · `WEBHOOK_IGNORED`                              | 서명을 검증한 알림을 수신했거나, 배포 대상이 아닌 알림을 제외했다.                   |
| 변경 조회     | `COMMIT_OBSERVED`                                                   | Poller가 `main`의 변경을 발견했다. 관측 기록만으로 새 배포가 등록됐다는 뜻은 아니다. |
| 작업 등록     | `DEPLOYMENT_QUEUED`                                                 | 특정 커밋 SHA의 배포 작업을 대기열에 등록했다.                                       |
| 작업 획득     | `WORK_ITEM_CLAIMED`                                                 | 워커가 작업의 처리 권한을 얻었다.                                                    |
| 단계 시작     | `BUILD_STARTED` · `TEST_STARTED` · `DEPLOY_STARTED`                 | 이미지 빌드, 테스트, Preview 배포 단계에 각각 들어갔다.                              |
| 배포 성공     | `PREVIEW_READY` · `DEPLOYMENT_SUCCEEDED`                            | 새 Preview의 실행 준비 확인과 배포 처리를 완료했다.                                  |
| 생성 실패     | `REPOSITORY_CREATE_FAILED` · `PROJECT_PROVISION_FAILED`             | 저장소 생성 또는 이후 프로젝트 준비 과정에서 문제가 발생했다.                        |
| 실행 실패     | `BUILD_FAILED` · `TEST_FAILED` · `DEPLOY_FAILED`                    | 실패한 단계와 요약 메시지를 기록한다.                                                |
| 복구 결과     | `ROLLBACK_SUCCEEDED` · `ROLLBACK_FAILED`                            | 이전 정상 버전으로 복구했거나, 복구하지 못했다.                                      |

이 표는 이벤트의 역할을 묶은 것이다. Webhook과 Poller가 별도로 동작하므로 모든 배포에 같은 이벤트가 같은 순서로 쌓이지는 않는다. 작업 등록 여부는 `DEPLOYMENT_QUEUED`, 실제 실행 시작은 `WORK_ITEM_CLAIMED`와 단계 시작 이벤트로 구분한다.

프로젝트의 현재 상태는 `ProjectStatus`로 관리한다. 이벤트가 **어떤 일이 있었는지**를 남긴다면, 상태는 **지금 어느 단계인지**를 나타낸다. 구현에 정의된 상태와 허용 전이는 다음과 같다.

![프로젝트 생성, 빌드, 테스트, 배포와 실패·복구 경로를 나타낸 프로젝트 상태 머신](../../assets/images/ai-native-mvp-platform/deployment-state-machine.svg)

- 기본 흐름은 `CREATING → CREATED → BUILDING → TESTING → DEPLOYING → RUNNING`이다. 큐 대기는 별도 작업의 상태로 관리한다.
- 새 배포의 Ready 확인이 실패해도 이전 버전 복구에 성공하면 프로젝트는 `RUNNING`으로 돌아온다. 이때 내부에 기록되는 **이번 배포 시도의 결과는 `FAILED`**이다. 화면에서도 `RUNNING`만 보고 새 배포가 성공했다고 판단하지 않고, 실패와 복구 이벤트를 함께 확인해야 한다.
- 복구할 버전이 없거나 복구하지 못하면 `DEPLOY_FAILED`가 되고, 재시도 전에 운영자 개입이 필요하다. 복구 처리 중 예외가 발생한 경우에는 `FAILED`로 기록한다.

### 3. Preview 주소에서 실제 응답을 확인한다

배포가 완료되면 프로젝트의 Preview 주소를 열어 FastAPI 애플리케이션의 JSON 응답을 확인한다. 저장소의 코드가 실제로 접속할 수 있는 서비스까지 이어진 것이다.

플랫폼은 컨테이너 실행 뒤 Ready 엔드포인트로 준비 상태를 확인한다. 사용자는 Preview에서 실제 응답을 확인하며 구현한 기능이 의도대로 동작하는지 검증한다.

## main의 변경을 실행 결과로 연결하기

첫 실행을 확인한 뒤에는 생성된 저장소의 코드를 수정한다. 개발자나 AI 에이전트가 `main`에 커밋을 push하면 플랫폼이 변경을 감지하고, 검증을 통과한 결과를 같은 Preview 주소에 반영한다.

사용자가 코드를 반영한 뒤에는 변경 감지와 배포 실행이 이어진다. GitHub 이벤트를 받는 요청 안에서 오래 걸리는 빌드까지 처리하지 않도록, 두 작업 사이에 PostgreSQL 작업 큐를 뒀다.

### Webhook으로 감지하고 Poller로 누락을 보완한다

GitHub이 Push Webhook을 보내면 수신기는 서명을 검증하고 관리 대상 저장소의 `main` 변경인지 확인한다. 배포 대상이면 프로젝트와 커밋 SHA를 작업 큐에 기록한다. 워커는 이 SHA로 지정된 코드를 가져오므로, 작업을 기다리는 동안 새 커밋이 생겨도 배포 대상이 바뀌지 않는다.

Webhook을 놓쳤을 때를 위해 Poller도 둔다. Poller는 주기적으로 GitHub의 최신 `main` 커밋을 조회해 아직 처리하지 않은 변경을 찾는다. 같은 프로젝트와 커밋 SHA는 하나의 배포로 기록해 두 경로가 같은 변경을 발견해도 중복 배포가 생기지 않도록 했다.

### 빌드와 테스트를 통과한 이미지를 Preview에 반영한다

워커는 작업 큐에서 작업을 가져와 다음 순서로 처리한다.

1. 지정된 커밋의 소스 코드를 가져온다.
2. Docker 이미지를 빌드하고, 그 이미지로 임시 컨테이너를 띄워 템플릿의 pytest를 실행한다.
3. 새 버전의 실행 환경을 준비하고 Ready 엔드포인트로 실행 준비 상태를 확인한다.
4. 성공한 결과를 저장하고 프로젝트의 고정 Preview 주소로 연결한다.

빌드가 끝나면 이미지 ID를 기록하고 테스트와 배포에 같은 이미지를 사용한다. 소스가 같다는 가정에 기대어 다시 빌드하는 대신, 검증한 실행 결과물을 그대로 배포 대상으로 삼는다.

첫 지원 범위를 FastAPI로 좁힌 이유도 여기에 있다. 실행 방법과 테스트 방법, 준비 상태를 확인하는 방법을 공통으로 정해야 자동 배포의 판단 기준을 만들 수 있다. AI 에이전트가 수정한 코드도 이 절차를 거친다. 플랫폼 안에서 자연어 요청을 받아 코드를 생성하는 기능은 현재 구현 범위에 포함하지 않았다.

## 오래 걸리는 작업과 사용자 요청의 실행 단위를 나누기

현재 Compose 구성은 포털, 제어 API, Webhook 수신기, Poller, 워커, PostgreSQL을 각각 실행한다. 프로젝트의 Preview 컨테이너는 별도로 실행한다.

| 실행 단위                           | 책임                                                          |
| ----------------------------------- | ------------------------------------------------------------- |
| 포털 (`portal`)                     | GitHub 로그인과 세션, 프로젝트 화면을 제공한다.               |
| 제어 API (`control-api`)            | 프로젝트와 저장소를 만들고 배포 상태와 이력을 관리한다.       |
| Webhook 수신기 (`webhook-receiver`) | GitHub의 변경 알림을 검증하고 작업을 등록한다.                |
| Poller (`poller`)                   | GitHub을 주기적으로 조회해 누락된 변경을 찾는다.              |
| 워커 (`worker`)                     | 소스를 가져와 빌드·테스트하고 Preview 교체와 복구를 수행한다. |
| PostgreSQL (`postgres`)             | 프로젝트 상태, 배포·이벤트 이력, 작업 큐를 보존한다.          |
| 프로젝트별 Preview                  | 사용자가 만든 FastAPI 애플리케이션을 실행한다.                |

Nginx Proxy Manager는 HTTPS 접속과 호스트 이름에 따른 라우팅을 맡는다. 플랫폼 구성 요소 중 Docker 소켓은 워커에만 연결한다. 사용자 화면이나 Webhook 수신기가 직접 컨테이너를 조작할 필요가 없기 때문이다.

작업을 데이터베이스에 보존하면 워커가 중단돼도 대기 작업은 남는다. 워커는 작업을 가져갈 때 유효 시간이 있는 처리 권한을 받고, 처리 중에는 heartbeat로 이를 갱신한다. 작업 완료 시에도 해당 권한을 확인해 이미 만료된 워커가 뒤늦게 결과를 덮어쓰지 않도록 했다.

실행 단위를 나눠도 의존성이 모두 사라지는 것은 아니다. 포털은 제어 API에 의존하고 여러 구성 요소가 PostgreSQL을 공유한다. 모든 서비스가 한 서버와 Docker 데몬에서 동작하므로 호스트 장애는 전체에 영향을 준다.

## 실패한 변경에서 서비스와 데이터를 복구하기

자동 배포에서는 성공 경로만큼 실패한 뒤 무엇을 남길지도 중요했다. 빌드 실패와 Preview 교체 중 실패는 이미 변경한 대상이 다르므로 대응도 나눴다.

| 실패한 단계             | 처리                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| 빌드·테스트             | Preview 교체를 시작하지 않고 실패 이력을 남긴다. 기존 정상 Preview는 계속 실행된다.              |
| Preview 교체·Ready 확인 | 이전 정상 이미지와 데이터 볼륨, 라우트로 복구를 시도한다. 복구 자체가 실패하면 그 이력도 남긴다. |
| 워커 실행 중단          | 시작 시점과 작업이 없는 시점의 복구 점검에서 중단된 배포를 정리한다.                             |

데이터도 컨테이너 밖에 보존해야 한다. 현재 템플릿은 앱의 `/data`에 SQLite 데이터와 파일을 저장할 수 있다. 재배포할 때는 기존 Preview를 멈춘 뒤, 이전 데이터 볼륨을 읽기 전용으로 연결해 새 세대의 볼륨으로 복제한다. 새 버전의 준비 확인이 실패하면 이전 이미지와 변경되지 않은 이전 데이터로 돌아갈 수 있게 한 것이다.

이 교체 방식은 상태를 가진 애플리케이션을 다시 띄우는 `Recreate` 방식이다. 교체 과정에는 중단이 생길 수 있으며, 복구 실패도 가능하다. 또한 배포 실패에 대비해 이전 볼륨을 남기는 것과 서버 장애에 대비한 백업은 별개다. PostgreSQL과 프로젝트 데이터의 자동 백업·복원은 후속 과제로 남아 있다.

## 배운 점과 다음 검증

현재는 FastAPI 저장소의 `main`을 프로젝트별 고정 Preview 주소에 배포한다. PR별 Preview와 정식 운영 승격, 다른 런타임 지원, 사내 보안 기준 적용은 후속 과제다.

자동 배포를 구현하며 실행 조건과 실패 시 복구 기준도 함께 정해야 한다는 점을 배웠다. 다음에는 첫 Preview까지 걸리는 시간과 운영자 개입 횟수를 측정하고, 사용자가 수정과 재배포를 직접 이어갈 수 있는지 확인하려 한다.
