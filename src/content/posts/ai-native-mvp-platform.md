## 개요

사내에서 MVP를 쉽게 검증할 수 있는 플랫폼을 구축하려 한다. 서버를 띄우고 연동하는 일은 AI에게 맡기고, 나는 공통 보안 가이드라인을 정하고 플랫폼을 운영한다. 제품 개발자는 인프라 준비 없이 아이디어를 바로 테스트한다.

이 글은 내가 겪는 병목을 Goldratt의 집중 개선 5단계로 해석하고, 플랫폼을 만들 순서를 정리하며 시작했다. 현재는 개인 홈 서버에서 프로젝트 생성부터 미리보기 서비스의 자동 배포까지 구현했다. 앞부분에는 처음의 문제의식을 남기고, 구현 과정과 남은 과제는 단계별로 이어서 기록한다.

## 나의 상황

백엔드 개발자로 일하면서 병목이 되지 않으려고 제한선을 둬왔다. 할 수 있는 만큼을 정하고, 넘치는 일은 일정을 조정했다. 그런데 최근 이 제한선 자체가 병목일 수 있다는 생각이 들었다. 제한선은 내 생산성이 고정이라는 전제로 만든 규칙인데, AI로 생산성을 높일 수 있게 되면서 그 전제가 유효하지 않게 됐다.

조직에도 비슷한 구조가 있다. 우리는 보안팀, 인프라팀, 개발팀으로 나눠 전문성을 높여왔다. 운영 중인 제품처럼 실수 비용이 큰 일에는 맞는 구조다. 그런데 아이디어 하나를 검증하려면 각 팀을 건별로 거쳐야 한다. 서버를 띄우려면 인프라 준비를 기다리고, 외부에 열려면 보안 검토를 기다린다. 검증 자체보다 준비에 시간이 더 들고, 준비는 아이디어가 살아남든 버려지든 매번 반복된다. 준비가 부담스러우면 만들어보면 금방 판단할 아이디어도 시작하지 않게 된다.

개인의 제한선과 조직의 분업을 같은 틀로 정리하려고 Goldratt가 『The Goal』에서 제시한 집중 개선 5단계에 대입해봤다.

## Goldratt의 집중 개선 5단계

Goldratt는 시스템 전체의 산출량을 가장 느린 지점, 즉 병목이 결정한다고 봤다. 개선은 다섯 단계로 진행한다.

1. **식별**. 전체 속도를 결정하는 병목을 찾는다. 일이 쌓이는 곳이 병목이다.
2. **활용(exploit)**. 병목을 늘리기 전에 지금 있는 병목부터 낭비 없이 쓴다. 병목이 한 시간 놀면 시스템 전체가 한 시간 늦어진다.
3. **종속(subordinate)**. 나머지 전부를 병목의 속도에 맞춘다. 병목이 아닌 곳을 최대 속도로 돌리면 산출량은 늘지 않고 병목 앞에 일만 쌓인다.
4. **키우기(elevate)**. 활용과 종속으로도 부족하면 병목의 용량을 늘린다. 여기부터 투자가 들어간다.
5. **반복**. 병목은 다음으로 약한 지점으로 이동하므로 1단계로 돌아간다. 옛 병목 시절에 만든 규칙이 살아남아 새 병목이 되지 않는지도 확인한다.

Goldratt는 규칙 때문에 생긴 병목을 정책 제약(policy constraint)이라고 불렀다. 규칙을 만들 때의 전제가 바뀐 뒤에도 규칙이 남아 있는 경우다. 이런 병목이 설비나 인력 부족보다 흔하다고 봤다.

## 집중 개선 5단계에 대입한 나의 상황

| 단계      | 나의 상황                                                           |
| --------- | ------------------------------------------------------------------- |
| 1. 식별   | 인프라 준비와 보안 검토를 기다리는 시간이 병목이다                  |
| 2. 활용   | 검토 서류를 미리 갖추고 요청을 모아서 낸다. 더 짜낼 게 없다         |
| 3. 종속   | 검증 속도를 준비 용량에 맞추고 제한선으로 일정을 조정해왔다         |
| 4. 키우기 | 플랫폼을 만드는 단계다. 반복되는 준비와 확인을 자동화한다           |
| 5. 반복   | 플랫폼 이후 병목이 이동할 자리다. 아래 "답해야 할 질문"이 그 후보다 |

플랫폼을 구상하기 전의 대응은 2~3단계였다. 제한선을 정하고 일정을 조정한 것은 병목을 그대로 둔 채 할 수 있는 최선이었다. 이번에는 4단계를 시도해보기로 했다.

내 상황의 병목은 정책 제약이다. "전문성은 요청이 올 때마다 그 팀의 사람이 직접 적용한다"는 규칙은 전문성을 자동화로 옮길 수 없던 시절에는 맞았다. 지금은 서버 구성의 정형화된 부분을 AI가 만들 수 있고, 보안 기준을 가이드라인으로 한 번 정리해 모든 MVP에 강제할 수 있다.

플랫폼은 4단계, 키우기에 해당한다. 보통은 병목에 사람을 더 넣지만 이 방식은 사람을 늘리지 않는다. 보안팀의 전문성은 건별 검토 대신 사전에 정의한 가이드라인으로 옮기고, 인프라 구성은 담당자 대신 AI가 만든다.

5단계의 경고도 미리 적어둔다. 각 팀의 대기가 사라진 자리에 플랫폼 운영자인 내 대기가 생기면 병목은 나에게 이동한 것뿐이다. MVP가 늘어도 내 일이 비례해서 늘지 않는 구조가 필요한 이유다.

## 역할을 어떻게 나누나

| 역할              | 담당                                   |
| ----------------- | -------------------------------------- |
| AI                | 서버 구성, 공통 요소 연동              |
| 플랫폼 운영자(나) | 공통 보안 가이드라인 정의, 플랫폼 운영 |
| 제품 개발자       | 아이디어 구현과 테스트                 |

제품 개발자는 인프라와 보안을 신경 쓰지 않는다. 만들고 싶은 것을 설명하고, 나온 결과를 써보며 아이디어를 판단한다. 나는 개별 MVP에 관여하지 않는다. 모든 MVP가 공통으로 지켜야 할 경계를 정하고, 그 경계가 지켜지는지 확인한다.

## 빌더로 일하는 문화

이 플랫폼의 밑바탕에는 개발 문화를 바꾸고 싶은 니즈가 있다. AI가 나오면서 개발자의 일은 코드를 직접 쓰는 것에서 무엇을 만들지 정하고 결과를 판단하는 쪽으로 옮겨간다고 생각한다. 나는 이 역할을 빌더라고 부르고 있다. 빌더로 일하려면 시도의 비용이 낮아야 한다. 플랫폼으로 준비 비용을 낮추면, 만들어보고 판단하는 방식으로 일하는 문화를 시도해볼 수 있다.

## 어떻게 진행하나

두 단계로 나눠 진행한다.

1. 개인 홈 서버에서 먼저 만든다. 사내에 들고 가기 전에 AI에게 서버 구성을 맡기는 방식이 실제로 돌아가는지, 보안 가이드라인을 어떤 형태로 강제할 수 있는지 혼자 확인한다.
2. 사내 서버로 옮기고 제품 개발자를 사용자로 받는다. 혼자 쓸 때는 안 보이던 문제가 여기서 드러날 것이다.

각 단계에서 아래 내용을 이 글에 추가한다.

- 진행 과정 요약
- 시스템의 역할과 흐름
- 배운 것

트러블슈팅은 단계가 끝날 때까지 기다리지 않고 겪는 대로 해당 단계 아래에 기록한다.

## 1단계 : 개인 홈 서버에서 검증

### 목표: 아이디어를 실행하기까지의 준비를 줄인다

첫 단계에서는 개발자가 프로젝트를 만들고, 코드를 바꾸고, 실행 결과를 확인하는 흐름을 연결했다. 서버를 준비하는 일을 반복하지 않아도 아이디어를 시험할 수 있게 만드는 것이 목표다. 구현 내용은 [GitHub 기반 내부 MVP 플랫폼 PR](https://github.com/this-is-spear/hello-mvp-sandbox/pull/2)에 정리했다.

개인 홈 서버에 만든 플랫폼은 프로젝트마다 미리보기 환경인 Preview를 제공한다. 사용자는 같은 주소에서 바뀐 결과를 확인할 수 있다. 첫 범위는 FastAPI로 만든 서비스로 좁혔다. 여러 개발 버전을 동시에 비교하거나 검증한 서비스를 정식 운영으로 옮기는 기능은 다음 과제로 남겼다.

### 사용 흐름: 만들고, 바꾸고, 확인한다

사용자가 하는 일은 세 단계다.

1. **만든다.** GitHub으로 로그인하고 프로젝트 이름을 입력한다. 플랫폼이 기본 구성을 갖춘 비공개 코드 저장소를 만든다.
2. **바꾼다.** 개발자나 AI 에이전트가 코드를 수정해 저장소의 기본 브랜치에 반영한다. 플랫폼이 변경을 감지하고 테스트와 배포를 진행한다.
3. **확인한다.** 배포가 성공하면 프로젝트의 Preview 주소에서 결과를 사용해본다. 포털에서는 자신에게 권한이 있는 프로젝트와 배포 상태를 확인한다.

프로젝트를 만드는 것과 서비스가 실행되는 것은 별개의 단계다. 첫 배포가 성공해야 Preview를 사용할 수 있다. 이후에는 같은 주소에서 변경한 결과를 확인하며 아이디어를 다듬는다.

### 구조: 사용자 요청, 배포 작업, 서비스 실행을 나눈다

이 흐름을 지원하기 위해 시스템의 역할을 나눴다. 핵심은 사용자 요청을 처리하는 일과 오래 걸리는 배포 작업을 분리하는 것이다.

| 역할        | 하는 일                                                        |
| ----------- | -------------------------------------------------------------- |
| 사용자 포털 | 로그인하고 프로젝트와 배포 상태를 확인하는 창구다              |
| 플랫폼 제어 | 프로젝트를 만들고 코드 저장소와 연결한다                       |
| 변경 감지   | 코드가 바뀌었는지 확인하고 배포할 작업을 등록한다              |
| 배포 실행   | 코드를 실행 가능한 형태로 만들고 테스트한 뒤 서비스에 반영한다 |
| 서비스 실행 | 사용자가 Preview 주소로 접속해 결과를 확인할 수 있게 한다      |
| 상태 기록   | 프로젝트와 배포 진행 상황, 실패 이력을 보존한다                |

변경 감지는 배포 실행에 작업을 넘기고, 배포 실행은 서비스 실행에 새 버전을 반영한다. 이 과정의 상태를 기록해두면 사용자는 포털에서 진행 상황을 확인할 수 있다.

#### 구현한 것

- **배포 작업의 독립 실행**: 배포 작업을 사용자 요청 처리와 분리해 별도로 실행한다. 배포를 맡은 프로그램이 멈춰도 사용자 요청 처리와 이미 실행 중인 Preview를 유지할 수 있도록 했다.

#### 의도적으로 구현하지 않은 것

- **기능별 독립 실행**: 이번 구현에서는 사용자 포털과 플랫폼 제어, 변경 알림 수신을 하나의 실행 단위로 묶었다. 이 실행 단위가 멈추면 세 기능이 함께 영향을 받는다.
- **서버 장애 시 서비스 전환**: 개인 서버 한 대에서 검증하는 범위로 정했다. 서버 자체가 멈췄을 때 다른 서버에서 서비스를 이어가는 구조는 이번 범위에서 제외했다.

### 배운 점: 자동 실행에는 확인과 복구도 필요하다

코드 변경을 자동으로 반영하려면 실패했을 때의 처리도 정해야 한다. 현재는 빌드나 테스트가 실패하면 기존 Preview를 유지한다. 새 버전을 반영한 뒤 정상 동작을 확인하지 못하면 이전 정상 버전으로 복구를 시도한다. 교체 중에는 중단이 생길 수 있어 무중단 배포를 보장하는 단계는 아니다.

처음에는 서버 구성을 AI에게 맡기는 데 초점을 뒀다. 구현하면서 함께 정리한 것은 어떤 조건을 만족해야 서비스를 실행할 수 있는가였다. 공통 템플릿과 배포 절차를 두면 프로젝트마다 실행 방법을 다시 정하는 일을 줄일 수 있다. AI가 코드를 만들어도 같은 확인 절차를 거치게 할 수 있다.

다만 테스트를 통과하고 서비스가 실행된다고 해서 사내 보안 기준까지 충족한 것은 아니다. 이번에는 프로젝트 생성과 배포 흐름을 구현했고, 보안 기준을 정하고 자동으로 확인하는 일은 더 진행해야 한다.

### 다음 검증: 실제로 기다리는 시간이 줄었는가

구현 PR에는 자동 테스트와 개인 서버의 외부 접속 확인 결과를 기록했다. 다음에는 사용자가 프로젝트를 만든 뒤 첫 결과를 보기까지 얼마나 기다리는지, 그 과정에서 운영자가 몇 번 개입하는지 확인하려 한다.

사내 사용자를 받기 전에는 장애가 났을 때 서비스와 데이터를 복구할 수 있는지, 사용자 권한과 보안 기준을 일관되게 적용할 수 있는지도 검증해야 한다. 후속 범위는 [구현 이슈](https://github.com/this-is-spear/hello-mvp-sandbox/issues/4)에 정리하고 있다.

처음의 문제는 아이디어를 검증하기 전에 준비를 기다려야 한다는 것이었다. 플랫폼을 사용한 뒤 그 시간이 줄어들고 운영자의 개입도 줄어야, 병목을 개선했다고 말할 수 있다.

## 2단계 : 사내 서버에서 사용자 받기

개인 홈 서버에서 운영·보안 검증을 더 진행한 뒤 사내 서버로 옮길 예정이다. 아직 사내 사용자를 받아 검증한 단계는 아니다.

## 사내 적용 전에 답해야 할 질문

구상할 때 남겼던 질문이다. 첫 구현을 마친 지금도 실행 규칙과 보안 기준의 범위, 사내 적용 방식은 더 정리해야 한다.

- 공통 보안 가이드라인의 범위를 어디까지 잡을지. 좁으면 가이드라인 밖 요청마다 예외 검토가 생겨 대기가 되살아나고, 넓으면 만들 수 있는 것이 줄어든다.
- AI가 만든 서버 구성을 어떻게 검증할지. 가이드라인을 지켰는지 사람이 매번 확인하면 준비 비용이 그대로 돌아온다. 자동으로 확인할 방법이 필요하다.
- 검증에 성공한 MVP를 제품으로 어떻게 옮길지. MVP 환경과 운영 환경의 차이가 크면 검증 결과를 신뢰하기 어렵다.
- 첫 사용자를 누구로 잡을지. 문화를 바꾸는 일이라 플랫폼을 만들어두고 기다리면 쓰이지 않을 가능성이 높다.

## 마무리하며

개인 홈 서버에서 프로젝트 생성부터 Preview 배포까지의 흐름을 연결했다. 반복되는 준비를 템플릿과 배포 절차로 옮기는 첫 구현이다.

다음은 운영·보안 기준을 보강하고 실제 사용에서 준비 시간이 줄어드는지 확인하는 일이다. 플랫폼을 만드는 것만으로 병목이 사라졌다고 판단할 수는 없다. 처음에 적었던 것처럼, 줄어든 대기가 플랫폼 운영자인 나에게 다시 쌓이지 않는지까지 살펴보려 한다.
