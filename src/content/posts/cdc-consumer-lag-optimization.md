## 개요

[2026년 8월 3주차 회고](/posts/2026-august-week3-review)에서 "CDC를 로컬에서 직접
테스트해보고 겪은 경험을 정리하기"를 Try로 남겼다. 그 후속이다.
Debezium과 MySQL binlog로 CDC 파이프라인을 만들고, 부하를 걸어 lag을 만든 다음,
컨슈머 처리량을 2.8배로 올려 lag이 형성되지 않는 지점까지 갔다.

결과보다 남은 것은 **예상이 세 번 틀렸다는 사실**이다.

1. 손으로 짚은 1순위는 이벤트당 로깅이었다. 틀렸다.
2. CPU 프로파일이 지목한 1순위는 JSON 파싱(54%)이었다. 이것도 실제 최대 레버가 아니었다.
3. 실제 최대는 **CPU 프로파일에 아예 보이지 않던 컨슈머 병렬성**이었다.

측정 도구를 두 번 고쳤고, 그중 한 번은 **개선된 설정이 오히려 더 느리게 측정되는**
역전까지 겪었다. 이 글은 그 과정을 순서대로 남긴다.

측정 환경: Mac16,7 / 14 core / 48GB, Docker에 14 CPU·8GB 할당.
MySQL 8.4, Kafka 4.0(KRaft), Debezium 3.6, Spring Boot 4.1 + Kotlin.
모든 수치는 로컬 단일 노드 기준이며 운영 환경의 절대값으로 읽을 값은 아니다.

## 결과부터

같은 조건(100만 이벤트, 파티션 4개)에서 설정을 하나씩만 바꿔 측정했다.

| 설정                        |    소비 속도 |      대비 |  최고 lag |
| --------------------------- | -----------: | --------: | --------: |
| 베이스라인                  |     31,121/s |         — |   602,723 |
| 이벤트당 로깅 제거          |     37,197/s |      +20% |   566,310 |
| `max.poll.records` 500→2000 |     48,049/s |      +54% |   418,870 |
| `fetch.bytes` 1MB→5MB       |     29,939/s |   **−4%** |   652,346 |
| **`concurrency` 1→4**       | **77,015/s** | **+147%** |   129,706 |
| 전체 조합                   |     86,041/s |     +176% | **3,693** |

측정 기간: 2026-08-24, 실행당 100만 이벤트
대상: 로컬 Docker 단일 브로커, 토픽 파티션 4개, 부하는 상품 키 300개에 분산
계산: 컨슈머가 포화된 구간(첫 샘플 ~ lag 최고점)의 `consumed` 기울기

![여섯 가지 설정의 소비 속도와 최고 lag을 나란히 그린 가로 막대그래프. concurrency 4가 단독으로 77,015/s로 가장 길고, fetch.bytes 5MB만 베이스라인보다 짧다](@/assets/images/cdc-consumer-lag-optimization/experiment-results.svg)

`concurrency` 하나가 나머지 세 요인을 다 합친 것(+94%)보다 컸다.
그리고 `fetch.bytes` 인상은 **성능을 떨어뜨렸다.**

## 무엇을 만들었나

목표는 CDC 학습이었고, 그중에서도 "Kafka를 끼운 CDC 파이프라인을 어떻게 구성하는가"만
관심사였다. 도메인, 앱 구조, 저장 방식은 모두 의도적으로 단순화했다.

Kotlin + Spring Boot 앱 하나가 상품 가격·재고를 REST로 변경하면,
그 변경이 MySQL binlog → Debezium → Kafka를 거쳐 같은 앱의 `@KafkaListener`로
돌아와 "가격이 얼마에서 얼마로 바뀌었다"로 해석된다.

![CDC 파이프라인을 세로로 그린 흐름도. Spring Boot 앱, MySQL, Debezium, Kafka, KafkaListener 다섯 단계가 화살표로 이어지고 각 화살표에 그 구간에 흐르는 데이터 형태와 실측 처리량이 붙어 있다](@/assets/images/cdc-consumer-lag-optimization/pipeline-overview.svg)

Embedded Engine으로 앱에 내장하면 Kafka 없이도 CDC는 된다. 그러면 정작 알아보려던
토픽 이름 규칙, 오프셋 관리, 컨슈머 그룹, lag 같은 주제가 전부 사라진다.
그래서 Kafka Connect 방식을 택했다.

### binlog에는 컬럼 이름이 없다

CDC를 손으로 만져보고 가장 인상적이었던 지점이다.
binlog의 ROW 이벤트에는 **컬럼 이름도 타입도 없다.** 그냥 "테이블 108번의
3번째 컬럼이 이 바이트에서 저 바이트로 바뀜" 수준의 raw 데이터다.

![raw binlog ROW 이벤트와 스키마 메타데이터가 합쳐져 Debezium envelope이 되는 3단 도식. 왼쪽 raw 이벤트에는 컬럼 이름이 없고, 가운데 스키마 히스토리가 price는 DECIMAL(12,2)의 3번째 컬럼이라는 정보를 제공한다](@/assets/images/cdc-consumer-lag-optimization/binlog-to-envelope.svg)

그래서 Debezium은 DDL 이력을 별도 Kafka 토픽에 쌓아두고, 재시작하면 그것을 재생해
"읽으려는 binlog 위치에서의 스키마"를 복원한다. `schema.history.internal.kafka.topic`
설정이 그것이고, 이름에 `history`가 붙은 이유다. 스키마는 `ALTER TABLE`로 변하니
시점별로 달라야 한다.

### 오프셋이라는 단어가 세 가지 뜻으로 쓰인다

lag을 이해하려면 이걸 먼저 구분해야 했다.

![오프셋 3종을 나란히 놓은 도식. binlog 위치는 connect_offsets 토픽에, log-end-offset은 토픽 자체에, committed-offset은 __consumer_offsets에 저장되며 lag은 뒤 두 값의 차이라고 표시되어 있다](@/assets/images/cdc-consumer-lag-optimization/three-offsets.svg)

lag은 **log-end-offset 빼기 committed-offset**이다. binlog 위치는 여기 안 들어간다.
그래서 MySQL과 Debezium 사이의 지연은 Kafka lag에 잡히지 않고,
Connect의 `MilliSecondsBehindSource`를 따로 봐야 한다.

## 딥다이브 1 : 부하를 걸었더니 lag이 115만까지 쌓였다

처음에는 SQL 문을 파이프로 보냈는데 문장마다 네트워크 왕복이 있어 초당 1,351건이
한계였다. 이 속도로는 Debezium이 여유롭게 따라가서 **lag이 전 구간 0**이었다.
저장 프로시저로 루프를 MySQL 내부에서 돌리고 500건마다 커밋하자 초당 19만 건이 나왔고,
그때부터 뒤쪽이 밀리기 시작했다.

```sql
CREATE PROCEDURE gen_load(IN target_id BIGINT, IN n INT, IN span INT)
BEGIN
  DECLARE i INT DEFAULT 0;
  SET autocommit = 0;
  WHILE i < n DO
    UPDATE products SET stock_quantity = (stock_quantity + 1) % 1000000
      WHERE id = target_id + (i % span);
    SET i = i + 1;
    IF i % 500 = 0 THEN COMMIT; END IF;
  END WHILE;
  COMMIT;
END
```

증가 연산을 쓴 데는 이유가 있다. 처음에는 난수를 대입했는데,
**난수가 현재 값과 우연히 같으면 그 UPDATE는 binlog 이벤트를 만들지 않는다.**
InnoDB가 모든 컬럼이 동일한 UPDATE는 행을 실제로 쓰지 않기 때문이다.
직접 확인해봤다.

| 실행               | `ROW_COUNT()` | `updated_at`             | 토픽 오프셋 |
| ------------------ | ------------: | ------------------------ | ----------: |
| 1회차 (777로 변경) |             1 | `02:19:47.348769`로 갱신 |          +1 |
| 2회차 (다시 777)   |         **0** | **그대로**               |      **+0** |

UPDATE 문을 두 번 실행했는데 이벤트는 1건만 발행됐다. 곁들여 알게 된 것은
`ON UPDATE CURRENT_TIMESTAMP`도 발동하지 않는다는 점이다.
"분명 UPDATE를 쳤는데 `updated_at`이 안 바뀐다"는 혼란의 원인이 대개 이것이다.

200만 건을 쏟아부은 결과다.

![produced, consumed, lag 세 선을 그린 부하 곡선. produced가 가파르게 오르는 동안 consumed는 완만해서 lag이 최대 1,156,000까지 벌어지고, 발행이 끝난 30.1초 지점부터 lag이 내려간다](@/assets/images/cdc-consumer-lag-optimization/lag-curve.svg)

| 총 이벤트 | MySQL 쓰기 | Debezium 발행 (평균 / 순간 최대) |      최고 lag | 컨슈머 소비 |
| --------: | ---------: | -------------------------------: | ------------: | ----------: |
|   600,000 |  166,081/s |              66,667/s / 95,262/s |       348,236 |    30,341/s |
| 1,200,000 |  194,449/s |              67,039/s / 97,770/s |       709,256 |    30,659/s |
| 2,000,000 |  196,296/s |              66,445/s / 97,515/s | **1,156,000** |    30,110/s |

### lag만으로는 원인을 알 수 없다

lag이 늘어나는 이유는 **컨슈머가 느려진 것**과 **생산이 폭증한 것** 두 가지인데,
lag은 생산과 소비가 동시에 만드는 값이라 숫자만으로는 구분되지 않는다.
발행이 멈춘 시점으로 구간을 나눠 소비 속도만 따로 계산했다.

| 구간                           |     발행 |     소비 |  lag 변화 |
| ------------------------------ | -------: | -------: | --------: |
| 발행 중 (+1.3s ~ +30.1s)       | 67,803/s | 29,518/s | +38,285/s |
| 발행 종료 후 (+30.1s ~ +41.4s) |      0/s | 30,110/s | −30,110/s |

두 구간의 소비 속도가 거의 같다. **컨슈머는 내내 같은 속도로 처리했고 발행이 2배 이상
빨랐던 것**이므로 생산 폭증으로 확정됐다. 컨슈머를 의심해 프로파일링부터 시작했다면
시간을 낭비했을 것이다.

그리고 소진 예상 시간은 `1,156,000 ÷ 30,110 ≈ 38초`였고 실제로 발행이 멈춘 뒤
lag은 0까지 내려갔다. 누적 401만 건에 유실은 0이었다. 순간 유입이 소비 능력의 4배를
넘었지만 Kafka가 버퍼 역할을 해 흡수했다. **이 lag 자체는 장애가 아니다.**

![MySQL 쓰기 196,296/s, Debezium 발행 66,445/s, 컨슈머 소비 30,110/s를 길이가 줄어드는 가로 막대로 그린 도식. 각 구간 사이에 얼마만큼이 밀리는지 표시되어 있다](@/assets/images/cdc-consumer-lag-optimization/stage-throughput.svg)

## 딥다이브 2 : 컨슈머는 왜 못 따라갔나

무엇을 고칠지 정하려면 **시간·메모리·I/O를 각각 재야 한다.**
측정은 lag이 쌓여 컨슈머가 포화된 catch-up 구간에서 했다.
부하가 없는 정상 상태에서는 컨슈머가 `poll()`에서 대기하므로
프로파일의 대부분이 park/wait로 채워진다.

### 시간 — 이벤트 1건에 33.0µs

`jdk.ThreadCPULoad`로 보니 리스너 스레드가 **1코어의 약 50%만** 쓰고 있었다.
절반은 CPU 실행이고 절반은 대기라는 뜻이다. JFR `ExecutionSample` 663개로
CPU 절반을 분해했다.

| 구간                        |   이벤트당 | 전체 비율 |        CPU 내 비율 |
| --------------------------- | ---------: | --------: | -----------------: |
| JSON 파싱 (jackson)         |      8.9µs |     27.0% |              54.1% |
| 로깅 (logback→stdout)       |      4.1µs |     12.4% |              24.9% |
| Kafka 클라이언트            |      1.9µs |      5.8% |              11.6% |
| Spring Kafka 컨테이너       |      1.0µs |      3.0% |               6.0% |
| `ChangeDetector` 등 앱 코드 |      0.5µs |      1.6% |               3.3% |
| **대기**                    | **16.5µs** | **50.0%** | 프로파일에 안 보임 |

![이벤트 1건 33.0µs를 가로 막대로 나눈 그림. 왼쪽 절반은 JSON 파싱, 로깅, Kafka 클라이언트 등 CPU 구간이고 오른쪽 절반은 회색 대기 구간이다](@/assets/images/cdc-consumer-lag-optimization/per-event-time.svg)

![컨슈머 CPU 프로파일 flame graph. 바닥의 Spring Kafka 컨테이너 층을 지나 onMessage에서 ObjectMapper.readValue와 Logger.info 두 갈래로 갈라진다](@/assets/images/cdc-consumer-lag-optimization/flamegraph-baseline.svg)

flame graph는 가로폭이 그 함수가 스택에 있던 샘플 수, 즉 CPU 시간 비중이다.
`onMessage` 위에서 `readValue`와 `Logger.info` 두 갈래로 갈라지는 것이 보인다.

### 메모리 — 이벤트당 12,635 bytes

`jdk.ObjectAllocationSample`의 `weight`를 합산하면 catch-up 구간에서 초당 380MB,
이벤트당 12,635 bytes를 할당했다. 상위 타입은 `byte[]` 31.3%, `Object[]` 12.6%,
`HeapByteBuffer` 6.4%, `String` 6.1%로 모두 JSON 파싱 부산물이다.

다만 **GC는 원인이 아니었다.** 34초 구간에서 pause 55건 합계 52.2ms(0.15%)에
불과했다. 할당은 많지만 대부분 단명 객체라 young GC가 싸게 처리했다.

### I/O — 대기 절반의 정체

여기서 막혔다. JFR의 I/O 이벤트는 임계값 이상만 기록하므로 리스너 스레드에서
`ThreadPark` 0건, `SocketRead` 0건, `FileWrite` 9건(27ms, 0.1%)뿐이었다.
**긴 블로킹은 없고 짧은 대기가 무수히 많은 형태**여서 프로파일로는 잡히지 않았다.

`spring-boot-starter-actuator`를 붙여 Kafka 컨슈머 메트릭을 보고서야 정체가 드러났다.

| 항목                      |     측정값 | 해석                                       |
| ------------------------- | ---------: | ------------------------------------------ |
| `fetch.latency.avg`       | **85.0ms** | fetch 왕복 1회에 85ms                      |
| `fetch.size.avg`          |     904 KB | 기본 상한 1MB의 88% — **상한에 붙어 있다** |
| `records.per.request.avg` |      1,031 | fetch 1회에 1,031건                        |
| `fetch.rate`              |     8.99/s | fetch 왕복 횟수                            |

**대기의 정체는 fetch 왕복이었다.** CPU 프로파일만 봤다면 절대 찾지 못했을 원인이다.

### `poll()`과 fetch는 다른 층이다

이 구분을 놓치면 엉뚱한 설정을 건드리게 된다.

- **fetch** — 네트워크 요청. 브로커에 왕복해서 데이터 덩어리를 받아 컨슈머 내부 버퍼를 채운다.
- **`poll()`** — 애플리케이션 API. 이미 버퍼에 있는 것에서 레코드를 꺼내 앱에 넘긴다.

| 설정                        | 기본값 | 층        |
| --------------------------- | -----: | --------- |
| `max.partition.fetch.bytes` |    1MB | **fetch** |
| `fetch.min.bytes`           |      1 | **fetch** |
| `max.poll.records`          |    500 | **poll**  |

`max.poll.records`는 네트워크와 무관하다. 버퍼에서 몇 개를 꺼내 줄지만 정한다.

![컨슈머가 이벤트 1건을 처리하는 8단계를 세로로 나열하고 각 단계의 CPU 비중을 배지로 표시한 도식. 맨 위에 전체 시간을 CPU 50%와 대기 50%로 나눈 막대가 있다](@/assets/images/cdc-consumer-lag-optimization/consumer-pipeline.svg)

## 딥다이브 3 : 요인을 분리하니 예상이 뒤집혔다

처음에는 여러 설정을 한꺼번에 바꿔 비교했다. 그 결과로
"`max.poll.records`가 최대 효과", "`fetch.bytes`는 단독으로는 미미하지만
조합하면 맞물린다"고 정리했다. **둘 다 틀렸다.**

조건을 다시 잡았다. **토픽 파티션을 4개로 고정**하고 부하를 키 300개에 분산시킨 뒤,
앱 실행 인자를 하나씩만 바꿨다. 파티션 수를 고정하고 `listener.concurrency`만
바꾸므로 병렬성 효과가 단독으로 분리된다.

앞의 결과표가 그 측정이다. 여기서 세 가지가 드러났다.

**첫째, 단독 최대는 `concurrency`(+147%)다.** 나머지 세 요인을 다 합쳐도 +94%로
병렬성 하나에 미치지 못한다. CPU 프로파일은 이 사실을 알려주지 않는다 —
스레드가 1개라는 것은 hot method가 아니라 구조의 문제이기 때문이다.

**둘째, 파티션만 늘리는 것은 아무 효과가 없다.** 파티션이 4개인데도 31,121/s로,
파티션 1개였던 이전 측정(30,315/s)과 사실상 같았다. 파티션은 병렬 소비의
**전제 조건**일 뿐 `concurrency`를 함께 올려야 효과가 난다.

![같은 group-id면 파티션을 나눠 갖고 다른 group-id면 전량을 각자 받는 구조를 좌우로 비교한 도식](@/assets/images/cdc-consumer-lag-optimization/consumer-groups.svg)

여기에도 전제가 하나 더 있었다. Debezium은 PK를 메시지 키로 쓰므로 파티션 분산은
PK 해시 기준인데, 상품이 4행뿐이면 키가 4개뿐이라 파티션을 늘려도 의미가 없다.
**상품을 304행으로 늘리고 부하도 300개 키에 분산시킨 뒤에야** 유효한 실험이 됐다.

**셋째, `fetch.bytes` 인상은 해로웠다.** 단독으로 −4%였고 조합에서도 마찬가지다.
`max.poll.records`만 올린 48,049/s에 `fetch.bytes`를 더하니 41,414/s로 떨어졌다.

의도대로 작동하기는 했다. `records.per.request.avg`가 3,827 → 15,260건,
`fetch.size.avg`가 3.4MB → 13.5MB로 4배가 됐고 왕복 횟수는 2.16 → 0.67/s로 줄었다.
문제는 **`fetch.latency.avg`가 148ms → 285ms로 함께 늘어난 것**이다.
게다가 `poll()`이 여전히 500건씩만 넘기니 15,260건짜리 버퍼를 비우는 데
`poll()`을 30여 번 불러야 한다. **poll 층에 병목이 있는데 fetch 층만 키우면
버퍼만 커지고 처리량은 늘지 않는다.**

## 딥다이브 4 : 베이스라인을 바꾸니 결론이 또 조정됐다

이벤트당 INFO 로깅은 CDC 이벤트를 눈으로 보여주려고 넣은 **샘플용 장치**다.
실무 컨슈머가 핫 패스에서 할 일이 아니다. 그런데 프로파일에서 24%를 차지할 만큼
크기 때문에, 이것을 베이스라인에 남겨두면 나머지 요인의 개선율이 부풀려진다.

코드는 그대로 두고 로그 레벨만 WARN으로 내려 `log.info`가 실행되지 않게 한 뒤
같은 조건에서 프로파일을 다시 떴다.

| 구간             |    AS-IS (INFO) |    TO-BE (WARN) |
| ---------------- | --------------: | --------------: |
| JSON 파싱        |     204 (48.8%) | 335 (**72.7%**) |
| 로깅             | 100 (**23.9%**) |        2 (0.4%) |
| Kafka 클라이언트 |      71 (17.0%) |      71 (15.4%) |
| Spring Kafka     |       30 (7.2%) |       33 (7.2%) |
| 앱 코드          |       13 (3.1%) |       20 (4.3%) |
| **소비 속도**    |    **29,587/s** |    **37,464/s** |

| AS-IS — 로깅 INFO                                                                                                                                                                                                       | TO-BE — 로깅 WARN                                                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ![로깅을 켠 상태의 flame graph. onMessage 위에서 readValue 갈래와 주황색 Logger.info 갈래가 나란히 갈라지고, logback appender 체인이 깊게 쌓여 있다](@/assets/images/cdc-consumer-lag-optimization/flamegraph-asis.svg) | ![로깅을 끈 상태의 flame graph. 주황색 로깅 갈래가 사라지고 readValue 갈래가 남은 폭을 차지해 붉은 덩어리 하나로 단순해졌다](@/assets/images/cdc-consumer-lag-optimization/flamegraph-tobe.svg) |

왼쪽에서 `onMessage` 위로 갈라지던 두 갈래 중 **주황색 로깅 갈래가 오른쪽에서는 통째로
사라졌다.** 남은 폭을 `readValue` 갈래가 차지하면서 붉은 덩어리 하나로 단순해진다.
세로 길이가 줄어든 것은 logback의 appender 체인이 통째로 없어졌기 때문이다.

**비중만 보면 오해한다.** JSON 파싱이 48.8% → 72.7%로 늘어난 것처럼 보이지만
JSON 파싱이 느려진 것이 아니라 **분모가 줄어든 것**이다. 절대량으로 환산해야 한다.

| 구간                   | AS-IS 이벤트당 | TO-BE 이벤트당 |        변화 |
| ---------------------- | -------------: | -------------: | ----------: |
| JSON 파싱              |         3.49µs |         4.03µs |     +0.54µs |
| 로깅                   |         1.71µs |         0.02µs | **−1.69µs** |
| Kafka 클라이언트       |         1.22µs |         0.85µs |     −0.36µs |
| **CPU 합계**           |     **7.15µs** |     **5.55µs** | **−1.61µs** |
| **이벤트당 전체 시간** |    **33.80µs** |    **26.69µs** | **−7.11µs** |

마지막 두 줄이 핵심이다. **CPU는 1.61µs 줄었는데 전체 시간은 7.11µs 줄었다.**
CPU 절감만으로는 처리량 향상을 설명할 수 없고, 차이만큼은 **로깅이 유발하던 대기**였다.
stdout 쓰기가 블로킹되는 시간이다.

그래서 로깅을 끈 상태를 진짜 베이스라인으로 두고 나머지를 다시 쟀다.

| 설정                      | 소비 속도 |      대비 |  최고 lag |
| ------------------------- | --------: | --------: | --------: |
| 로깅 OFF (베이스라인)     |  37,103/s |         — |   558,632 |
| + `max.poll.records` 2000 |  63,502/s |  **+71%** |   200,548 |
| + `concurrency` 4         |  84,112/s | **+127%** | **4,849** |
| + 둘 다                   |  85,050/s |     +129% |     8,943 |

순위는 그대로지만 크기가 달라졌다. 로깅을 포함한 베이스라인에서는
`max.poll.records` +54% / `concurrency` +147%였는데, 로깅을 끄니 **+71% / +127%**가 됐다.

`concurrency`의 몫이 줄어든 것은 앞선 수치에 **로깅 오버헤드를 4갈래로 나눠 처리한
효과가 섞여 있었기** 때문이다. 반대로 `max.poll.records`의 몫이 커진 것은
레코드당 처리가 가벼워질수록 poll 호출 자체의 오버헤드가 상대적으로 큰 비중이 되기 때문이다.

그리고 **`concurrency` 위에 `max.poll.records`를 더해도 거의 늘지 않는다**(+1%).
스레드가 4개면 각 스레드가 감당할 poll 횟수가 이미 1/4로 줄어 있어서다.
**두 설정은 상당 부분 같은 비용을 줄이고 있다.**

## 발견한 트레이드오프

**조용한 유실이 있었다.** 리스너에서 파싱 실패를 `catch` 하고 `return` 하도록
짜뒀는데, 컨슈머가 멈추지 않게 하려는 의도였다. 깨진 메시지를 토픽에 직접 넣어 확인했다.

```text
WARN  failed to parse CDC message, skipping. offset=4541902 value=THIS-IS-NOT-JSON
파티션 3  current=4541902 → 4541903,  lag=0
```

리스너가 정상 종료했으니 Spring Kafka는 그 레코드를 처리 완료로 보고 오프셋을 커밋한다.
재시도도 없고 어디에도 남지 않는다. `catch`를 지워도 크게 다르지 않다.
`DefaultErrorHandler`가 몇 차례 재시도한 뒤 로그를 남기고 넘어가므로,
**dead letter topic을 붙이지 않으면 결국 버려진다.**

**tombstone도 처리해야 한다.** DELETE 하나에 메시지가 2개 나온다.

![DELETE 시 offset 6에 op=d 이벤트가, offset 7에 value=null인 tombstone이 같은 key로 발행되는 것과 컴팩션 전후 로그를 비교한 도식](@/assets/images/cdc-consumer-lag-optimization/tombstone-and-compaction.svg)

value가 null인 tombstone은 로그 컴팩션 신호다. 컴팩션은 key별 최신 값만 남기는데
삭제된 레코드를 표현할 방법이 없으므로, Kafka는 null value를 "이 key는 삭제됨"으로
약속했다. 컨슈머에서 null 체크를 빼면 바로 다음 줄의 JSON 파싱에서 예외가 터진다.

**측정 지표 자체가 무효화되기도 한다.** 소비 속도를 "발행 종료 후" 구간에서 쟀는데,
컨슈머가 빨라질수록 남은 backlog가 없어져 **개선된 설정이 1,390/s로 측정되는**
역전이 일어났다. 컨슈머가 포화된 구간에서 재도록 바꿔 해결했다.

## 마무리하며

**측정 없이 최적화하면 틀린다.** 손으로 짚은 1순위(로깅), CPU 프로파일의
1순위(JSON 파싱), 실제 최대 레버(병렬성)가 전부 달랐다.

**CPU 프로파일은 절반만, 그것도 한 스레드 안쪽만 보여준다.** `ExecutionSample`은
실행 중인 스레드를 샘플링하므로 대기 시간이 보이지 않고, "스레드가 하나뿐"이라는
구조적 사실도 hot method 목록에는 나타나지 않는다. 그래서 순서가 생겼다 —
**`ThreadCPULoad`로 CPU 포화 여부를 먼저 보고, 포화가 아니면 대기 원인부터 찾는다.**
프로파일을 뜨는 것은 그다음이다.

**베이스라인에서 무엇을 빼야 하는지 정하는 것도 측정 설계다.** 샘플용 장치가
섞여 있으면 개선율이 부풀려질 뿐 아니라 요인 간 상대 크기까지 왜곡된다.

**조합만 비교하면 오귀인이 생긴다.** 해로운 설정(`fetch.bytes`)이 좋은 설정에 가려져
"조합하면 맞물린다"는 잘못된 결론이 나왔다. 한 번에 하나만 바꿔야 한다.

**"lag이 크다"가 곧 "장애"는 아니다.** 최고 lag 115만은 숫자로만 보면 심각하지만
38초면 소진되고 유실도 없었다. 판단 기준은 절대값이 아니라 추세와 소진 시간
(lag ÷ 소비 속도)이다. 생산 폭증이고 소진 시간이 허용 범위면 기다리는 것도 답이다.

lag이 늘었을 때 쓸 순서를 이렇게 정리했다.

1. 소비 처리량을 함께 확인한다 — lag만 보면 컨슈머 저하와 생산 폭증이 구분되지 않는다
2. 추세와 소진 시간을 본다
3. `ThreadCPULoad`로 CPU 포화 여부를 본다 — 포화가 아니면 대기 원인을 찾는다
4. CPU가 포화면 catch-up 구간에서 프로파일을 수집한다
5. 대기가 크면 Kafka 컨슈머 메트릭(`fetch.latency.avg`, `fetch.size.avg`)을 본다
6. 한 번에 하나만 바꿔 검증한다

다음에 확인할 것은 세 가지다. 지금 병목은 컨슈머가 아니라 **Debezium 발행
(약 66,500/s)** 으로 옮겨갔으니 `max.batch.size`와 프로듀서 설정을 봐야 한다.
JSON 파싱은 CPU 1순위지만 컨슈머가 이미 발행을 따라잡아 지금은 손대도 lag이 줄지 않는다.
그리고 dead letter topic은 학습용이라도 붙여두는 편이 맞겠다.
